Chapter 1 · Week 5: Handling Big Data Files: YARN, File Formats & Optimization

The chapter in plain words

Week 5 asks two questions that come up once data is stored in HDFS and processed with MapReduce. First, scheduling: how does one big cluster (for example 1,000 machines) get shared fairly by 50 jobs from different teams at the same time? Second, format: how should data be laid out on disk so a query that needs 3 of 100 columns reads only about 3% of the data? (P1 slide 6)

YARN (Yet Another Resource Negotiator) is the answer to the scheduling question. In Hadoop 1.x one process, the JobTracker, did everything: it handed out cluster resources and also ran every MapReduce job. That made it a bottleneck (about 4,000 nodes maximum) and it could only run MapReduce. Hadoop 2.0 (2013) split the job in two: a global ResourceManager hands out resources, and each job gets its own ApplicationMaster that manages just that job. (P1 slides 7, 9)

Think of YARN as a hotel. The ResourceManager is the front desk that decides who gets which rooms. The NodeManager is the floor manager on each floor who opens rooms and checks they are used properly. The ApplicationMaster is a tour group leader who asks the front desk for rooms and then tells group members which room to go to. A container is one room: a fixed amount of CPU cores and RAM on one machine. (P1 slides 10-11)

YARN can share the cluster with three schedulers: FIFO (first in, first out; one long job can block everyone), Capacity (the cluster is split into queues with guaranteed percentages, e.g. Engineering 60%, Finance 40%, and idle capacity can be borrowed), and Fair (all running jobs get equal shares so short jobs finish fast). DRF (Dominant Resource Fairness) makes fairness work when jobs need different mixes of CPU and RAM. (P1 slides 13-14)

For the format question, the key idea is row storage vs columnar storage. A row store (CSV, JSON, Avro) writes one whole record after another, so reading one column still means reading every column. A columnar store (Parquet, ORC) writes all values of one column together, so a query can read only the columns it needs. On a 100-column, 10 TB table, a 3-column query reads 10 TB from CSV but about 300 GB from Parquet: a 33× speedup from format alone. (P1 slides 6, 16)

Parquet splits a file into row groups (about 128 MB each), each row group into column chunks, and each chunk into pages. The file footer stores the min and max of each column chunk. A query like WHERE score > 90 reads the footer first and skips any row group whose max score is below 90. This skipping is called predicate pushdown. Avro is a row format whose strength is schema evolution: new fields can be added without breaking old readers. ORC is columnar and tuned for Hive with the highest compression. (P1 slides 17-18, 22-23)

Compression codecs trade speed for size: Snappy is fast with medium compression, Gzip is slow with high compression, Bzip2 is slowest but smallest, LZO is fast, Zstd is fast with high compression. The property that matters most is splittability: can the file be cut into pieces that different Mappers read in parallel? A 10 GB gzip CSV is not splittable, so exactly 1 Mapper reads all of it. Parquet + Snappy is splittable at row-group boundaries. Rule of thumb: Parquet + Snappy for analytics, Avro + Snappy for streaming ingest, never raw gzip on big CSV. (P1 slides 20-21)

Part 2 covers the YARN research paper (Vavilapalli et al., ACM SoCC 2013) and LinkedIn's YARN cluster (2013-2016). LinkedIn merged three separate clusters (MapReduce, Spark, Samza) into one 5,000-node YARN cluster using the Capacity Scheduler with 6 queues. Average utilisation went from 45% to 78%, so the same hardware served 73% more work, and the PYMK (People You May Know) job dropped from 18 hours on MapReduce v1 to 4 hours. The big lesson: YARN is the operating system of the cluster and frameworks are its processes. (P2 slides 17, 19, 21)

Part 1 · Student Assessment Pool: MCQ

Q1.Which component in YARN is responsible for global resource allocation across the entire cluster?
  • (a) NodeManager
  • (b) ApplicationMaster
  • (c) ResourceManager
  • (d) NameNode

Answer: (c) ResourceManager

The ResourceManager (RM) is the global cluster resource scheduler. There is one RM per cluster, running on a dedicated master node. Its Scheduler part decides which application gets which containers (P1 slide 10). The instructor note says it plainly: one RM per cluster, one AM per running application (P1 slide 28).

  • (a) NodeManager: a per-node agent. It only launches and watches containers on its own machine.
  • (b) ApplicationMaster: a per-job manager. It asks the RM for resources for one job only. This is the most common wrong choice.
  • (d) NameNode: an HDFS component that stores file metadata. It does not allocate CPU or RAM.
Q2.Which Hadoop file format stores data in columnar format and is best suited for analytical, read-heavy workloads?
  • (a) Avro
  • (b) Text/CSV
  • (c) Parquet
  • (d) JSON

Answer: (c) Parquet

Parquet is columnar: all values of one column are stored together, so a query reads only the columns it needs. Its row groups carry min/max statistics that allow predicate pushdown (skipping whole row groups). It is the standard for Spark, Presto and ML pipelines (P1 slides 17-18). ORC is also columnar, but it is not an option here; the instructor note says ORC would be partly correct for Hive, while Parquet is the broader analytics standard (P1 slide 28).

  • (a) Avro: row-oriented. Its strength is schema evolution for streaming ingest, not analytics.
  • (b) Text/CSV: row-oriented, no built-in schema. A query must read every column.
  • (d) JSON: row-oriented and not splittable in raw form. Used for APIs and logs.
Q3.What does “splittable” mean for a file format in Hadoop?
  • (a) The file can be deleted in parts by HDFS
  • (b) Multiple Mappers can process different parts of the file simultaneously
  • (c) The file format supports splitting schema across multiple NameNodes
  • (d) The file can be distributed across multiple data centres

Answer: (b) Multiple Mappers can process different parts of the file simultaneously

A file is splittable if reading can start from any point in the file without decompressing from the beginning (P1 slide 21). Then each piece (for example each Parquet row group) can go to its own Mapper and they run in parallel. The instructor note adds that splittability enables data-local task scheduling: each Mapper runs on the node that holds its piece (P1 slide 29). Example: a 10 GB gzip CSV is not splittable, so exactly 1 Mapper reads it all (P1 slide 20).

  • (a) Splittability is about parallel reading, not deleting.
  • (c) Schemas are not split across NameNodes; this is made up.
  • (d) Spreading data across data centres is replication/geography, not splittability.
Q4.YARN was introduced in which major Hadoop version, and what did it replace?
  • (a) Hadoop 1.0; replaced the NameNode
  • (b) Hadoop 2.0; replaced the monolithic JobTracker with a decoupled ResourceManager + ApplicationMaster
  • (c) Hadoop 3.0; replaced DataNodes with Containers
  • (d) Hadoop 2.0; replaced the Secondary NameNode with a Standby NameNode

Answer: (b) Hadoop 2.0; replaced the monolithic JobTracker with a decoupled ResourceManager + ApplicationMaster

In Hadoop 1.x the JobTracker did both resource management and job scheduling, only ran MapReduce, and topped out at about 4,000 nodes. Hadoop 2.0 (2013) separated the two jobs: a global ResourceManager plus one ApplicationMaster per job (P1 slides 7, 9).

  • (a) Wrong version, and YARN did not touch the NameNode (that is HDFS).
  • (c) Wrong version; containers are resource slices, they do not replace DataNodes (which store HDFS blocks).
  • (d) Right version but wrong change. The Standby NameNode (HDFS high availability) is also a Hadoop 2.0 feature, but it has nothing to do with YARN. The instructor note calls this the common distractor (P1 slide 29).

Part 1 · Student Assessment Pool: Descriptive

D1.Explain YARN’s three-component architecture — ResourceManager, NodeManager, and ApplicationMaster. Draw a diagram showing how they interact when a Spark job is submitted to the cluster.

Definition. YARN (Yet Another Resource Negotiator) is Hadoop 2's resource manager. It separates cluster resource management from per-job execution logic using three components (P1 slides 10-11).

  1. ResourceManager (RM): one per cluster, on a master node. Its Scheduler hands out containers (pluggable: FIFO, Capacity, Fair). Its ApplicationsManager accepts job submissions and starts the first container for each ApplicationMaster.
  2. NodeManager (NM): one per worker node. It launches and monitors containers, reports node health and container status to the RM by heartbeat, and enforces CPU/RAM limits per container.
  3. ApplicationMaster (AM): one per running job. It requests containers from the RM, tells NMs to launch tasks in them, watches progress, re-requests containers for failed tasks, and releases containers when done.

A container is a slice of one node: a set number of CPU cores plus a set amount of RAM.

Diagram (Spark job submission, P1 slide 12):

 Client --(1) submit job--> ResourceManager
                              |  (2) launch AM container
                              v
                     Spark ApplicationMaster
          (3) register + request executor containers --> RM
                 |              |              |
       (4) launch task   (4) launch task  (4) launch task
                 v              v              v
           NodeManager 1  NodeManager 2  NodeManager 3
           [Executor]     [Executor]     [Executor]
                 \--------(5) task status--------/ --> AM
          (6) AM unregisters from RM on completion

Example (P1 slide 11): the Spark AM asks for 100 containers of 4 cores and 8 GB each. The cluster is busy, so the RM grants 80. The AM runs Spark executors in those 80 containers and assigns tasks to them.

D2.What is columnar storage? Why does it improve performance for analytics queries that select only a subset of columns? Use a concrete example with numbers to illustrate the I/O reduction.

Definition. Columnar storage writes all the values of one column next to each other on disk, instead of writing one full row after another. Parquet and ORC are columnar; CSV, JSON and Avro are row stores (P1 slides 16-17).

Why it is faster for analytics:

  • Less I/O. A query reads only the columns it names and physically skips the rest. In a row store, SELECT score FROM users still reads id, name and age, because they sit in the same row on disk (P1 slide 16).
  • Skipping row groups. Parquet keeps min/max stats per column chunk in its footer, so a filter like WHERE score > 90 skips whole row groups without reading them (predicate pushdown, P1 slide 23).
  • Better compression. Values in one column are of the same type and often similar, so they compress well.

Worked example (P1 slide 6): a 100-column table holds 10 TB. A query selects 3 columns.

  • CSV (row store) reads all 10 TB.
  • Parquet reads 3/100 of the data = 0.03 × 10 TB = 300 GB.
  • I/O reduction = 1 − 3/100 = 97%. Speedup ≈ 100/3 ≈ 33× from format alone.

Analogy: a library that shelves each chapter type together lets you grab only "Chapter 3" of every book, instead of carrying every whole book to your desk.

D3.Compare Avro and Parquet. Explain what “schema evolution” means and why Avro handles it better. In which scenarios would you use each?

Schema evolution means the structure of the records (the schema: field names and types) changes over time, for example a new field is added, while old files and old programs keep working.

Why Avro handles schema evolution better: Avro stores the writer schema with the data and lets the reader supply its own reader schema. Avro then matches fields by name: a field the reader expects but the file lacks gets its default value; a field in the file that the reader does not know is ignored. This gives backward and forward compatibility. Example: when LinkedIn adds a new field to a Kafka event schema, old consumers reading the same HDFS files do not break (P1 slide 18).

When to use each (P1 slides 25-26):

  • Avro: streaming ingest (Kafka → HDFS), data exchange / APIs, anywhere records are appended and the schema keeps changing. bKash ingests Kafka events as Avro for API versioning.
  • Parquet: Spark analytics pipelines and ML feature tables, where queries read a few columns of many rows. bKash converts nightly to Parquet + Snappy for analytics.

Part 1 · Student Assessment Pool: Analytical

A1.Data Lake Performance Migration: A Dhaka-based telecom company stores 10 TB of daily call-detail records (CDR) on HDFS as gzip-compressed CSV files. Their data engineers report that a Hive query selecting 4 of 80 columns takes 6 hours. – Identify two specific reasons why this configuration is slow – Propose a migration strategy: new format, compression codec, and partitioning scheme – Estimate the expected I/O reduction (show your calculation) – What YARN scheduler would you use and why, given that multiple teams share the cluster?

Step 1: Two reasons it is slow

  1. Gzip is not splittable. Each gzip file must be read from its start by exactly one Mapper. A big gzip CSV gets no parallelism even though HDFS stores it in many blocks (P1 slide 20). Most of the cluster sits idle.
  2. CSV is a row store. To read 4 columns, Hive must read and parse all 80 columns of every row, so it reads the full 10 TB (P1 slides 6, 16). There are also no min/max stats, so no row group can be skipped.

Step 2: Migration strategy

  • Format: ORC or Parquet (columnar). For a Hive warehouse the slides recommend ORC (best compression, Hive ACID, vectorized reads); Parquet is the choice if Spark also reads it (P1 slide 25).
  • Codec: Snappy for hot data (fast, and the file stays splittable at row-group/stripe boundaries). Use Zlib for ORC in Hive, or Zstd for cold archive data (P1 slides 21, 25).
  • Partitioning: partition by date, like bKash's dt=YYYY-MM-DD/region= (P1 slide 26), e.g. dt=2026-10-13/region=Dhaka. A query for one day or region then reads only that folder.
  • Run a one-time conversion job (Hive INSERT OVERWRITE ... STORED AS ORC or a Spark job) and convert new data nightly.

Step 3: I/O reduction estimate

  • Fraction of columns read = 4 / 80 = 0.05 = 5%.
  • Data read per day = 10 TB × 0.05 = 0.5 TB = 500 GB.
  • I/O reduction = 1 − 0.05 = 0.95 = 95%, i.e. 80/4 = 20× less data.
  • If the query is I/O-bound, time drops roughly from 6 h = 360 min to 360 × 0.05 = about 18 minutes. This is a rough estimate; in practice it can be faster, because the files are now splittable (many Mappers in parallel), and predicate pushdown and date partitions skip even more data.

Step 4: Scheduler choice

Use the Capacity Scheduler. It splits the cluster into queues with guaranteed shares, e.g. a production ETL queue, an analyst ad-hoc queue and a data-science queue, and lets a queue borrow idle capacity from others (P1 slide 13). One team's huge job cannot starve the others, as in the a2i example where queue A keeps its 60% guarantee (P1 slide 14). FIFO is unsuitable because one long job blocks everyone. Fair Scheduler is a reasonable alternative if the main goal is quick turnaround for short ad-hoc queries.

A2.YARN Failure Trace: A NodeManager (NM2) hosting 5 running containers for a MapReduce job fails mid-execution. Trace the complete failure recovery sequence: which components detect the failure, in what order, what state changes occur in the ResourceManager, and how are the 5 containers’ tasks restarted.

Background: every NodeManager sends a regular heartbeat (an "I am alive" message with node health and container status) to the ResourceManager (P1 slide 10).

  1. Failure happens. NM2 crashes. Its 5 containers die with it, and NM2 stops sending heartbeats.
  2. RM detects it. The ResourceManager notices the missing heartbeats. After the timeout (more than 10 minutes, P2 slide 11) it declares NM2 lost.
  3. RM state changes. The RM marks NM2 as lost/unhealthy, removes its CPU and RAM from the pool of schedulable capacity, and marks all 5 containers on NM2 as failed (P1 slide 12).
  4. AM is notified. The RM tells the job's MapReduce ApplicationMaster that its 5 containers failed (P2 slide 11). The AM may also have noticed earlier, because it stopped getting task status from those containers.
  5. AM re-requests resources. The AM asks the RM for 5 replacement containers of the same size (P1 slide 11: "re-requests containers for failed tasks").
  6. RM allocates elsewhere. The Scheduler grants containers on healthy nodes, e.g. NM1 and NM3, ideally on nodes holding HDFS replicas of the input blocks (data locality).
  7. Tasks restart. The AM tells NM1/NM3 to launch the 5 tasks in the new containers. Map tasks re-run from the start of their input split (input is safe in HDFS, which keeps replicas). Completed map tasks whose output lived on NM2's local disk may also need to be re-run, because reducers can no longer fetch that output.
  8. Job continues. New containers send status to the AM; the job finishes normally, only later.

Edge cases: if the AM itself had been on NM2, the RM restarts a new AM (up to yarn.resourcemanager.am.max-attempts, default 2); MapReduce's AM can recover job state from HDFS checkpoints (P1 slide 12, P2 slide 11). If the RM failed, a Standby RM takes over via ZooKeeper in under 60 seconds (YARN 2.4+, P2 slide 11).

Part 2 · Discussion Questions

L1.Resource consolidation increases utilisation: merging 3 siloed clusters into one raised average utilisation from 45% to 78% — the same capacity served 73% more workload

Note: P2 slide 21 lists these as lessons, not separate questions; each is treated here as a discussion prompt.

What it means. A silo is a cluster kept for one workload only. Before YARN, LinkedIn ran three: Cluster A for MapReduce/Hive ETL, Cluster B for Spark, Cluster C for Samza streams (P2 slide 16). Each sat idle at different times, but idle machines in one silo could not help a busy one. One shared YARN cluster lets any workload use any idle machine.

The numbers. Utilisation went from 45% to 78% (P2 slide 19). 78 / 45 = 1.73, so the same hardware did 73% more work. At 45% the silos wasted 55% of their capacity; at 78% only 22% is unused.

For consolidation:

  • Peaks in one workload fill gaps in another, so less hardware sits idle.
  • No cross-cluster data copying, which had added latency; all frameworks read the same HDFS (P2 slides 16, 18).
  • One configuration to manage instead of three, which had tripled ops cost (P2 slide 16).

Against / risks:

  • Workloads now compete; without queues and guarantees, one team can slow another (handled by the Capacity Scheduler, lesson L2).
  • Borrowing capacity means taking it back later, which needs pre-emption that can kill jobs (lesson L3).
  • One shared cluster is a bigger single point of failure, so ResourceManager HA (ZooKeeper, P2 slide 11) becomes essential.

Conclusion. The utilisation gain is large and measured, so consolidation wins, provided scheduling and isolation are set up carefully.

L2.Capacity Scheduler enables SLAs: production queues guaranteed minimum resources; analyst adhoc queries cannot starve revenue-generating pipelines

What it means. An SLA (service level agreement) is a promise such as "the nightly ETL finishes by 6 a.m." Starving a job means it never gets enough resources to run. The Capacity Scheduler splits the cluster into queues with guaranteed shares. LinkedIn used 6 queues: production 40%, spark 25%, samza 15%, adhoc 10%, tez 7%, reserve 3% (P2 slide 17).

For:

  • Production (Hive ETL, Pig) always has at least 40%, so a flood of analyst queries cannot delay revenue pipelines such as ad targeting.
  • Unused capacity is not wasted: other queues borrow it elastically (P1 slide 13).
  • Same idea in Bangladesh: a2i keeps DGHS batch jobs at 60% so streaming cannot take over (P1 slide 14).

Against / limits:

  • Fixed percentages need regular tuning; if needs change, a queue may be too small while another is oversized.
  • Analysts in the 10% adhoc queue may wait long at busy times. The Fair Scheduler gives short jobs faster turnaround (P1 slide 13).
  • Getting borrowed capacity back quickly needs pre-emption (L3).

Conclusion. For a shared cluster with revenue-critical jobs, guaranteed queues are the safer choice; Fair suits clusters with many short, equal-priority jobs.

L3.Pre-emption needs tuning: aggressive pre-emption killed long-running Spark jobs; LinkedIn set 30-second grace periods and added Spark checkpoint-on-preempt hooks

What it means. Pre-emption is the scheduler taking containers back from a queue that borrowed them, so the owning queue gets its guarantee. A grace period is a warning time before the container is killed. A checkpoint saves a job's progress so it can resume instead of restarting.

For pre-emption:

  • Without it, borrowed capacity might never return, and guarantees (L2) would be empty promises.
  • It makes borrowing safe, which is what drives utilisation up (L1).

Against / costs:

  • Killing a container wastes all the work done in it. Long Spark jobs, such as PYMK's multi-hour graph run (4 h on YARN, P2 slide 19), lost the most.
  • Too-aggressive settings mean jobs keep restarting and the cluster does work twice.

LinkedIn's fix (P2 slides 17, 21): a 30-second warning before reclaiming capacity, plus Spark hooks that checkpoint state when pre-empted, so the job resumes rather than starts over.

Conclusion. Pre-emption is needed, but its timing must match the workload: fast for short tasks, gentle (grace + checkpoints) for long-running ones.

L4.YARN is the OS; frameworks are processes: the paradigm shift — the cluster is the computer, YARN is its kernel

What it means. On a laptop, the operating system kernel gives CPU and memory to programs (processes) and isolates them from each other. YARN plays the same role for a whole cluster: the ResourceManager hands out containers (CPU + RAM) and NodeManagers enforce limits, while MapReduce, Spark, Tez and Samza are just applications, each with its own ApplicationMaster (P2 slides 7, 9).

For the analogy:

  • YARN is framework-agnostic: any framework that writes an AM can run (P2 slide 9).
  • Isolation like an OS: cgroups for CPU and memory limits; a container over its memory limit is killed to protect others (P2 slide 9).
  • The container model became the ancestor of Kubernetes Pods, and the three-tier design (global scheduler / node agent / per-app master) is the same in Kubernetes (P2 slides 13, 27).

Against / limits:

  • YARN only manages CPU and memory; it is not a full OS (no file system of its own, it relies on HDFS).
  • Kubernetes has largely replaced YARN for new deployments (P2 slide 13), so YARN is one kernel among several, not the only one.

Conclusion. The analogy holds for resource management and isolation, and explains why separating the scheduler from per-app logic made Hadoop a general cluster platform.

L5.Samza on YARN: stream processing is just another set of long-running containers; YARN’s fault tolerance restarts failed Samza tasks

What it means. Samza is LinkedIn's stream processing framework, built natively for YARN (P2 slide 13). A stream job never "finishes": it keeps reading Kafka events. On YARN it is simply a set of containers that stay alive indefinitely, in the samza queue (15%, P2 slide 17).

For:

  • No separate streaming cluster (the old Cluster C, P2 slide 16); streams share hardware with batch jobs.
  • Free fault tolerance: if a node fails, the RM marks its containers failed and the AM gets replacements elsewhere (P2 slide 11).
  • It worked at scale: Samza Kafka lag stayed under 500 ms at p99 (P2 slide 19).

Against / risks:

  • Long-running containers hold capacity permanently, so the queue must be sized for peak stream load.
  • Pre-emption or a node failure interrupts the stream; YARN's NodeManager failure detection (heartbeat timeout over 10 minutes, P2 slide 11) is slow for real-time data unless the framework recovers faster itself.
  • Restarted tasks must resume from the right Kafka position to avoid lost or duplicate events; that is the framework's job, not YARN's.

Conclusion. Treating streams as long-lived containers lets one cluster serve batch and streaming, but streaming needs its own guaranteed queue and fast recovery logic.

LE.Task (20 minutes, pairs) Model LinkedIn’s 5,000-node YARN cluster in Python. NODES    = 5_000
RAM_GB   = 64
VCPUS    = 16

  "production": 0.40,

  "samza":      0.15,

Dominant Resource Fairness (DRF)

Share of resource r for user i = used_i,r / total_r
Dominant share_i = max over r of that share
DRF: keep giving the next task to the user with the lowest dominant share, until something runs out (ends with equal dominant shares).
What each symbol means
  • used_i,r: amount of resource r (CPU or RAM) user i holds
  • total_r: cluster total of resource r
  • Dominant resource: the resource a user needs the largest fraction of

The slides name DRF (Ghodsi et al., 2011) for fairness across CPU and memory (P1 slide 14); the formula is the paper's standard definition.

Worked example

Cluster: 9 CPU, 18 GB. User A tasks need <1 CPU, 4 GB>; user B tasks need <3 CPU, 1 GB>.

  • A per task: CPU 1/9, RAM 4/18 = 2/9. Dominant = RAM.
  • B per task: CPU 3/9 = 1/3, RAM 1/18. Dominant = CPU.
  • Give A 3 tasks and B 2 tasks: A uses 3 CPU, 12 GB (dominant share 12/18 = 2/3); B uses 6 CPU, 2 GB (dominant 6/9 = 2/3).
  • Totals: 9 CPU used (all), 14 GB used. Dominant shares are equal, so allocation is fair.

Chapter 2 · Week 6: Apache Spark: RDDs, DataFrames & In-Memory Computing

The chapter in plain words

The problem Spark solves. MapReduce (Week 4) writes every intermediate result to HDFS (the cluster's shared disk) before the next step can start. That is fine for a job that reads the data once. It is very slow for iterative algorithms, which pass over the same data again and again, such as K-Means clustering, logistic regression or PageRank. Example from the slides: 100 K-Means iterations over 50 GB cost 10 TB of disk I/O in MapReduce, but only 50 GB in Spark (P1 slide 6).

The big idea: keep the working data in RAM. Spark reads the data from HDFS once, keeps it in the cluster's memory (RAM), and runs every later iteration from memory. Reading RAM is far faster than reading disk. Analogy: MapReduce is a cook who puts every ingredient back in the store room after each step; Spark keeps them on the kitchen counter. Spark came from Matei Zaharia's PhD work at UC Berkeley AMPLab (2009 to 2013) (P1 slide 9).

Architecture: three parts. The Driver runs your main program, creates the SparkContext/SparkSession and builds the plan (a DAG, a graph of steps). The Cluster Manager (YARN, Kubernetes, Mesos or Spark Standalone) hands out machines and memory. Executors are worker processes (JVMs) on worker nodes that run tasks and hold cached data in memory (P1 slide 11).

RDD = Resilient Distributed Dataset. The core data object in Spark. It is a read-only, partitioned collection of records. Partitioned means it is split into pieces spread over many Executors so they work in parallel. Immutable (read-only) means you never change it; each operation makes a new RDD. Lineage means each RDD remembers the recipe of steps that built it from its parents (P1 slide 13).

Resilient = it can rebuild itself. HDFS protects data by keeping 3 copies. Spark instead keeps the recipe (lineage). If an Executor crashes and a partition is lost, Spark re-reads that piece of the input and re-applies the same steps. "The computation is the backup" (P1 slide 14).

Transformations vs. actions, and lazy evaluation. A transformation (map, filter, flatMap, reduceByKey, join...) only records a step in the plan and returns a new RDD; nothing runs yet. An action (count, collect, first, take, reduce, saveAsTextFile) starts the real work and returns a result to the Driver or writes to storage. Waiting until an action is called is lazy evaluation. It lets Spark see the whole plan, run filter and map together in one pass, and stop early (for example first() stops at the first match) (P1 slides 17 to 19).

Narrow vs. wide dependencies. In a narrow dependency each output partition needs at most one input partition (map, filter): no data moves between machines, and steps are chained in one stage. In a wide dependency an output partition needs data from many input partitions (groupByKey, reduceByKey, join): data must be shuffled (sent across the network), which starts a new stage and is the main cost in Spark. Prefer reduceByKey over groupByKey because it combines locally before the shuffle (P1 slides 21 to 22).

DataFrames, the ecosystem, and the papers. A DataFrame is a distributed table with named columns and a schema. The Catalyst optimizer rewrites DataFrame/SQL queries before running them, so DataFrames are 10 to 100 times faster than raw RDDs for structured data (P1 slide 26). On top of Spark Core sit Spark SQL, MLlib (machine learning), Structured Streaming and GraphX (P1 slide 29). Part 2 covers the two Zaharia papers (2010 HotCloud, 2012 NSDI best paper) and the Databricks GraySort record: 100 TB sorted in 23 minutes on 206 nodes, against Hadoop's 72 minutes on 2,100 nodes (P2 slides 13 to 14).

Part 1 · Student Assessment Pool: Descriptive

D1.Explain the concept of a Resilient Distributed Dataset (RDD). What does “resilient” mean in this context? How does Spark recover a lost RDD partition without replication?

Definition. An RDD is a read-only, partitioned collection of records. It can only be created in two ways: by loading data from stable storage (HDFS, S3) or by transforming an existing RDD (map, filter) (P1 slide 13).

Five properties (P1 slide 13):

  • Immutable: never changed in place; each transformation makes a new RDD.
  • Partitioned: split into pieces spread across Executors, so the pieces are processed in parallel.
  • Lazy: transformations run only when an action is called.
  • Lineage: each RDD knows exactly how it was derived from its parents.
  • Resilient: lost partitions are recomputed from lineage, not replicated.

What "resilient" means. The RDD can survive a machine failure. HDFS does this by storing 3 copies. An RDD does it by remembering the steps (its lineage) and re-running them. "The computation is the backup" (P1 slide 14).

Recovery steps (P1 slides 14 to 15):

  1. Spark detects that a partition (say Part 2 of mappedRDD) is lost because its Executor crashed.
  2. It traces the lineage: mappedRDD came from filteredRDD, which came from inputRDD.
  3. It re-reads only Part 2 of the input from HDFS.
  4. It re-applies filter, then map, to that one partition.
  5. Part 2 is restored without restarting the whole job.

Trade-off: this is cheap for narrow dependencies but expensive for wide ones, so long lineage chains should be checkpointed to HDFS (P1 slide 14).

Diagram (text form):
inputRDD (HDFS) → filter → filteredRDD → map → mappedRDD [Part 2 lost] ⇒ re-read input Part 2 → filter → map → Part 2 restored.

Analogy: instead of photocopying a finished cake three times, you keep the recipe. If the cake is dropped, you bake that one cake again.

Transformation: an operation that builds the computation DAG and returns a new RDD, but does not run straight away (lazy) (P1 slide 17).

Action: an operation that triggers execution of the DAG and returns a value to the Driver or writes to storage (eager) (P1 slide 18).

Why not execute immediately? Rule: no transformation executes until an action is called (P1 slide 18). Waiting lets Spark:

  • see the whole DAG first and optimise it (DAG scheduler, or Catalyst for DataFrames);
  • pipeline steps, for example run filter and map in one pass over each partition, without writing intermediate results to disk;

D3.Describe Spark's lazy evaluation model. What is the advantage of deferring computation until an action is called? Use the example rdd.filter(x > 1000).first() to illustrate.

Definition. Lazy evaluation means Spark does not run a transformation when you write it. It only records it in a computation graph (the DAG). The work starts only when an action is called (P1 slide 19).

What happens when the action is called (P1 slide 19):

  1. Spark analyses the full DAG.
  2. It applies the Catalyst optimizer (for DataFrames) or Spark's DAG scheduler.
  3. It pipelines compatible transformations, e.g. filter and map in one pass over each partition, never writing intermediate results to disk.
  4. It executes only the partitions needed.

Advantages:

  • Less work: Spark can stop early and skip partitions it does not need.
  • Fewer passes and no intermediate disk writes, thanks to pipelining.
  • Whole-plan optimisation, since Spark sees all steps before running any.
  • Lineage stays as a plan, which is what fault recovery replays.

Example: rdd.filter(x > 1000).first()

  1. filter(x > 1000) is a transformation: Spark only notes "keep values above 1000". No data is read.
  2. first() is an action: now Spark starts reading the first partition and tests values one by one.
  3. As soon as it finds one value above 1000, it returns it and stops.
  4. Without lazy evaluation, Spark would first filter the entire dataset, then take one element, wasting almost all the work (P1 slide 19).

Analogy: you write a shopping list (transformations) but only go to the shop when you need dinner (action). If you only need one item, you grab it and leave instead of buying the whole list.

With realistic gains from skipping the HDFS writes and pipelining, the slides quote 10 to 100× for iterative work (P1 slide 31).

Step 4: when Spark would NOT outperform MapReduce.

  • Single-pass jobs: one read, one write. There is no reuse, so caching gives nothing. For single-pass ETL over data larger than RAM, gains are only 2 to 5× (P2 slide 16).
  • Data does not fit in cluster RAM: partitions spill to disk or are evicted (LRU) and recomputed, so Spark loses its edge (P2 slide 10).
  • Memory overhead too high: Spark needs about 8 GB per Executor minimum; on very large clusters with little RAM per node this can be prohibitive (P1 slide 32).
  • Stable existing MapReduce code that is already fast enough (P1 slide 32).
  • Workloads that hurt the JVM memory model, such as many small files or high-cardinality groupBy (P2 slide 16).
A2.RDD Failure Recovery Trace: A Spark job computes input → filteredRDD → mappedRDD → reducedRDD over 10 partitions. Mid-execution, the Executor holding partitions 3 and 7 of reducedRDD crashes. Trace the complete recovery sequence: what does the Driver detect, which partitions of which RDDs need to be recomputed, and what is the worst-case recovery cost if reducedRDD involves a wide dependency (groupByKey)?

Step 1: the stages. filter and map are narrow, so input → filteredRDD → mappedRDD is pipelined in Stage 1 (10 tasks, one per partition). groupByKey is wide, so it needs a shuffle and starts Stage 2, which builds reducedRDD (10 tasks) (P1 slides 20 to 21). Stage 1 tasks write shuffle output files on the local disk of the Executor that ran them.

Step 2: what the Driver detects. The Driver coordinates execution (P1 slide 11). It sees that the Executor is lost (it stops responding) and that the tasks for reducedRDD partitions 3 and 7 failed. It marks those two partitions as missing. Partitions 0 to 2, 4 to 6, 8 and 9 are unaffected.

Step 3: trace the lineage. reducedRDD came from mappedRDD by groupByKey; mappedRDD came from filteredRDD by map; filteredRDD came from input by filter (P1 slide 15).

Step 4: what must be recomputed.

  • If it were narrow all the way (for comparison): rebuild only partitions 3 and 7 at each level: re-read input partitions 3 and 7, re-apply filter and map, then the last step. That is 2 of 10 partitions = 20% of the work (P1 slide 21, "recompute only that partition from its single parent partition").
  • With groupByKey (wide): reducedRDD partition 3 holds every value for the keys that hash to 3, and these values came from all 10 mappedRDD partitions. The same holds for partition 7. So each lost partition depends on all 10 parent partitions (P1 slide 21).

Step 5: best case vs. worst case.

  • Best case: the Stage 1 shuffle files are still on surviving nodes. The Driver re-runs only 2 Stage 2 tasks (partitions 3 and 7), which fetch their data again from all 10 map outputs. No filter or map work is repeated.
  • Worst case: the crashed Executor also stored Stage 1 shuffle output (it likely ran map tasks too), or none of mappedRDD is cached. Then the fetch fails and the Driver must re-run Stage 1: re-read all 10 input partitions from HDFS, re-apply filter and map to all 10 (filteredRDD and mappedRDD partitions 0 to 9), redo the full shuffle, then rebuild reducedRDD partitions 3 and 7. That is 10 + 10 + 10 = 30 partition computations in Stage 1 plus 2 in Stage 2, i.e. close to rerunning the whole job, against 2 × 4 = 8 partition computations in the narrow case.

Step 6: how to limit the cost. Use reduceByKey instead of groupByKey so less data is shuffled (P1 slide 22); cache mappedRDD; checkpoint long lineage chains to HDFS (P1 slide 14). This is why wide dependencies make lineage recovery "expensive" (P1 slide 21).

Part 2 · Discussion Questions

1.In-memory is a multiplier, not a panacea: Spark is 10–100× faster on iterative workloads; for single-pass ETL over data larger than RAM, gains are smaller (2–5×)

Note: P2 slide 16 is titled "Lessons Learned & Discussion Questions", but the rendered slide shows only the five "Key Lessons from Spark's Rise". No separate question list is printed on it (it seems to have been cut off). Each lesson is copied below exactly and answered as a discussion point.

Meaning. A multiplier makes an existing advantage bigger; a panacea fixes everything. Memory helps most when the same data is read many times.

For (where Spark wins big): iterative jobs reuse the working set. RDD paper: logistic regression 127 s/iteration on Hadoop vs. 0.96 s on Spark, 132×; K-means 150 s vs. 5 s, 30× (P2 slide 10). Databricks: logistic regression on 1 TB took 2 min on Spark vs. 10+ hours on Mahout (P2 slide 15).

Against (where gains are small): single-pass ETL (extract, transform, load) reads each byte once, so there is nothing to cache; if the data is larger than RAM, Spark spills to disk like MapReduce. Gains drop to 2 to 5×.

Conclusion: choose Spark by workload shape: more than 2 iterations over the same data favours Spark (P1 slide 32).

2.The lineage model scales elegantly: re-computing a lost partition from lineage is cheaper than maintaining 3× replicated in-memory state

For: replicating in-memory data 3 times would triple RAM use and send every write over the network. Lineage stores only the small list of steps, and failures are rare, so you pay only when something breaks. Only the lost partitions are rebuilt (P1 slide 14).

Against: recovery is cheap only for narrow dependencies. With wide dependencies (groupByKey, join) a lost partition may need all parent partitions recomputed, and long chains get slow to replay. The fix is to checkpoint long lineage chains to HDFS (P1 slides 14, 21).

Conclusion: lineage is the better default for iterative in-memory work, with checkpoints as a safety net (P2 slide 20).

3.Shuffle is the bottleneck: both at GraySort and in production; minimising wide dependencies (shuffle) is the primary Spark tuning skill

Why shuffle costs so much: a wide dependency moves data across the network, writes it to disk, and creates a stage boundary (a barrier where all tasks must finish) (P2 slide 9).

Evidence from GraySort: Spark won mainly by making the shuffle cheaper: sort-based shuffle that writes sorted runs once (saving about 120 TB of extra I/O at 100 TB), all 8 SSDs used as shuffle directories, off-heap sort buffers, and a single wide transformation (sortByKey) (P2 slide 15).

Tuning moves: prefer reduceByKey over groupByKey (local combine first, P1 slide 22); co-partition two RDDs on the same key so a join needs no shuffle (P2 slide 10); avoid unneeded repartition/distinct.

Other side: some shuffles cannot be avoided (a global sort or join needs them), so the goal is to minimise them, not remove them.

4.Benchmark marketing is real: GraySort made Spark famous; it also hid cases where Spark's JVM memory overhead hurt performance (many small files, high-cardinality groupBy)

Positive side: the record (100 TB in 23 min on 206 nodes vs. Hadoop's 72 min on 2,100 nodes) drew huge press. Spark went from 200 GitHub stars in 2013 to more than 36,000 by 2020, and Databricks raised a $150M Series B within 6 months (P2 slides 14 to 15).

Negative side: a benchmark tests one workload on tuned hardware (206 large EC2 nodes with 244 GB RAM and 8 SSDs each). It hides weak spots: many small files (overhead per file and task) and high-cardinality groupBy (a huge number of distinct keys, which fills JVM memory and causes garbage-collection pauses).

Lesson: test a system on your own workload before trusting a headline number.

5.Open-source velocity: the Apache Spark community grew to 1,000+ contributors in 5 years; Databricks’ business model (cloud + support) aligned commercial incentives with open-source development

For: Spark was donated to Apache in 2013 and Databricks was founded the same year (P1 slide 9). Because Databricks earns from cloud service and support, not from licences, improving the free engine also helps its business. The result was fast growth: 1,000+ contributors in 5 years, and libraries such as Spark SQL, MLlib, Structured Streaming, GraphX and Delta Lake (P2 slide 11).

Risk (other side): when one company leads a project, its priorities can shape the roadmap, and some features may appear first in the paid product. Users should watch for vendor lock-in.

Conclusion: an open engine plus a paid service gave Spark both community trust and steady funding, which helped it become the default engine at Netflix, LinkedIn, Alibaba and Uber (P1 slide 9).

Iterative disk I/O: MapReduce vs. Spark

MR_IO = k × (D_read + D_write)
Spark_HDFS_IO = D (read once)
Reduction = MR_IO / Spark_HDFS_IO
What each symbol means
  • k: number of iterations
  • D: dataset size
  • D_read, D_write: data read and written to HDFS per iteration (both = D in the slide example)
  • Reduction: how many times less disk I/O Spark does
Worked example

K-Means, D = 50 GB, k = 100 (P1 slide 6).

  • MR_IO = 100 × (50 + 50) = 10,000 GB = 10 TB
  • Spark_HDFS_IO = 50 GB
  • Reduction = 10,000 / 50 = 200×
Practice

  • MR_IO = 30 × (20 + 20) = 1,200 GB = 1.2 TB
  • Spark = 20 GB
  • Reduction = 1,200 / 20 = 60×

t = size / speed
T_MR = k × (D/R_hdfs + D/W_hdfs)
T_Spark = D/R_hdfs + (k − 1) × D/R_ram
Speedup = T_MR / T_Spark
What each symbol means
  • R_hdfs: HDFS read speed (MB/s); W_hdfs: HDFS write speed (assumed equal to R_hdfs when not given)

Throughput = data / time
Total resource = nodes × per-node amount

Hash partitioning and shuffle volume

partition = key.hashCode() % numPartitions
groupByKey records shuffled = total pairs
reduceByKey records shuffled ≤ partitions × distinct keys per partition
What each symbol means
  • hashCode(): a number computed from the key
  • %: remainder after division
  • numPartitions: number of output partitions
Worked example

Chapter 3 · Week 7: Querying Big Data: Hive, HiveQL & the SQL-on-Hadoop Ecosystem

The chapter in plain words

The problem Hive solves. Hadoop stores huge data on HDFS and processes it with MapReduce (MR), but every MR job had to be a Java program, often 100+ lines for a simple GROUP BY. Analysts know SQL, not Java, so a simple question took days to answer (P1 slide 5). Facebook needed thousands of non-engineers to query petabytes.

Hive = SQL on top of Hadoop. Apache Hive (Facebook, 2008) gives you HiveQL, a SQL-like language. You write SELECT; Hive translates it into MapReduce jobs, Tez DAGs or Spark jobs (the "execution engine"). Analogy: you order food in your own language and the waiter (Hive) translates it into kitchen instructions (MR jobs) (P1 slide 5).

The parts of Hive. HiveServer2 accepts queries from clients (Beeline, JDBC, Tableau). The Driver parses, checks, plans and optimises the query. The Metastore is a normal relational database (MySQL/PostgreSQL) that stores table schemas, partition lists and HDFS file locations. The Execution Engine runs the jobs. HDFS holds the actual data: a table is a directory, a partition is a sub-directory (P1 slides 8-9).

Schema-on-read. A traditional database (MySQL) checks data when you INSERT it (schema-on-write) and rejects bad rows. Hive just copies files to HDFS and applies the schema only when you query. Loading is fast and flexible, but bad values show up silently as NULL at query time (P1 slides 13-14).

Partitioning and bucketing. Partitioning splits a table into HDFS sub-directories by a low-cardinality column such as date or country, so a query with WHERE on that column reads only the matching folders (partition pruning). Bucketing splits data further into a fixed number N of files using hash(column) % N, so two tables bucketed the same way on a join key can be joined bucket-by-bucket without a big shuffle (P1 slides 19-24).

Hive is batch, not interactive. HiveQL looks like SQL, but a COUNT(*) on 1 TB can take 5-10 minutes on MapReduce because MR writes intermediate results to disk between stages. Presto (Meta, 2013) keeps everything in an in-memory pipeline and answers in seconds. Use Hive for big ETL and nightly jobs, Presto/Trino or Spark SQL for dashboards and ad-hoc questions (P1 slides 17, 26).

The research and the case study. Thusoo et al. (VLDB 2009, ICDE 2010) describe Hive at Facebook: 2 PB, 15 TB/day growth, 7,500+ queries/day, 200+ analysts. Their most lasting idea is the Metastore, now the shared catalogue for Spark, Presto/Trino, Impala and AWS Glue (P2 slides 5-12). Spotify used HiveQL plus Spark, scheduled with Luigi, over ~3 billion events/day and 2 billion playlists to build Discover Weekly (P2 slides 14-18).

D1.Explain the Hive architecture: what is the role of HiveServer2, the Driver, and the Metastore? How is a HiveQL query compiled into executable jobs? Draw the component diagram.

Definition. Hive is a data warehouse layer on Hadoop that turns SQL-like HiveQL queries into distributed jobs over files on HDFS (P1 slide 5).

Roles (P1 slide 8):

  • HiveServer2: the front door. A JDBC/ODBC server that authenticates users and accepts HiveQL from Beeline, BI tools (Tableau, Power BI) and JDBC drivers.
  • Driver: the brain. It runs the pipeline Parser, Semantic Analyser, Logical Planner, Query Optimizer, Physical Plan Generator, and manages the query's lifecycle.
  • Metastore: the catalogue. A relational DB (MySQL/PostgreSQL) holding table schemas, column types, partition info and HDFS file locations.
  • Execution Engine: MapReduce, Tez or Spark (SET hive.execution.engine=spark). HDFS holds the data: tables are directories, partitions are sub-directories.

Compilation steps (P2 slide 11):

  1. Parse: HiveQL text into an abstract syntax tree (AST).
  2. Semantic analysis: look up tables and columns in the Metastore, check types (e.g. user_id is BIGINT, dt is a partition column).
  3. Logical plan: Filter, Join, GroupBy, OrderBy operators.
  4. Optimise and build the physical plan: MR/Tez/Spark jobs, with partition pruning.
  5. Submit jobs to YARN in dependency order; results go to HDFS and back to the client.

D3.What is "schema-on-read"? What are its advantages and disadvantages compared to "schema-on-write" in a traditional RDBMS such as MySQL? Give one example where schema-on-read causes a data quality problem.

Definition. Schema-on-read means the table structure (columns and types) is applied when data is queried, not when it is loaded. Hive copies raw files to HDFS and only interprets them at SELECT time (P1 slide 13). Schema-on-write (MySQL) checks every row at INSERT time and rejects bad rows.

Advantages of schema-on-read (P1 slides 13-14):

  • Fast loading: a raw file copy to HDFS, no validation cost.
  • Flexible: load web logs before you know the final schema; no ETL needed at ingest.
  • Many schemas on the same data: define several Hive tables over the same files as needs change.
  • Open formats: ORC, Parquet, CSV, JSON, Avro.

Disadvantages:

  • Slower queries: data is parsed and checked on every query.
  • Bad data is silent: invalid values become NULL instead of raising an error.
  • Suited to OLAP (analysis), not OLTP like banking or e-commerce orders, where schema-on-write is better.

Data quality example (P1 slide 13). A bKash transaction file has abc in the amount column (declared DOUBLE). MySQL would reject the INSERT. Hive stores it, and the query returns NULL for that row. SUM(amount) then ignores it, so the revenue report is too low and nobody is warned. Fix: add downstream checks such as Great Expectations or dbt tests (P1 slide 14).

Step 1: pick partition columns. The reports filter on txn_date and country. Both have low cardinality (a few hundred or thousand days, a handful of countries), so they are safe partition keys (P1 slide 19). Never partition on user_id or txn_id: millions of directories would overload the NameNode.

Step 2: pick the bucket column. The join key is user_id, which has high cardinality. Bucket both tables on user_id with the same number of buckets so Hive can do a bucket map join (bucket i with bucket i, no full shuffle) (P1 slide 23). SORTED BY (user_id) also enables a sort-merge bucket join.

Step 3: size the buckets. Assumptions (state these in the exam): 3 years of data and 5 countries.

  • Partitions = 3 × 365 days × 5 countries = 1,095 × 5 = 5,475.
  • Data per partition = 5 TB / 5,475 ≈ 0.913 GB.
  • With 8 buckets: 0.913 GB / 8 ≈ 114 MB per file, close to one 128 MB HDFS block. Good.
  • With 32 buckets: about 28.5 MB per file: too many small files (5,475 × 32 = 175,200 files) for the NameNode.
  • Total files with 8 buckets: 5,475 × 8 = 43,800.
  • User table: 10 M rows × ~200 bytes ≈ 2 GB; 8 buckets ≈ 250 MB each.

So 8 buckets gives files near the block size on both sides, and the same count on both tables makes the bucket map join possible. If the data were bigger per day, raise the count (16, 32) keeping it equal or a multiple on both tables.

A2.Query Compilation to MapReduce: Write HiveQL to find the top 5 products by total revenue in 2023. Then trace how Hive compiles this query into MapReduce stages: what is emitted by the Map phase, what is the shuffle key, and what does the Reduce phase compute? How would switching the execution engine from MapReduce to Tez change the execution plan?

Step 1: HiveQL (same style as P1 slide 18):

SELECT   product_id,
         SUM(amount) AS total_revenue
FROM     transactions
WHERE    YEAR(txn_date) = 2023
GROUP BY product_id
ORDER BY total_revenue DESC
LIMIT    5;

Step 2: compilation (P1 slide 8, P2 slide 11). Parse to AST; semantic analysis checks transactions, product_id, amount, txn_date in the Metastore; logical plan = Filter, GroupBy, OrderBy, Limit; physical plan = two MR jobs.

Job 1: aggregate.

  • Map: read each row (or only the 2023 partitions if the table is partitioned by date), drop rows where YEAR(txn_date) is not 2023, emit (product_id, amount). Hive does map-side aggregation (a combiner): each mapper emits one partial sum per product (P2 slide 10).
  • Shuffle key: product_id. All partial sums for one product go to the same reducer.
  • Reduce: add the partial sums: (product_id, SUM(amount)). Output is written to a temporary HDFS file.

Job 2: sort and limit.

  • Map: read Job 1 output, emit (total_revenue, product_id); each mapper can keep only its own top 5 (limit push-down).
  • Shuffle key: total_revenue in descending order, all to one reducer because ORDER BY needs a global order.
  • Reduce: output the first 5 rows.

Tiny example. 2023 rows: (P1,100), (P2,50), (P1,30), (P3,80), (P2,20), (P4,10). Job 1 gives P1=130, P2=70, P3=80, P4=10. Job 2 sorts: P1 130, P3 80, P2 70, P4 10 (all 4 shown since fewer than 5).

Step 3: MapReduce vs Tez. With SET hive.execution.engine=tez the two jobs become one DAG: Map 1 (scan, filter, partial sum) to Reducer 2 (final sum) to Reducer 3 (sort, limit 5). Differences:

  • No HDFS write between Job 1 and Job 2: data passes directly between stages.
  • One job submission instead of two, and containers can be reused, so less start-up cost.
  • Same HiveQL, same result; only the plan and speed change (Tez is "DAG of tasks, faster", P1 slide 8).

1.Spotify's co-occurrence query runs GROUP BY song_a, song_b over 2 billion playlist rows. Estimate the output size if there are 30M songs. Propose a partitioning + bucketing scheme for the playlist_songs Hive table that would reduce the shuffle size for this query. [CLO4 – Apply]

What the query does. For every playlist, every pair of songs in it is one row; GROUP BY counts how many playlists contain each pair; HAVING COUNT(*) > 5 keeps frequent pairs (P2 slide 16).

Estimate 1: upper bound from the song count. Possible distinct pairs = 30M × (30M − 1) / 2 ≈ 4.5 × 10^14. At 16 bytes per output row (two 4-byte song ids + 8-byte count) that is about 7.2 PB. This can never happen in practice, because pairs only come from real playlists.

Estimate 2: from the data. Assume the 2 billion rows are (playlist, song) rows and a playlist has about 20 songs on average.

  • Playlists = 2 × 10^9 / 20 = 10^8 (100 million).
  • Pairs per playlist = 20 × 19 / 2 = 190.
  • Pair rows before GROUP BY = 10^8 × 190 = 1.9 × 10^10 (19 billion).
  • Distinct pairs are at most 1.9 × 10^10, which is about 0.0042% of the 4.5 × 10^14 possible pairs; at 16 bytes that is at most about 304 GB.
  • After HAVING COUNT(*) > 5 most pairs vanish (the long tail), so the final output is far smaller, likely a few GB.

(If instead there are 2 billion playlists of 20 songs, the pair rows are 2 × 10^9 × 190 = 3.8 × 10^11, about 6.08 TB at 16 bytes. Show your assumption.)

Where the shuffle comes from. (1) The self-join on playlist_id to build pairs, which shuffles all 2B rows by playlist. (2) The GROUP BY on (song_a, song_b), which shuffles the pairs.

Proposed scheme:

Other side. Bucketing by playlist_id does not help the GROUP BY shuffle itself, because the group key is the song pair. An option is to precompute and store the weekly pair counts and add each new week incrementally (Luigi skips finished outputs, P2 slide 14).

2.The ALS collaborative filtering model is a matrix factorisation over a 75M-user × 30M-song matrix. At 4 bytes per float and rank k = 50, calculate the model size and explain whether it fits in a 5,000-node YARN cluster's aggregate RAM. [CLO4 – Analyse]

Idea. ALS (Alternating Least Squares) does not store the full user × song matrix. It learns two small matrices: a user matrix U (one row of k numbers per user) and a song matrix V (one row of k numbers per song). A user's predicted liking for a song = dot product of their two rows. Analogy: describe each person and each song by 50 "taste" scores instead of storing every person-song rating.

Calculation.

  • User factors: 75 × 10^6 × 50 × 4 B = 1.5 × 10^10 B = 15 GB.
  • Song factors: 30 × 10^6 × 50 × 4 B = 6 × 10^9 B = 6 GB.
  • Model size = (75M + 30M) × 50 × 4 B = 2.1 × 10^10 B = 21 GB (about 19.6 GiB).

Compare with the full matrix. 75M × 30M × 4 B = 9 × 10^15 B = 9 PB. Factorisation makes the model about 430,000 times smaller (9 × 10^15 / 2.1 × 10^10).

Does it fit? The slides do not give RAM per node. Assume 64 GB per node: aggregate RAM = 5,000 × 64 GB = 320 TB. 21 GB is about 0.0066% of that. Even split evenly it is about 4.2 MB per node. So yes, it fits easily; it would even fit in one large server's memory. The dense 9 PB matrix would not fit (about 28 times the 320 TB).

Caveats. Training needs more than the model: the rating/interaction data, shuffled factor blocks each iteration, and JVM overhead, often several times the model size. Spark ALS partitions U and V into blocks across executors so each node holds only a slice. Still well within the cluster.

3.Add a broadcast join hint for the songs dimension table and compare timings.

A broadcast join sends a full copy of the small table (songs: 200 rows) to every executor. Each executor joins its slice of the big table locally, so the big table is not shuffled. Hive calls this a map-side join. The hint is /*+ BROADCAST(s) */ right after SELECT.

Maths for Week 7

This chapter has a handful of simple calculations: how much map-side aggregation shrinks a shuffle, how much data partition pruning skips, which bucket a row lands in, how big partitions and bucket files are, how big an ALS model is, and speed-up ratios. Each is one or two steps. All numbers below were checked in Python.

Map-side aggregation (combiner) shuffle reduction

Reduction factor = N_rows / G
What each symbol means
  • N_rows: rows a mapper would emit without aggregation (one per input row).
  • G: number of distinct groups (GROUP BY values); with aggregation the mapper emits at most one row per group.

This is the ideal case of one mapper. With M mappers the shuffle is up to M × G rows, so the real factor is N_rows / (M × G).

Worked example

P2 slide 10: SELECT country, COUNT(*) FROM logs GROUP BY country, 50 million rows, 200 countries.

50,000,000 / 200 = 250,000× less shuffle data.

Practice

120 million rows grouped by 400 regions. Reduction = 120,000,000 / 400 = 300,000×.

Partition pruning: fraction of data read

Fraction read = P_read / P_total    (assuming equal-size partitions)
What each symbol means
  • P_read: partitions matching the WHERE filter.
  • P_total: all partitions = product of the number of values of each partition column.
Worked example

P2 slide 11: table partitioned by dt (365 days) and country (200). P_total = 365 × 200 = 73,000. Query reads dt=2024-10-01 for BD, IN, US: P_read = 3.

Fraction = 3 / 73,000 ≈ 0.0041%; skipped = 72,997 partitions.

P1 slide 20: 1 month of 36 = 1/36 ≈ 2.78% read.

Practice

24 months × 50 countries; query one month for 2 countries. P_total = 1,200, P_read = 2. Fraction = 2 / 1,200 ≈ 0.167%.

Bucket assignment

bucket = hash(column) mod N
What each symbol means
  • hash(column): hash of the bucketing column; for an INT/BIGINT key in Hive this is essentially the value itself.
  • N: number of buckets from INTO N BUCKETS.
  • mod: remainder after division.

Rows with the same key always land in the same bucket number, in every table bucketed the same way, which is what makes bucket i × bucket i joins work (P1 slides 23-24).

Worked example

P1 slide 24 uses 4 buckets on user_id. user_id = 98: 98 mod 4 = 2, so the row goes to bucket 2 in both sales and users.

Practice

32 buckets (P1 slide 24 DDL), user_id = 1,234,567. 1,234,567 mod 32 = 7.

Partition and bucket file sizing

File size ≈ S / (P × N);   files = P × N
What each symbol means
  • S: total table size.
  • P: number of partitions.
  • N: buckets per partition.

Aim for files near the HDFS block size (128 MB); far smaller means too many small files for the NameNode.

Worked example

A1: S = 5 TB, 3 years × 5 countries: P = 1,095 × 5 = 5,475. Per partition = 5 TB / 5,475 ≈ 0.913 GB. N = 8: 0.913 GB / 8 ≈ 114 MB per file, 43,800 files. N = 32 would give about 28.5 MB files.

Practice

S = 2 TB, partitioned by day for 2 years (P = 730), N = 16. File size = 2 TB / (730 × 16) = 2 TB / 11,680 ≈ 171 MB; 11,680 files.

ALS model size

Size = (U + I) × k × b
What each symbol means
  • U: number of users.
  • I: number of items (songs).
  • k: rank, the number of latent factors per user/item.
  • b: bytes per number (4 for a float).

Compare with the dense matrix U × I × b.

Worked example

P2 slide 18: (75M + 30M) × 50 × 4 = 2.1 × 10^10 B = 21 GB. Dense matrix: 75M × 30M × 4 = 9 × 10^15 B = 9 PB. With 5,000 nodes × 64 GB (assumed) = 320 TB RAM, 21 GB fits easily.

Practice

10M users, 1M songs, k = 100, 4 bytes. Size = 11M × 100 × 4 = 4.4 × 10^9 B = 4.4 GB.

Speed-up and time saved

Speed-up = T_old / T_new;   time saved % = (T_old − T_new) / T_old × 100
What each symbol means
  • T_old: time before the change.
  • T_new: time after.

Use the same units for both.

Worked example

P2 slide 18: partitioning play_events by week took the query from 8 h to 2 h. Speed-up = 8 / 2 = 4×; saved = (8 − 2) / 8 = 75%.

P1 slide 26: Hive+MR 5-15 min vs Presto 5-60 s. Same-end comparisons: 300 s / 60 s = 5× and 900 s / 5 s = 180×; the slide title rounds the typical gain to 10×.

Practice

A report drops from 2 hours to 30 minutes. Speed-up = 120 / 30 = 4×; saved = 90 / 120 = 75%.

Co-occurrence pair count

Pairs per playlist = L(L − 1) / 2;   total pairs = number of playlists × L(L − 1) / 2;   max distinct pairs = S(S − 1) / 2
What each symbol means
  • L: songs in a playlist.
  • S: songs in the catalogue.
Worked example

Discussion Q1: S = 30M gives at most 4.5 × 10^14 distinct pairs. With 2B (playlist, song) rows and L = 20: 10^8 playlists × 190 = 1.9 × 10^10 pairs (about 304 GB at 16 bytes each).

Practice

Chapter 4 · Week 8: Data Integration at Scale: Pipelines, Data Lakes & Modern Architectures

The chapter in plain words

Data integration means moving data from the systems where it is born (bank databases, web servers, phone apps) to the systems where it is analysed (Hadoop, dashboards, fraud checkers). The old way was point-to-point ETL (Extract, Transform, Load): one nightly job for every pair of systems. With N systems that grows like N², so 50 systems can need 2,450 separate jobs (P1 slide 5). Those jobs break on schema changes, cannot replay lost data, and are at least 24 hours late.

The modern answer is an event-driven pipeline: put one central message bus (usually Apache Kafka) in the middle. Sources publish events to the bus, consumers subscribe. Adding a new consumer needs zero changes to any source (P1 slide 5). Think of a post office: senders drop letters at one place instead of driving to every recipient.

Four tools to know (P1 slide 7): Sqoop = bulk copy between a relational database and HDFS (nightly batch). Flume = collects log files into HDFS using Source, Channel, Sink. Kafka = real-time event bus, any source to any consumer. NiFi = visual, drag-and-drop data routing. Spark Streaming then processes the streams.

Kafka stores data as an append-only log: new messages are only added at the end, never changed or removed on read. A topic is a named log (e.g. bkash-transactions). It is split into partitions for parallel work. Each message has an offset, its position number in the partition. Brokers are the Kafka servers; each partition is copied to R brokers (replication factor, default 3). Consumers track their own offset, so a late consumer can go back to offset 0 and replay everything still retained (P1 slides 14-16).

Kafka is fast because of four tricks: sequential disk writes (about 600 MB/s vs much less for random writes), zero-copy transfer with the sendfile() call, batching many messages per network trip, and partition parallelism (P1 slide 18). In the 2011 paper benchmark Kafka produced 50.5 MB/s vs 4.3 MB/s for ActiveMQ and 14.7 MB/s for RabbitMQ (P2 slide 11).

Lambda architecture (Nathan Marz, 2011) has three layers: a Batch layer (accurate, hours old), a Speed layer (approximate, seconds old) and a Serving layer that merges both for queries. Its big cost: the same business logic is written twice, once for batch and once for stream, and teams spend 30-40% of effort keeping them in sync (P1 slides 21-23).

Kappa architecture (Jay Kreps, 2014) drops the batch layer. All history sits in a long-retention log (Kafka, or Iceberg on S3). One stream job handles live data, and to reprocess history you start a new job at offset 0 and let it catch up (P1 slide 25). It only works if the stream engine is fast enough to replay the history.

A data lake stores raw data of any format with no schema needed up front (ingest, storage, processing, catalogue layers). Without governance it turns into a data swamp: files with no owner, no metadata, stale copies and mixed personal data. Prevent it with a catalogue at ingest, owners, access control, quality checks and table formats like Delta Lake or Iceberg (P1 slides 29-30). Part 2 covers the original Kafka paper (Kreps, Narkhede & Rao 2011) and Netflix's Kafka pipeline (100 billion events per day).

Definition. Lambda architecture (Nathan Marz, 2011) serves both accurate historical views and low-latency real-time views from the same data, with fault tolerance and the ability to recompute from scratch (P1 slide 21).

Three layers:

  1. Batch layer: keeps the complete, immutable master dataset on HDFS and recomputes batch views every hour or night. Accurate but 1-24 hours stale.
  2. Speed layer: stream processor (Kafka + Spark Streaming/Flink) covers only data since the last batch run. Approximate but under seconds.
  3. Serving layer: merges both. Query result = batch view (up to N hours ago) UNION real-time view (last N hours).

Main disadvantage vs Kappa: dual code paths. The same business logic is written twice (batch job and stream job) and must be kept in sync; 30-40% of engineering effort goes to this. It also needs two clusters and a runtime merge (P1 slide 23). Kappa has one stream code path.

D2.Describe how Apache Kafka achieves high throughput and fault tolerance. Explain the roles of topics, partitions, offsets, brokers, and replication factor in the Kafka data model.

Definition. Kafka is a distributed, partitioned, replicated commit log: every message is appended to an ordered, immutable log (P2 slide 5).

Data model (P1 slide 16):

  • Topic: a named, durable, append-only log for one kind of event (e.g. bkash-transactions).
  • Partition: a topic is split into P ordered partitions so work runs in parallel. Messages with the same key go to the same partition, so order per key is kept.
  • Offset: the integer position of a message inside a partition. Each consumer tracks its own offset; replay = move the offset back.
  • Broker: a Kafka server storing partitions on disk. A cluster has B brokers.
  • Replication factor (R): each partition has 1 leader and R − 1 follower copies on other brokers (default R = 3).

High throughput (P1 slide 18):

  1. Sequential, append-only disk writes: about 600 MB/s vs under 1 MB/s random on HDDs.
  2. Zero-copy: sendfile() sends data disk to network without a user-space copy (4 copies down to 2, P2 slide 9).
  3. Batching: many messages per network trip (batch.size, linger.ms).
  4. Partition parallelism: P partitions allow up to P consumers in a group at once; throughput grows with partition count.

Fault tolerance: replicas on other brokers take over if a leader's broker fails (leader election by ZooKeeper or KRaft); messages are retained on disk for days so a crashed consumer resumes from its saved offset.

Example: topic bkash-txns, 3 partitions, RF = 2: each partition has a leader on one broker and a replica on the other, so losing one broker loses no data (P1 slide 17).

D3.What is a data lake? How does it differ from a data warehouse in terms of schema enforcement, storage format, and typical use cases? What is a “data swamp” and how is it prevented?

Definition. A data lake is a central store for raw data at any scale and in any format (structured, semi-structured, unstructured) with no schema needed up front. Data goes in cheaply; transformation happens when needed (P1 slide 29).

Four layers: Ingestion (Sqoop, Flume, Kafka, NiFi), Storage (HDFS or S3/ADLS in raw, processed, curated zones), Processing (Spark, Hive, Presto), Catalogue/Governance (Atlas, Glue, Hive Metastore).

Data swamp: a lake with no governance. Symptoms (P1 slide 30): analysts cannot find datasets (no catalogue); nobody knows which files are current; many copies with different transforms and no versioning; personal data (PII) mixed with other data, breaking privacy rules.

L1.Kafka as the single source of truth: all events written to Kafka first; the speed and batch layers are both consumers of the same topic — eliminating the data inconsistency problem of classic Lambda (two separate ingestion paths)

Meaning. In classic Lambda, data can enter the batch and speed layers by different routes, so the two layers may see different data. Netflix writes every event to Kafka once; Flink (speed, under 1 minute) and the S3 sink + Spark/Iceberg (batch, about 1 day) both read the same topic (P2 slide 15).

L2.Retention enables reprocessing: 7-day retention lets Netflix replay any event window when a Flink job has a bug or a Spark job fails

Meaning. Kafka does not delete a message when it is read. With 7-day retention, a fixed job can reset its offset and recompute the last week (P2 slide 18).

For: bugs can be fixed after the fact without asking devices to resend. Against: only 7 days. A bug found on day 8 cannot be fixed from Kafka; the S3/Iceberg copy is needed. Longer retention costs storage (at 100 billion events/day, 7 days is about 700 billion events). Tiered storage (Kafka 3.6) moves old segments to S3 to cut this cost (P2 slide 12).

L3.Kappa simplification: Netflix increasingly moved batch jobs to Flink stream processing (processing historical S3 data as a bounded stream), reducing pipeline complexity

Meaning. A "bounded stream" is a stream with a start and an end, for example last month's files in S3. Flink can read it with the same code it uses for live data, so one code path covers both (Kappa idea, P1 slide 25).

For: less duplicate code, fewer systems. Against: Netflix still keeps Spark + Iceberg for ML training and billing (P2 slide 15), because some batch work is easier or cheaper in batch. The move is gradual, not all at once.

Meaning. A schema is the structure of a message (field names and types). If a producer renames a field, every consumer reading it may crash. Schema Registry stores the Avro/Protobuf schema per topic and lets a consumer read messages from any past producer version (P2 slide 12).

For: with 4,000+ topics and 150+ Flink jobs, manual coordination is impossible. Against: one more service to run, and teams must follow compatibility rules. This is the streaming version of the data-swamp lesson: without governance, data becomes unusable (P1 slide 30).

Meaning. Backpressure is when data arrives faster than consumers can process it. A 5× spike on the 1.3 million events/second peak would be 6.5 million/second. Kafka just appends the extra events to disk; Flink reads them a little later and catches up (P2 slides 17-18).

For: no data lost, no need to size consumers for the rare peak. Against: during the spike results are delayed by minutes (the 5-minute A/B result latency may slip); brokers need disk space for the burst. Analogy: a water tank between a burst pipe and a small tap.

from collections import Counter
from kafka import KafkaConsumer, TopicPartition
import json

TOPIC  = "play-events"
BROKER = "localhost:9092"

def make_consumer(group):
    return KafkaConsumer(
        bootstrap_servers=BROKER,
        group_id=group,
        auto_offset_reset="earliest",   # new group starts at offset 0
        enable_auto_commit=True,
        consumer_timeout_ms=5000,       # stop after 5 s with no new messages
        value_deserializer=lambda b: json.loads(b.decode()))

def count(consumer):
    total, all_events, plays = 0, Counter(), Counter()
    for msg in consumer:
        e = msg.value
        total += 1
        all_events[e["content_id"]] += 1
        if e["action"] == "play":
            plays[e["content_id"]] += 1
    return total, all_events, plays

# Goal 2: read everything, count per content_id
c = make_consumer("play-counter")
c.subscribe([TOPIC])
total1, ev1, plays1 = count(c)
print("read", total1, "events")
print("plays per content_id:", sorted(plays1.items()))
c.close()

# Goal 3: reset the SAME group to the beginning and re-consume
c = make_consumer("play-counter")
parts = [TopicPartition(TOPIC, p) for p in c.partitions_for_topic(TOPIC)]
c.assign(parts)
c.seek_to_beginning(*parts)
total2, ev2, plays2 = count(c)
print("re-read", total2, "events; same counts?", plays1 == plays2)
c.close()

# Goal 4: a NEW group id has no saved offset, so it starts at offset 0
c = make_consumer("play-counter-v2")
c.subscribe([TOPIC])
total3, ev3, plays3 = count(c)
print("new group read", total3, "events")
c.close()

Maths for Week 8

This chapter has no heavy formulas, but the slides use several numbers that can be turned into one-step calculations: point-to-point connection counts, disk speed ratios, zero-copy savings, message throughput, consumer-group sharing, replica counts, event rates and storage, and Sqoop parallel splits. Point-to-point ETL connections vs a message bus

Connections (point-to-point) = N × (N − 1)   |   Connections (bus) = N
What each symbol means
  • N = number of systems that must exchange data.
  • N × (N − 1) counts every ordered pair (A to B and B to A are separate ETL jobs). If you count each pair once, divide by 2.
  • With a bus each system connects only once, to the bus.
Worked example

Slide: 50 systems (P1 slide 5).

50 × (50 − 1) = 50 × 49 = 2,450 ETL jobs, matching the slide. Counted once per pair: 2,450 / 2 = 1,225.

With Kafka as a bus: 50 connections.

Practice

A company has 10 systems. Point-to-point: 10 × 9 = 90 jobs (45 if one per pair). With a bus: 10. For 20 systems: 20 × 19 = 380.

Sequential vs random disk speed

Advantage = sequential speed ÷ random speed
What each symbol means
  • Sequential speed = MB/s when writing one block after another (append-only).
  • Random speed = MB/s when jumping around the disk.
Worked example

P2 slide 11: sequential ≈ 600 MB/s, random ≈ 100 MB/s. 600 / 100 = 6× advantage.

P1 slide 18 uses a harsher random figure (< 1 MB/s): 600 / 1 = more than 600×. Quote whichever slide the question uses.

Practice

A disk writes 200 MB/s sequentially and 2 MB/s randomly. Advantage = 200 / 2 = 100×.

Zero-copy: data copies per transfer

Speedup ≈ copies (traditional) ÷ copies (zero-copy)
What each symbol means
  • Traditional path: disk → kernel buffer → user space → socket buffer → NIC = 4 copies.
  • sendfile() path: disk → kernel buffer → NIC = 2 copies.
  • NIC = network interface card.
Worked example

P2 slide 9: 4 / 2 = 2× throughput, with CPU near zero. Copies saved per message = 4 − 2 = 2.

Practice

A broker sends 1,000,000 messages. Copies saved = 1,000,000 × 2 = 2,000,000 memory copies avoided.

Throughput: MB/s to messages per second

Messages/sec = throughput (bytes/s) ÷ message size (bytes)   |   Speedup = Kafka ÷ other
What each symbol means
  • Throughput in MB/s, with 1 MB = 1,000,000 bytes (the slide's table uses this).
  • Message size = 100 bytes in the paper's benchmark.
Worked example

P2 slide 11, producer: 50.5 MB/s ÷ 100 B = 50,500,000 / 100 = 505,000 msgs/s (matches the table). ActiveMQ: 4.3 MB/s → 43,000. Kafka vs ActiveMQ = 50.5 / 4.3 ≈ 11.7×. Kafka vs RabbitMQ = 50.5 / 14.7 ≈ 3.4×.

Practice

Partitions and consumer groups

Active consumers = min(P, C)   |   Idle consumers = C − P (if C > P)   |   Partitions per consumer ≈ P ÷ C
What each symbol means
  • P = partitions in the topic.
  • C = consumers in one consumer group.
  • Rule: each partition goes to exactly one consumer in the group (P1 slide 16), so extra consumers sit idle.
Worked example

What each symbol means
  • P = partitions, R = replication factor (default 3, P1 slide 16).
  • One copy is the leader; the other R − 1 are followers.

Chapter 5 · Week 9: Data Visualization: Principles, Techniques & Big Data Tools

The chapter in plain words

Data visualization means turning numbers into pictures (charts, maps, graphs) so a person can see patterns quickly. In big data it is the first quality check: before you trust any average, you plot the data. Anscombe's Quartet (1973) is the classic proof: four datasets share the same mean of x (9.0), mean of y (7.5), variance of x (11.0), correlation (r = 0.816) and fitted line (y = 3 + 0.5x), yet one is a straight line, one a curve, one has an outlier and one is a vertical cluster (P1 slide 5).

At big data scale, averages hide even more. A 10-billion-row table can mix groups with opposite trends, skewed data (income, web traffic) makes the mean meaningless, and a daily average can hide a sudden change. Example from the slides: DGHS monthly disease averages look stable, but a line chart shows a cholera spike every June to August and a dengue peak every October (P1 slide 6).

Edward Tufte (1983) gave the design rules. Data-ink ratio = ink that shows data ÷ total ink in the chart; make it as high as possible. Anything that does not carry data is chartjunk: 3-D effects, heavy gridlines, gradient fills, redundant legends, decorative borders. Rule of thumb: if erasing an element loses no information, erase it (P1 slide 8). He also gave small multiples (the same small chart repeated for each district or year, on the same scale), sparklines (tiny word-sized trend lines next to a number) and the lie factor (how much a graphic exaggerates the real change) (P2 slides 6-7).

Ben Shneiderman (1996) gave the interaction rule, called the mantra: "Overview first, zoom and filter, then details on demand." Think of Google Maps: you see the whole country, zoom into a city, then click a shop for its details. He also listed seven data types (1-D, 2-D, 3-D, temporal, multi-dimensional, tree, network) and the tasks a tool must support: overview, zoom, filter, details-on-demand, relate, history, extract (P1 slides 11-12, P2 slide 9). He invented the treemap (1991) and dynamic queries (sliders that update a chart in under 100 ms) (P2 slide 10).

Choosing a chart depends on the question: line chart for change over time, horizontal bar chart for which category is largest, choropleth map for how a rate spreads across regions, histogram or box plot for the spread of one variable, scatterplot for whether X predicts Y, network graph for connections. The pie chart is the most abused chart: use it only for 4 or fewer categories when the question is "what fraction of the whole?" (P1 slides 14-15).

Big data adds three special problems (P1 slides 17-20). Overplotting: millions of dots pile into a solid blob; fix with transparency, hexbin counts, or density contours (KDE). Latency: a filter on a 100-billion-row table takes minutes; fix with a pre-computed data cube (summary tables) or approximate answers from samples (AQP). Streaming: charts must update live; the pipeline is Kafka → Spark Structured Streaming/Flink window aggregation → time-series database → Grafana/Kibana (polling every few seconds), or WebSocket push to a D3.js chart for sub-second updates.

Tools (P1 slides 22-23): Tableau and Power BI for business users; D3.js for custom interactive web charts (it binds data to SVG elements in the browser); Grafana for real-time operations monitoring; Apache Superset for open-source BI on Hadoop/Spark data lakes; Kibana for log search over Elasticsearch.

The Part 2 case study is the New York Times Graphics Desk, where Mike Bostock built D3.js. Their COVID-19 tracker (2020-2022) used Tufte's small multiples (a 50-state grid) and Shneiderman's mantra (national total, then state selector, then hover tooltip). The main lesson: the hardest work was cleaning messy data from 50 state health departments, not drawing the charts (P2 slides 13-15, 19).

D2.What is overplotting? Describe three techniques to address it when visualising millions of data points in a scatterplot. For each technique, explain what information it preserves that the original overplotted chart lost.

Definition. A scatterplot draws one dot per record. With millions of records the dots cover each other completely, so the chart becomes a solid blob that says nothing except "data exists here". This is overplotting (P1 slide 17). Analogy: a photo of a packed stadium from far away; you cannot tell where the crowd is thickest.

Three techniques (in increasing sophistication):

  1. Alpha transparency. Make each dot almost see-through, e.g. opacity α = 0.02. Where many dots stack, the area looks darker. Preserves: relative density (dark = many points, light = few). Limit: at very high densities everything turns fully dark again.
  2. Hexbin aggregation. Divide the plot into a hexagonal grid, count points in each hexagon, colour each hexagon by its count. 10 million points become about 10,000 cells, which is fast and interactive. Preserves: the actual count per area, so you can read exact density, which the blob hid.
  3. Kernel Density Estimation (KDE) / 2-D density contour. Estimate a smooth probability density over the point cloud and draw contour lines (like height lines on a map) at probability levels. Preserves: the shape of the distribution, its modes (peaks, clusters) and its tails.

Example. Plotting 10 million bKash transactions (amount vs time of day): the raw scatter is one blob; a hexbin shows the busiest amount/time cells; KDE contours show two peaks, for example a lunchtime and an evening cluster (P1 slides 17-18).

D3.What is a data cube? How does pre-aggregating a billion-row fact table into a data cube enable interactive visualization at sub-second latency? What is the trade-off of this approach?

Definition. A fact table holds one row per event (each sale, each transaction). A data cube is a set of pre-computed summary tables (aggregates such as SUM, COUNT) for every combination of dimensions, for example district × date × product × channel (P1 slide 19). Analogy: instead of counting every receipt each time the boss asks, you keep a ready-made tally sheet per shop per day.

How it gives sub-second latency:

  1. A scheduled Spark/Hive job (e.g. nightly) scans the huge fact table once and writes the cube.
  2. The cube has millions of rows, not billions.
  3. When the analyst moves a Tableau/Superset filter ("show Q1 2024 only"), the query reads the small cube, not the raw table.
  4. Reading millions of pre-summed rows takes under 1 second, while a Hive query over 100 billion raw rows takes minutes.

Trade-offs:

  • Staleness: the cube is only as fresh as the last job run, up to 24 hours old for a nightly job.
  • Fixed questions: you can only slice by dimensions you pre-computed; a new dimension needs a rebuild.
  • Storage and compute: materialising all combinations costs extra space and batch time.

Alternative: Approximate Query Processing (AQP, e.g. Apache DataSketches, BlinkDB) samples the table and returns a statistically sound estimate in milliseconds. It trades accuracy for speed: fine for dashboards, not for financial reconciliation (P1 slide 19).

Example: 100 billion rows reduced to a 5-million-row cube is 20,000 times fewer rows to read.

Why 1 minute: it turns 600,000 tweets into one point per topic, it smooths second-to-second noise, and it is still fast enough to see drift. Option: add a 15-minute sliding window (overlapping, recomputed each minute) as a smoother trend line; trade-off: smoother but reacts later.

(b) Charts.

  • Sentiment drift over time (temporal data): line chart of mean sentiment per minute, or a 100% stacked area chart of positive/neutral/negative share; small multiples, one panel per topic on the same scale (Tufte).
  • Topic clustering (high-dimensional data, e.g. tweet embeddings): t-SNE/UMAP scatterplot (P1 slide 14). Because there are millions of points, draw it as a hexbin or KDE contour to avoid overplotting (P1 slide 17), coloured by mean sentiment.
  • A sparkline next to each topic's live count gives trend at a glance.

(c) Velocity at the visualization layer.

  • Never send raw tweets to the browser; send only window aggregates. Over a 5-second refresh that is 50,000 raw tweets replaced by a handful of numbers.
  • Keep a fixed rolling buffer in the chart (e.g. the last 60 one-minute points) and drop the oldest point on each update.
  • Throttle redraws (e.g. at most once per second) and update the existing SVG elements with D3's data join instead of redrawing everything; use Canvas when many marks are needed.
  • Pre-aggregate the cluster view server-side into hex cells, so the browser draws thousands of cells, not millions of dots.

(d) Pipeline. X/Twitter API producer → Apache Kafka topic (durable event log) → Spark Structured Streaming / Flink (sentiment scoring + 1-min tumbling window) → time-series store (InfluxDB / Prometheus, or Elasticsearch) → either Grafana polling every 5 s for the ops view (or Kibana on Elasticsearch), or a WebSocket server pushing each new aggregate to a D3.js chart for sub-second custom views (P1 slide 20). This matches the Harvard CS171 lab that wires a Kafka consumer to a D3.js chart via WebSocket (P1 slide 24).

Tufte/Shneiderman check: no 3-D, no heavy gridlines; overview (all topics) → filter (topic dropdown, time range) → details (hover shows minute, count, score).

Lesson 1.Data quality is a visualisation problem: the NYT's biggest engineering effort was cleaning data, not drawing charts; retroactive state corrections forced D3 charts to support negative bars (days where cases were revised down)

Note: P2 slide 15 is titled "Lessons Learned & Discussion Questions" but only the five Key Lessons are printed on it. Each lesson is listed here as a discussion prompt.

What it means. A chart can only be as right as its data. The NYT pulled from Johns Hopkins CSSE, CDC and 50 state health departments, each with different column layouts (schemas), missing values and later corrections (P2 slide 14). Their pipeline was Python scrapers → pandas cleaning → GitHub CSV → D3 charts updated hourly.

For: most of the work was schema normalisation across 50 states, not SVG rendering (P2 slide 19). When a state revised cases down, the daily change was negative, so the chart design had to allow negative bars. Data problems showed up as visual design problems.

Against / nuance: cleaning is a data-engineering job, and good design can still not fix bad data. But hiding corrections would mislead readers, so the visual must show them honestly.

Exam point: in big data, visualization is the first quality check (P1 slide 6); bad data shows up first in charts.

Lesson 2.Accessibility is non-negotiable at 6M readers/day: every chart had a data table alternative for screen readers; colour scales were tested for colour-blindness (deuteranopia, protanopia)

What it means. With 6 million readers a day (P2 slide 13), even a small share who are blind or colour-blind is a large number of people. A screen reader cannot read an SVG chart, so a data table was offered. Deuteranopia and protanopia are forms of red-green colour-blindness, so red/green scales were avoided.

For: public-health information must reach everyone; the tracker was cited in CDC, WHO and UK SAGE briefs (P2 slide 14).

Against / cost: extra tables and testing take time on a daily deadline; colour-safe palettes limit design choices. The NYT judged the cost worth paying.

Lesson 3.Small multiples beat animation: the 50-state grid (Tufte small multiples) was more actionable than an animated map of spreading cases

What it means. Small multiples show every state at once on the same scale. Animation shows one frame at a time, so the viewer must remember the previous frame to compare (P2 slide 7).

For: readers could compare all states side by side and find their own state's trend without waiting.

Against: animation can grab attention and show spread across geography in a vivid way; a grid of 50 small charts can feel dense on a phone. For analysis, the grid wins; for a headline graphic, animation may still be used.

Lesson 4.Rolling averages are editorial decisions: choosing 7-day vs. 14-day average changes what story the chart tells; these are journalistic choices with ethical weight

What it means. A 7-day rolling average replaces each day with the mean of that day and the 6 before it. The NYT used it to remove day-of-week reporting artefacts, such as low weekend counts (P2 slide 14).

For 7-day: removes the weekly cycle and reacts within days to real change.

For 14-day: smoother, fewer false alarms, but hides a turning point for longer.

Why it is ethical: the same data can look calm or alarming depending on the window, and readers made health decisions from it. The window choice should be stated on the chart.

Lesson 5.GitHub as data infrastructure: publishing the raw CSV on GitHub enabled 1,000+ derivative dashboards worldwide within days

What it means. The NYT published its cleaned COVID data as CSV files on GitHub. Others built more than 1,000 dashboards from it within days (P2 slide 15).

For: openness lets researchers check the numbers and reuse the expensive cleaning work; GitHub gives version history, so corrections are traceable.

Against: GitHub is not built as a database; others may misuse or misread the data, and the publisher must keep the files consistent as corrections arrive.

Maths for Week 9

This chapter is mostly about design, but several slide facts are simple ratios: data-ink ratio, lie factor, how much hexbins and data cubes shrink the data, how alpha transparency saturates, how much a stream window compresses events, and how D3 scales turn values into pixels. All numbers below were recomputed in Python.

Data-ink ratio (Tufte)

Data-ink ratio = data-ink ÷ total ink
What each symbol means
  • data-ink: ink that encodes data (bars, points, lines).
  • total ink: all ink in the chart, including borders, gridlines, legends, 3-D shading.
  • Result is between 0 and 1; higher is better (P1 slide 8).
Worked example

A chart uses 1,000 units of ink, of which 300 draw the bars. Ratio = 300 ÷ 1,000 = 0.3. Remove 500 units of chartjunk (3-D, gridlines, legend): total = 500, data-ink still 300, ratio = 300 ÷ 500 = 0.6. The ratio doubled without changing the data.

Practice

A chart has 400 units of data-ink and 600 units of decoration. Ratio? Total = 1,000, ratio = 400 ÷ 1,000 = 0.4. After deleting all decoration, ratio = 400 ÷ 400 = 1.0 (the maximum).

Lie factor (Tufte)

Lie factor = size of effect shown in graphic ÷ size of effect in data
What each symbol means
  • effect in data: the real % change between values.
  • effect shown: the % change in the drawn size (e.g. bar height).
  • 1 = truthful; above 1 = overstates; below 1 = understates (P2 slide 7).
Worked example

Slide example: y-axis starts at 50 instead of 0. Data rises +10%, but the bar doubles in height (+100%). Lie factor = 100 ÷ 10 = 10.

Practice

Revenue goes from 100 to 110 (+10%). Because of a cut axis, the bars are drawn 40 px and 60 px tall: shown change = (60 − 40) ÷ 40 = +50%. Lie factor = 50 ÷ 10 = 5, so the graphic overstates the change five times.

Hexbin reduction (overplotting)

reduction factor = number of points ÷ number of hex cells
What each symbol means
  • points: records in the scatter.
  • hex cells: hexagons drawn after binning, each coloured by its count.
Worked example

Slide: 10,000,000 points → about 10,000 hex cells (P1 slide 17). Factor = 10,000,000 ÷ 10,000 = 1,000 times fewer shapes to draw.

Practice

2,000,000 GPS pings binned into 500 hexes. Factor = 2,000,000 ÷ 500 = 4,000; the browser draws 1 − 500 ÷ 2,000,000 = 99.975% fewer shapes.

Data cube size and row reduction (latency)

cube rows (finest level) ≈ d₁ × d₂ × … × dₖ; speed-up in rows read ≈ fact rows ÷ cube rows; number of group-by combinations = 2^k
What each symbol means
  • dᵢ: number of distinct values of dimension i (dates, districts, products, channels).
  • k: number of dimensions.
  • fact rows: rows in the raw table.
Worked example

Slide: 100 billion fact rows; cube of millions of rows (P1 slide 19). Take 5 million: 100,000,000,000 ÷ 5,000,000 = 20,000 times fewer rows; the cube is 1 − 5,000,000 ÷ 100,000,000,000 = 99.995% smaller.

Practice

Dimensions: 365 dates × 64 districts × 50 products × 4 channels. Finest cube = 365 × 64 × 50 × 4 = 4,672,000 rows (at most; only combinations that occur are stored). Rows-read reduction vs 100 billion = 100,000,000,000 ÷ 4,672,000 ≈ 21,404. With k = 4 dimensions there are 2⁴ = 16 possible group-by combinations (including the grand total).

Alpha transparency saturation (why it fails at high density)

opacity after n stacked points = 1 − (1 − α)^n
What each symbol means
  • α: opacity of one point (slide uses 0.02).
  • n: points stacked on the same pixel.
  • This standard compositing formula is added here to explain the slide's remark that alpha "still fails at very high densities" (P1 slide 17).
Worked example

α = 0.02: n = 10 → 1 − 0.98¹⁰ = 0.183; n = 50 → 0.636; n = 100 → 0.867; n = 200 → 0.982. Above roughly 200 points per pixel everything looks equally black, so dense regions can no longer be told apart.

Practice

How many stacked points reach 50% opacity at α = 0.02? Solve 0.98ⁿ = 0.5: n = ln 0.5 ÷ ln 0.98 ≈ 34.3, so about 35 points (1 − 0.98³⁵ = 0.507). For 99%: n = ln 0.01 ÷ ln 0.98 ≈ 227.9, about 228 points.

Streaming volume per window and refresh

events per window = event rate × window length; updates per day = 86,400 s ÷ refresh interval
What each symbol means
  • event rate: events per second.
  • window length: tumbling window size in seconds.
  • refresh interval: seconds between chart updates.
Worked example

A2: 10,000 tweets/s, 1-minute tumbling window → 10,000 × 60 = 600,000 tweets summarised into one point per topic. Per 5-s Grafana refresh: 10,000 × 5 = 50,000 tweets. Per day: 10,000 × 86,400 = 864,000,000 tweets.

Practice

A1(b): hospitalisation rate updated every 5 minutes. Updates per day = 24 × 60 ÷ 5 = 288. A chart of the last 24 hours therefore needs only 288 points.

D3 linear and band scales (Live Exercise)

y(v) = 260 − 240 × v ÷ max; bar height = 260 − y(v) = 240 × v ÷ max; band step = (480 − 50) ÷ (n − p + 2p), bandwidth = step × (1 − p)
What each symbol means
  • v: a topic's count; max: largest count.
  • 260 and 20: pixel range of the y scale (bottom, top), so 240 px of height.
  • n: number of bars (5); p: padding (0.3); 50..480: x pixel range (430 px).
Worked example

max = 60,000, v = 30,000: height = 240 × 30,000 ÷ 60,000 = 120 px; the bar top is at y = 260 − 120 = 140.

Practice

Band layout for 5 bars, padding 0.3: step = 430 ÷ (5 − 0.3 + 0.6) = 430 ÷ 5.3 ≈ 81.13 px; bandwidth = 81.13 × 0.7 ≈ 56.79 px; the first bar starts at 50 + 0.3 × 81.13 ≈ 74.34 px.

Chapter 6 · Week 10: Big Data in Real Applications: Social Media, Time Series & Health Data

The chapter in plain words

This week is about using the big data tools from Weeks 1 to 9 (HDFS, Kafka, Spark, Hive, Grafana) on three real domains: social media, time series and healthcare (P1 slide 5). The tools stay the same. What changes is the shape of the data and the risks.

Social media data is mainly a graph: people are nodes, and "follows" or "retweets" are edges. It is also timestamped, full of messy short text (slang, emojis, Bangla-English mixing) and heavy on images and video (P1 slide 7). Common analyses: community detection (finding tightly linked groups, using the Louvain algorithm), influence maximisation (picking the few users to seed so a message spreads furthest), sentiment analysis (is a post positive or negative, using VADER) and trend detection (spotting a phrase whose frequency suddenly jumps above its normal level).

Time series data is a list of values in time order, like weekly flu cases or daily sales. Order matters: shuffle the rows and the pattern is gone. Today's value is linked to yesterday's (autocorrelation). Most series have a trend (long-run drift up or down) and seasonality (repeating cycles, like every winter or every weekend) (P1 slide 14).

Three forecasting tools appear. ARIMA is the classic statistics model: it predicts from past values and past errors, but needs a stable (stationary) series and expert tuning. Facebook Prophet splits a series into parts you can read: y(t) = trend g(t) + seasonality s(t) + holidays h(t) + noise. It fits thousands of series automatically, and Spark can run one Prophet model per group in parallel with applyInPandas (P1 slides 16, 19). LSTM is a neural network for sequences. For anomaly detection the slides give STL (flag big leftover residuals) and Isolation Forest (odd points are easy to cut off from the rest) (P1 slide 18).

Healthcare big data comes in four forms: electronic health records (EHR), genomics (one genome is about 200 GB), wearables (per-second streams) and medical images (DICOM files of 200 MB to 2 GB) (P1 slide 21). ML on EHR data can predict ICU deaths, readmissions and sepsis earlier than doctors' rules of thumb (P1 slide 23). Because the data is about real patients, privacy law (HIPAA in the USA, GDPR in the EU, the upcoming PDPA in Bangladesh) shapes every design. Tools to protect it: de-identification, differential privacy (adding calibrated noise) and federated learning (training at each hospital without moving the raw data) (P1 slide 24).

AlphaFold (DeepMind) is the science example: trained on 170,000 known protein structures and searches across 250 million sequences, it predicts a protein's 3D shape from its amino-acid sequence. It released 200 million predicted structures in 2022 and won the 2024 Nobel Prize in Chemistry (P1 slides 25, 26, 32).

Part 2 adds two papers and a case study. Kwak et al. (2010) crawled 41.7 million Twitter users and 1.47 billion follow edges and found Twitter behaves like a news medium, not a friendship network: only 22.1% of follows are mutual and 85% of trending topics are headline news (P2 slides 5 to 7). Taylor & Letham (2018) is the Prophet paper (P2 slides 9, 10).

The case study is flu surveillance. Official CDC reports lag 1 to 2 weeks. Twitter posts, pharmacy sales, ER notes and searches can show an outbreak earlier (P1 slide 28). But Google Flu Trends over-predicted flu by 2× in 2012-2013 because search behaviour changed. The lesson: big data signals are a supplement to clinical reporting, never a replacement (P1 slide 29, P2 slide 14).

Louvain starts with every node in its own community, greedily merges nodes to raise modularity (edges inside communities minus what chance would give), collapses communities into super-nodes and repeats until modularity stops rising. D1.Describe three types of analysis commonly performed on social media data (e.g., community detection, sentiment analysis, influence maximisation). For each, state one specific ethical risk that arises when the analysis is deployed at scale.

Social media analytics treats a platform as a graph of users (nodes) and interactions (edges) with timestamped text attached (P1 slide 7). Three common analyses:

  1. Community detection. Finds groups of users more densely linked to each other than to the rest of the graph. The Louvain algorithm merges nodes to maximise modularity and scales to billion-node graphs in Spark GraphX (P1 slide 9). Use: interest groups, political factions, bot networks.
    Ethical risk: profiling. Labelling users by group can expose political views, religion or sexuality they never shared, and can be used to target or watch a whole faction.
  2. Sentiment analysis. Scores each post as positive, neutral or negative. VADER gives a compound score in [−1, +1]; above 0.05 is positive, below −0.05 negative (P1 slide 11).
    Ethical risk: suppressing dissent. A government can flag posts with negative sentiment about its policy and target their authors (P1 slide 12). Errors on Bangla slang or sarcasm can also wrongly flag people.
  3. Influence maximisation. Chooses k seed users so a message spreads to the most people. It is NP-hard; Kempe et al.'s greedy method reaches at least (1 − 1/e) ≈ 63% of the best spread (P1 slide 10).
    Ethical risk: manipulation. The same method that spreads a health message can spread misinformation or micro-target ads at vulnerable users (P1 slide 12).

Mitigation in one line: transparency and purpose limitation: say what the analysis is for and use it only for that (P1 slide 12).

Example: the #QurbaniEid spike (1,200× in 6 hours) was checked with VADER plus a Bangla lexicon: 92% positive, so it was real celebration, not a coordinated campaign (P1 slide 12).

D2.What is the difference between ARIMA and Facebook Prophet for time series forecasting? Under what conditions would you prefer Prophet over ARIMA? When might ARIMA still be the better choice?

ARIMA(p, d, q) (AutoRegressive Integrated Moving Average) predicts the next value from the past p values (AR), after differencing the series d times to make it stationary (I), plus the past q forecast errors (MA) (P1 slide 14). "Stationary" means the mean and variance do not change over time.

Prophet fits an additive model y(t) = g(t) + s(t) + h(t) + ε(t): piecewise trend with automatic changepoints, Fourier seasonality (yearly, weekly, daily at once), a user list of holidays, and noise (P1 slide 16).

Prefer Prophet when: the series has strong or multiple seasonality, holiday effects, trend shifts, missing data or outliers, and when you must forecast thousands of series automatically (P1 slides 15, 16; P2 slide 10). Example: 5,000 SKU demand forecasts, 8 hours down to about 12 minutes with applyInPandas (P1 slide 19).

ARIMA can still be better when: the series is short, stationary, has no strong seasonality and the dataset is small (P1 slide 14). It is a well-understood statistical model, and an expert can tune it closely for one important series.

Healthcare big data mixes EHR records, genomics, wearable streams and DICOM images (P1 slide 21), all about identifiable patients under laws like HIPAA, GDPR and Bangladesh's PDPA (P1 slide 24).

1.Kwak et al. found Twitter's average shortest path is 4.12 hops over 41.7M users. If a misinformation tweet is retweeted by a high-PageRank account, estimate how many users it reaches within 3 hops assuming an average out-degree of 45. What graph property makes this estimate an overestimate? [CLO4 — Apply]

Idea: treat spread like a tree. Each account passes the tweet to 45 new followers, and each of them to 45 more.

  • Hop 1: 45 users
  • Hop 2: 45² = 2,025 users
  • Hop 3: 45³ = 91,125 users

Total within 3 hops = 45 + 2,025 + 91,125 = 93,195 users (93,196 counting the high-PageRank account itself). That is about 0.22% of the 41.7M users.

Context: since the average shortest path is only 4.12 hops (P2 slide 6), one more hop (45⁴ = 4,100,625) would make the tree estimate reach about 4.19 million, so a tweet can reach a large part of the network in a few hops.

Why it is an overestimate: the tree model assumes every follower at each hop is a new, different person. Real social graphs have clustering and overlapping neighbourhoods (followers of the same account often follow each other and share followers; Twitter communities are dense inside, P1 slide 9). So many hop-2 and hop-3 users are the same people counted again. Other reasons it is high:

  • Not everyone who sees a tweet retweets it. Retweet cascades are wide and shallow (P2 slide 7), so most spread stops after hop 1.
  • Low reciprocity (22.1%, P2 slide 6) and the power-law degree distribution mean the average of 45 is pulled up by a few celebrities; a typical user has far fewer followers.

Other side: the high-PageRank first hop can be much bigger than 45 (celebrities have over 1 million followers), so hop 1 alone can exceed the estimate. The real number depends on who retweets.

2.A Prophet model for weekly hospital admissions has strong annual and weekly seasonality but misses a sudden COVID-19 wave onset. Identify which Prophet component should detect this changepoint and explain what prior hyperparameter controls the model's sensitivity to new changepoints. [CLO4 — Analyse]

Component: the trend g(t). In Prophet the trend is piecewise linear, g(t) = (k + a(t)ᵀδ)t + (m + a(t)ᵀγ), and δ holds slope changes at automatically detected changepoints (structural breaks) (P2 slide 10). A sudden wave is a break in the trend, not a repeating seasonal cycle, so seasonality s(t) cannot capture it and h(t) only covers known dates listed in advance.

Hyperparameter: changepoint_prior_scale. Prophet puts a sparse prior on δ: most changepoints get a slope change near 0 and only a few are large (P2 slide 10). The prior scale sets how big those changes may be.

  • Small (default 0.05): stiff trend, fewer real shifts allowed. Good against overfitting, but it can smooth over a sudden wave, which is what happened here.
  • Larger (e.g. 0.5, as in the Live Exercise): flexible trend that bends quickly at the wave onset, but may chase noise and gives wider forecast uncertainty.

Practical fixes: raise changepoint_prior_scale step by step and check on held-out weeks; let changepoints cover the latest data (changepoint_range near 1.0, since by default Prophet only places changepoints in the first 80% of the history); or add the known wave start as a manual changepoint or an extra regressor (e.g. case counts). Weekly seasonality on weekly data does nothing (all points fall on the same weekday), so it can be turned off.

  2. The data only has Sundays. 2021-05-13 (Thu) to 05-16 covers Sunday 2021-05-16; 2023-04-22 (Sat) to 04-25 covers Sunday 2023-04-23; but 2022-05-03 (Tue) to 05-06 contains no Sunday, so that Eid matches no data point at all.

Expected: without the holiday the model treats the spikes as noise and its band widens a little; with the holiday the components plot shows an Eid bar near +3 on those weeks and the trend and seasonality stay clean. This is the h(t) idea from P1 slide 16: known one-off events are modelled, not mistaken for trend.

5.Change changepoint_prior_scale from 0.05 to 0.5 and compare trend flexibility.

changepoint_prior_scale controls how big the slope changes δ at changepoints may be (the sparse prior, P2 slide 10).

  • 0.05 (default): stiff trend. The true trend here is flat at 5, so the expected trend line is nearly flat around 5.
  • 0.5: 10× looser prior. The trend can bend at many changepoints, so it wiggles and starts to absorb noise and bits of the seasonal wave. The future band also gets wider, because Prophet projects larger possible trend changes forward.

Lesson: higher values react faster to real breaks (like a sudden outbreak, Discussion Q2) but overfit noise on stable data. Pick the value by checking forecast error on held-out weeks.

Speedup of parallel batch forecasting

Speedup = T_sequential / T_parallel;   time per model = T_sequential / number of models;   models per executor = models / executors
What each symbol means
  • T_sequential: time to fit all models one after another on one machine
  • T_parallel: time on the Spark cluster
  • executor: a Spark worker process that runs tasks
Worked example

P1 slide 19: 5,000 SKUs, 8 hours sequential, about 12 minutes on 20 executors.

  1. 8 h = 480 min
  2. Speedup = 480 / 12 = 40× (matches the slide)
  3. Time per model = 8 × 3600 s / 5,000 = 5.76 s
  4. Models per executor = 5,000 / 20 = 250
  5. If each executor ran one model at a time, the best case would be 480 / 20 = 24 min. Getting 12 min means about 40 models fit at once, e.g. 2 cores per executor.
Practice

Q: The chain grows to 10,000 SKUs. Each model still takes 5.76 s and the cluster runs 40 models at once. Sequential time and parallel time?

A: Sequential = 10,000 × 5.76 = 57,600 s = 16 h. Parallel = 57,600 / 40 = 1,440 s = 24 min. Speedup stays 960 / 24 = 40×.

Prophet additive model

y(t) = g(t) + s(t) + h(t) + ε(t)
What each symbol means
  • y(t): the value at time t (e.g. admissions this week)
  • g(t): trend, long-run growth (piecewise linear or logistic)
  • s(t): seasonality, repeating cycles (Fourier series)
  • h(t): holiday or event effect on listed dates
  • ε(t): noise, what the model cannot explain
Worked example

An Eid week: trend g = 100 admissions, seasonal effect s = +15, Eid effect h = +30, noise ε = −2.

y = 100 + 15 + 30 − 2 = 143.

Practice

Q: A forecast says y = 120 for a non-holiday week, with g = 110 and noise 0. What is s?

A: h = 0 (no holiday), so s = 120 − 110 − 0 − 0 = +10.

Prophet piecewise linear trend with changepoints

g(t) = (k + a(t)ᵀδ) t + (m + a(t)ᵀγ)
What each symbol means
  • k: base growth rate (slope)
  • m: offset (starting level)
  • δ: slope changes, one per changepoint; sparse prior keeps most near 0
  • a(t): 0/1 vector, 1 for every changepoint already passed at time t
  • γ: offset corrections so the line stays joined at each changepoint (for one changepoint at s: γ = −sδ)
Worked example

k = 0.5, m = 1, one changepoint at t = 10 with δ = 0.3, so γ = −10 × 0.3 = −3.

  1. Before the changepoint, t = 10: g = 0.5 × 10 + 1 = 6
  2. After, slope = 0.5 + 0.3 = 0.8. At t = 10: 0.8 × 10 + 1 − 3 = 6 (line stays joined)
  3. At t = 20: 0.8 × 20 + 1 − 3 = 14
Practice

Q: Same model but δ = −0.5 (a slowdown). Slope after t = 10 and g(20)?

A: Slope = 0.5 − 0.5 = 0. γ = −10 × (−0.5) = +5. g(20) = 0 × 20 + 1 + 5 = 6: flat after the changepoint, still joined at 6.

Prophet Fourier seasonality

s(t) = Σ (n = 1 to N) [ a_n cos(2πnt / P) + b_n sin(2πnt / P) ]
What each symbol means
  • P: period in days: 365.25 for yearly, 7 for weekly (P2 slide 10)
  • N: number of terms; larger N gives a wigglier, less smooth pattern
  • a_n, b_n: weights the model learns; there are 2N of them
  • t: time in days
Worked example

Weekly seasonality (P = 7), N = 1, a₁ = 2, b₁ = 0.

  • t = 0: s = 2 cos(0) = 2
  • t = 3.5 (half a week): s = 2 cos(π) = −2
  • t = 1.75: s = 2 cos(π/2) = 0

Number of weights: N = 10 gives 2 × 10 = 20; N = 3 gives 6.

Practice

Q: Yearly seasonality (P = 365.25), N = 1, a₁ = 0, b₁ = 3. Value at t = 365.25/4 (a quarter year)?

A: s = 3 sin(2π × 0.25) = 3 sin(π/2) = 3.

Reach within h hops (tree estimate)

Reach ≤ d + d² + … + d^h
What each symbol means
  • d: average out-degree (followers each user passes the post to)
  • h: number of hops
  • ≤: an upper bound, because overlapping friends are counted more than once
Worked example

P2 slide 15: d = 45, h = 3.

45 + 45² + 45³ = 45 + 2,025 + 91,125 = 93,195 users, about 0.22% of 41.7M.

Practice

Q: d = 30, h = 3?

A: 30 + 900 + 27,000 = 27,930 users.

Power-law follower distribution

P(k) ∝ k^(−α),   so P(ck) / P(k) = c^(−α)
What each symbol means
  • k: number of followers
  • P(k): share of users with k followers
  • α: exponent, ≈ 2.276 for Twitter followers (P2 slide 6)
  • ∝: "proportional to"
Worked example

How common are users with twice as many followers? 2^(−2.276) = 0.206, about 1/5 as common.

Reciprocity

Reciprocity = mutual follow links / all follow links × 100%
What each symbol means
  • mutual link: A follows B and B follows A
Worked example

Twitter: 22.1% mutual (P2 slide 6), so 100 − 22.1 = 77.9% are one-way. Of 1.47 billion edges, 0.221 × 1.47B ≈ 324.87 million are mutual.

Modularity (what Louvain maximises)

Q = Σ_c [ L_c/m − (d_c / 2m)² ]
What each symbol means
  • c: each community
  • L_c: edges inside community c
  • d_c: sum of degrees of nodes in c
  • m: total edges in the graph
  • L_c/m is the actual fraction inside; (d_c/2m)² is the fraction expected by chance (the slide's definition, P1 slide 9). Higher Q = better split.
Worked example

Two triangles joined by one edge: 6 nodes, m = 7. Each triangle is a community: L_c = 3, degrees 2 + 2 + 3 = 7.

Per community: 3/7 − (7/14)² = 0.4286 − 0.25 = 0.1786. Q = 2 × 0.1786 = 0.357.

All nodes in one community: Q = 7/7 − (14/14)² = 0. So the two-triangle split is better, and Louvain would keep it.

Practice

Q: Two 4-node rings (each a 4-cycle) joined by one edge. Q for the two rings as communities?

A: m = 4 + 4 + 1 = 9. Each ring: L_c = 4, d_c = 2+2+2+3 = 9. Per ring: 4/9 − (9/18)² = 0.4444 − 0.25 = 0.1944. Q = 2 × 0.1944 = 0.389.

Greedy influence maximisation guarantee

Greedy spread ≥ (1 − 1/e) × optimal spread ≈ 0.632 × optimal
What each symbol means
  • e ≈ 2.718, the base of natural logarithms
  • optimal spread: the best possible reach with k seeds (NP-hard to find exactly)
Worked example

If the best k seeds would reach 10,000 users, Kempe et al.'s greedy method (P1 slide 10) is guaranteed at least 10,000 × 0.632 = 6,321 users.

Practice

Q: Optimal reach 50,000. Guaranteed greedy reach?

A: 50,000 × (1 − 1/e) = 31,606 users.

What each symbol means

Worked example

A phrase normally at 10/hour jumps to 10,000/hour: 10,000 / 10 = 1,000×, so it is trending (P1 slide 12). Same ratio for the bKash agent going from 10 to 10,000 transactions per hour (P1 slide 18).

STL residual anomaly rule

Flag a point if |residual| > k × IQR(residuals), IQR = Q3 − Q1
What each symbol means
  • residual: what is left after removing trend and seasonality (STL, P1 slide 18)
  • Q1, Q3: first and third quartiles (25th and 75th percentiles)
  • IQR: interquartile range, the spread of the middle half
  • k: a chosen multiplier (the slide leaves it open; 1.5 or 3 are common)
Worked example

Residuals: 0.2, −0.1, 0.3, −0.4, 0.1, 5.0, −0.2, 0.0. Sorted: −0.4, −0.2, −0.1, 0.0, 0.1, 0.2, 0.3, 5.0.

  1. Q1 = −0.125, Q3 = 0.225 (linear interpolation, Python statistics.quantiles(method="inclusive"))
  2. IQR = 0.225 − (−0.125) = 0.35
  3. k = 3: threshold = 3 × 0.35 = 1.05
  4. Only |5.0| > 1.05, so the 6th point is the anomaly.
Practice

Q: Same data, k = 1.5. Which points are flagged?

A: Threshold = 1.5 × 0.35 = 0.525. Largest normal value is |−0.4| = 0.4 < 0.525, so still only 5.0 is flagged.
