Pool · MCQQ5.1 Q1. Which component in YARN is responsible for global resource allocation across the entire cluster? (a) NodeManager (b) ApplicationMaster (c) ResourceManager (d) NameNode

(c) ResourceManager. One RM per cluster does global allocation; the ApplicationMaster is per-application, the NodeManager is per-node, and the NameNode is HDFS, not YARN.

Pool · MCQQ5.2 Q2. Which Hadoop file format stores data in columnar format and is best suited for analytical, read-heavy workloads? (a) Avro (b) Text/CSV (c) Parquet (d) JSON

(c) Parquet. It is columnar, so analytic queries read only the needed columns. Avro is row-based (write-heavy). ORC is also columnar and would get partial credit, but Parquet is the general standard across Spark, Presto and ML tools.

Pool · MCQQ5.3 Q3. What does "splittable" mean for a file format in Hadoop? (a) The file can be deleted in parts by HDFS (b) Multiple Mappers can process different parts of the file simultaneously (c) The file format supports splitting schema across multiple NameNodes (d) The file can be distributed across multiple data centres

(b) Multiple Mappers can process different parts simultaneously. A splittable format lets each HDFS block become its own input split, which gives parallel, data-local map tasks.

Pool · T/FQ5.5 1. Parquet is a row-oriented file format optimised for write-heavy workloads.

False. Parquet is columnar and built for read-heavy analytical queries. Avro is the row-oriented, write-friendly format.

Pool · T/FQ5.6 2. YARN allows multiple computation frameworks such as Spark and Tez to share resources on the same Hadoop cluster.

True. YARN separates resource management from processing, so MapReduce, Spark, Tez and Samza all run as YARN applications in containers on one shared cluster.

Pool · T/FQ5.7 3. Gzip-compressed files are natively splittable in Hadoop, allowing multiple Mappers to process them in parallel.

False. Gzip is a streaming codec with no internal block boundaries, so a file must be decompressed from the start. The whole file therefore goes to one Mapper.

True. ORC was built for Hive (stripes, lightweight indexes, ACID support), and with ZLIB it gets among the highest compression ratios of any Hadoop format.

Pool · DescriptiveQ5.9 D1. Explain YARN's three-component architecture: ResourceManager, NodeManager and ApplicationMaster. Draw a diagram showing how they interact when a Spark job is submitted to the cluster.
  • ResourceManager (RM): one per cluster. Its Scheduler hands out containers across the cluster; its ApplicationsManager accepts jobs and launches each job's AM.
  • NodeManager (NM): one per node. It launches and monitors containers (vCPU + RAM) and sends heartbeats with node health and resources to the RM.
  • ApplicationMaster (AM): one per application. It negotiates containers from the RM, tells NMs to start them, and tracks its own tasks.

Spark job flow (diagram as arrows):

Client --spark-submit--> RM (ApplicationsManager)
RM --launch AM container--> NM1  [AM + Spark Driver (cluster mode)]
AM --register + request N executor containers--> RM Scheduler
RM --container grants (node, <mem,vcores>)--> AM
AM --start executor--> NM2, NM3 ... [Executor containers]
Executors <--tasks/results--> Driver ;  NMs --heartbeat--> RM
Pool · DescriptiveQ5.10 D2. What is columnar storage? Why does it improve performance for analytics queries that select only a subset of columns? Use a concrete example with numbers to illustrate the I/O reduction.

Columnar storage keeps all values of one column next to each other (Parquet column chunks, ORC stripes) instead of storing whole rows together. An analytics query then reads only the columns it references (column pruning). Similar values sit together, so they also compress better (dictionary, RLE), and min/max statistics let the reader skip whole blocks.

Example (equal column widths assumed): a 1 TB table with 100 columns, and a query that uses 5 of them.

  1. Row format (CSV): reads all 1 TB.
  2. Columnar: 1 TB × 5/100 = 50 GB.
  3. Reduction = 1 − 0.05 = 95% (20× less I/O), before compression gains are counted.

Meaning: the query cost scales with the columns used, not with the width of the table.

Pool · DescriptiveQ5.11 D3. Compare Avro and Parquet. Explain what schema evolution means and why Avro handles it better. In which scenarios would you use each?
  • Avro: row-based, binary, the schema is stored in the file header as JSON. Fast to write and append, splittable. Good for ingestion, Kafka messages and RPC.
  • Parquet: columnar, with column chunks, row groups and footer statistics. Good for read-heavy analytics with column pruning and predicate pushdown.
  • Schema evolution means the schema changes over time (fields are added, removed or renamed) while old data stays readable. Avro resolves the writer schema against the reader schema at read time: a new field gets its default value, a removed field is ignored, and an alias handles a rename. So old and new records can be read together without rewriting any files. Parquet only supports adding columns safely and has weaker resolution rules.
  • Use Avro for landing and streaming data whose schema changes often (for example, LinkedIn's event pipeline). Use Parquet for the curated analytics or warehouse layer that Spark, Hive and Presto query.
Pool · Plan · AnalyticalQ5.12 A1. Data Lake Performance Migration: a Dhaka telecom stores 10 TB of daily call-detail records on HDFS as gzip-compressed CSV. A Hive query selecting 4 of 80 columns takes 6 hours. (a) Identify two specific reasons this configuration is slow. (b) Propose a migration strategy: new format, compression codec and partitioning scheme. (c) Estimate the expected I/O reduction (show calculation). (d) Which YARN scheduler would you use and why, given that multiple teams share the cluster? [Plan seed version: 10 TB of web click data stored as gzip CSV; propose a migration strategy (format, partitioning, codec).]

(a) 1. Gzip is not splittable, so each large file goes to one Mapper and the job has little parallelism and few data-local reads. 2. CSV is row-oriented, so selecting 4 columns still reads and parses all 80. A third reason: there is no partitioning, so every query does a full scan.

(b) Convert to Parquet (or ORC for a Hive-only stack) with Snappy compression, which is fast and splittable at the row-group level. Partition by date (dt=YYYY-MM-DD, optionally plus region), keep files of about 128 MB to 1 GB, and sort by a commonly filtered column so predicate pushdown can skip row groups. Migrate with a one-off INSERT OVERWRITE ... SELECT CTAS job. The web-click seed version gets the same answer, partitioned by event date (and hour).

(c) I/O read = table size × (columns read / total columns), with equal column widths (assumed).

  1. Column pruning: 10 TB × 4/80 = 0.5 TB.
  2. Reduction = 1 − 4/80 = 95% (20×).
  3. Query time scales roughly with I/O (assumed): 6 h / 20 = 0.3 h ≈ 18 min. Date-partition pruning and predicate pushdown reduce it further.

Meaning: the same query reads about 1/20 of the data and finishes in minutes instead of hours.

(d) Capacity Scheduler: each team gets its own queue with a guaranteed minimum share and an elastic maximum, so ad-hoc users cannot starve production ETL. Preemption returns borrowed capacity when the owning queue needs it. The Fair Scheduler (DRF) is a reasonable alternative when equal sharing between teams matters more than guarantees.

Pool · AnalyticalQ5.13 A2. YARN Failure Trace: a NodeManager (NM2) hosting 5 running containers for a MapReduce job fails mid-execution. Trace the complete failure recovery sequence: which components detect the failure, in what order, what state changes occur in the ResourceManager, and how the 5 containers' tasks are restarted.
  1. NM2 stops sending heartbeats to the RM.
  2. The RM's NMLivenessMonitor waits for the expiry interval (default 10 min, yarn.nm.liveness-monitor.expiry-interval-ms) and then marks NM2 LOST. The node is removed from the scheduler and its capacity is taken out of the cluster totals.
  3. The RM marks the 5 containers as completed/failed (lost) and reports them to the MapReduce ApplicationMaster in the next allocate() heartbeat response. The AM may already suspect the failure from missing task heartbeats.
  4. The AM marks the 5 task attempts FAILED/KILLED. This is not counted against the task's retry limit, because the node failed, not the task. The AM then asks the RM for 5 new containers with locality preferences (nodes holding replicas of the input blocks).
  5. The RM grants containers on healthy nodes. The AM starts them through those NMs, and the tasks restart from the beginning.
  6. Completed map tasks whose output lived on NM2's local disk are also re-run if reducers have not fetched that output yet.

If the AM itself had been on NM2, the RM would restart the AM attempt (up to yarn.resourcemanager.am.max-attempts).

v1 deck · DiscussionQ5.15 LinkedIn's Capacity Scheduler allocates 40% of 5,000 nodes to the production queue. If a Spark job in the spark queue needs 2,000 containers but only 1,250 are available, describe the outcomes under (a) Capacity, (b) Fair and (c) FIFO schedulers.

(a) Capacity: the job immediately gets its guaranteed 1,250 containers. The other 750 can come from elastic borrowing of idle capacity in other queues, up to the spark queue's maximum-capacity. If other queues are busy, those 750 stay pending. Borrowed containers may later be preempted when their owning queue needs them back.

(b) Fair: the job is given its fair share, recomputed as jobs come and go (DRF on CPU and RAM). It can use idle resources beyond that share, and if it is below its share it can preempt jobs that are over theirs. So it ramps up toward 2,000 over time instead of waiting.

(c) FIFO: there are no queues or guarantees. The job receives whatever is free in arrival order (1,250 now) and waits for the remaining 750 as earlier jobs release containers. A large job ahead of it causes head-of-line blocking, and a job behind it is starved.

v1 deck · DiscussionQ5.16 LinkedIn's PYMK Spark job processes a 300-million-node social graph using 600 executors, each with 8 GB RAM. Calculate the total memory requested as YARN containers and identify the dominant resource if each node has 64 GB RAM and 16 vCPUs.

Total RAM = executors × RAM per executor; dominant resource = max(RAM share, CPU share)

  1. Total memory = 600 × 8 GB = 4,800 GB (≈4.7 TB) of container memory (plus Spark memory overhead).
  2. Each executor uses 4 vCPU (assumed, the case-study Spark executor spec {8 GB, 4 vCPU}).
  3. Per node: RAM share = 8/64 = 12.5%, CPU share = 4/16 = 25%.

v1 deck · DiscussionQ5.17 Compare YARN's two-level scheduling (RM allocates containers; AM places tasks) with Kubernetes's one-level scheduling (kube-scheduler places pods directly). Under what workloads does two-level scheduling outperform one-level?
  • Two-level (YARN): the RM only decides how much each application gets, as containers. Each framework's AM decides which task runs in which container using its own logic (data locality, stage DAG, speculative execution). The central scheduler stays light and each framework can schedule its own way.
  • One-level (Kubernetes): one central scheduler places every pod using generic filters and scores. It is simpler and uniform, but it does not understand a framework's tasks.
  • Two-level wins for many short, data-local tasks, as in MapReduce or Spark batch jobs with thousands of tasks per second. The AM reuses a container for many tasks without a central decision each time, and applies HDFS locality and stage-aware placement. It also wins for multi-framework clusters with framework-specific needs (iterative ML, streaming, gang scheduling).
  • One-level is better for long-running services and microservices, where placement happens rarely and has to be uniform.
v1 deck · AnalyticalQ5.18 Harvard CS265 exam question: Prove that for a query selecting k columns from a c-column row-store table of n rows, the I/O complexity is Θ(n·c), but Θ(n·k) for a column store.

Assume fixed-width cells and that I/O is counted in cells, or pages of B cells (assumed).

  1. Row store: each row's c cells are stored together on a page, so one page holds B/c rows. Any query touching all n rows must read every page, even to get only k columns: n·c/B pages. The k needed cells cannot be read without reading their neighbours on the same page. The cost is at least n·c/B and at most n·c/B, so it is Θ(n·c), independent of k.
  2. Column store: each column is stored as its own contiguous file of n cells, which is n/B pages. The query opens only the k needed columns: k·n/B pages, and no other column is touched. That is both an upper and a lower bound (all n values of each selected column are needed), so it is Θ(n·k).

Meaning: the I/O ratio is c/k. For example, k = 4 and c = 80 gives 20× less I/O, which is the column-pruning gain behind Parquet and ORC.

Book ch05 · ShortQ5.19 What is the YARN ResourceManager's Scheduler component? What information does the Scheduler use to make allocation decisions, and what information does it deliberately not know?

The Scheduler is the RM component that divides cluster resources into containers among applications according to a policy (FIFO, Capacity, Fair). It decides using resource requests (memory, vCores, number of containers, priority, locality: node, rack or any), queue capacities and limits, and the free resources each NodeManager reports in its heartbeat. It deliberately does not know about application logic: tasks, their progress, or job semantics. It does not monitor or restart tasks either; the ApplicationMaster does that. This is what makes it a pure scheduler.

Book ch05 · ShortQ5.20 Explain the role of the ApplicationMaster (AM) in YARN. Why does one AM per job, rather than a centralised AM for all jobs, improve the scalability of the ResourceManager?

The AM is a per-application process running in its own container. It negotiates containers from the RM, asks NodeManagers to launch them, assigns tasks, monitors progress and handles task failure and retry. With one AM per job, all job-level bookkeeping is spread across the cluster, so the RM only tracks resources and container leases. In Hadoop 1 the single JobTracker had to track every task of every job, which capped clusters at about 4,000 nodes. Separating the work lets YARN scale to 10,000+ nodes and lets each framework run its own AM.

Book ch05 · ShortQ5.21 What is a YARN Container? Write the resource specification for a container that would host a Spark executor requiring 8 CPU cores and 24 GB of RAM on node dn-07.cluster.internal.

A Container is a lease on a bundle of resources (memory + vCores) on one specific node. The NodeManager grants and enforces it (cgroups), and a process such as an executor runs inside it.

ResourceRequest {
  priority: 1,
  resourceName: "dn-07.cluster.internal",
  capability: <memory: 24576 MB, vCores: 8>,
  numContainers: 1,
  relaxLocality: false
}

24 GB = 24 × 1024 = 24,576 MB. In practice Spark adds memoryOverhead, max(384 MB, 10%), on top of this.

Book ch05 · ShortQ5.22 Explain the difference between YARN's Capacity Scheduler and Fair Scheduler. Give a production scenario where the Capacity Scheduler is the better choice, and a scenario where the Fair Scheduler is better.

The Capacity Scheduler has hierarchical queues, each with a guaranteed % of the cluster and an elastic maximum. It is FIFO or priority inside a queue and can preempt. The Fair Scheduler moves resources so that all running apps or pools get an equal (weighted) share over time, using DRF across CPU and RAM, with preemption toward fair share.

Capacity is better for a multi-tenant enterprise cluster where the finance ETL queue must have a guaranteed 40% to meet a nightly SLA, whatever analysts submit. Fair is better for a shared research or data-science cluster with many small ad-hoc jobs, so short queries finish quickly instead of waiting behind a long job.

Book ch05 · ShortQ5.23 What is Dominant Resource Fairness (DRF)? Give an example where allocating equal CPU across two jobs would result in an unfair outcome, and explain how DRF resolves it.

DRF extends max-min fairness to several resources. A job's dominant share is its largest share of any one resource, and DRF equalises dominant shares.

Example: a cluster of 9 CPU and 18 GB. Job A's tasks need <1 CPU, 4 GB> (RAM-heavy); job B's need <3 CPU, 1 GB> (CPU-heavy). Splitting CPU equally (4.5 each) lets A run 4 tasks (4 CPU, 16 GB = 89% of RAM) while B runs only 1 task (3 CPU = 33%). A dominates.

DRF gives A 3 tasks (3 CPU, 12 GB, dominant RAM = 12/18 = 2/3) and B 2 tasks (6 CPU, 2 GB, dominant CPU = 6/9 = 2/3). The dominant shares are equal, so neither job would prefer the other's allocation.

Book ch05 · ShortQ5.24 A YARN NodeManager stops sending heartbeats to the ResourceManager. Trace the sequence of events: which component detects the failure, what happens to the containers on that NodeManager, and which component decides what to do next?

The RM's NMLivenessMonitor detects it: after the expiry interval with no heartbeat (default 10 min) the node is marked LOST and removed from the scheduler. Every container on that node is treated as failed/lost, and the RM reports their completion status to each affected ApplicationMaster in its next allocate response. The AM decides what to do next: it requests replacement containers and re-runs the tasks (for MapReduce, completed map outputs on that node are re-run too). If an AM itself was on the node, the RM restarts that AM attempt.

Book ch05 · ShortQ5.25 What is the difference between the write schema and the read schema in Apache Avro? Give a concrete example where they differ and explain how Avro handles the mismatch.

The writer schema is the one used when the data was serialised; it is stored in the file header. The reader schema is the one the consuming application expects now. Avro resolves the two at read time, matching fields by name.

Example: v1 writer schema {user_id, page}; v2 reader schema {user_id, page, country (default "unknown")}. Reading an old file, the missing country is filled with its default. A field in the writer schema but not the reader schema is skipped, renames resolve through aliases, and allowed type promotions (int to long) are applied. Old and new data can therefore be read together without rewriting.

Book ch05 · ShortQ5.26 Explain predicate pushdown in Apache Parquet. What information is stored in the Parquet file footer, and how does a query engine use it to avoid reading data?

Predicate pushdown means the WHERE filter is evaluated inside the reader using metadata, before the data is decoded. The footer holds the schema, the list of row groups, and for each column chunk its offset and size, codec/encodings and statistics: min, max, null count (plus optional page indexes and bloom filters). The engine reads the footer first. For WHERE amount > 1000 it skips every row group whose max ≤ 1000 and seeks only to the needed column chunks of the remaining ones, so whole row groups are never read from disk.

Book ch05 · ShortQ5.27 What is the splittability property for a Hadoop file format? A 10 GB file on a 100-node cluster is stored as Gzip-compressed CSV. How many Map tasks does MapReduce assign to this file, and why?

A format is splittable if a reader can start at an arbitrary block boundary and process that part on its own, so each HDFS block can become its own input split. For the 10 GB Gzip CSV, MapReduce assigns 1 Map task. Gzip has no sync points, so the stream must be decompressed from the start, and the input format marks the whole file as one split. The file still occupies 10 GB / 128 MB = 80 blocks (10 × 1024 / 128), but one mapper reads all of them, mostly remotely, while the other 99 nodes sit idle. Splittable alternatives are bzip2, LZO with an index, or Snappy inside Parquet/ORC/Avro containers.

Book ch05 · ShortQ5.28 Compare Parquet and ORC on three dimensions: primary processing engine, default compression codec, and ACID transaction support.
  • Primary engine: Parquet targets Spark (also Impala, Presto, Arrow). ORC targets Hive (also Presto/Trino).
  • Default codec: Parquet uses Snappy (in Spark). ORC uses ZLIB (Hive default; Snappy or Zstd optional).
  • ACID: ORC supports Hive ACID transactional tables (INSERT, UPDATE, DELETE with delta files). Plain Parquet has no ACID; that needs a table layer such as Delta Lake, Iceberg or Hudi.
Book ch05 · ShortQ5.29 A data engineer proposes storing a 500 TB analytics warehouse as raw JSON files (one JSON object per line) in HDFS. Identify three specific performance problems with this proposal and propose a better alternative.
  1. No column pruning: every query reads and parses whole objects, including repeated field names in every record, so all 500 TB are scanned.
  2. Expensive parsing and no types: text-to-type conversion is CPU-heavy, and the schema is inferred on every read, with no statistics for predicate pushdown.
  3. Poor compression and splittability trade-off: uncompressed JSON is huge, and gzip-compressed JSON is not splittable.

Better: Parquet (or ORC) + Snappy, partitioned by date, with files of about 128 MB to 1 GB. Use Avro or JSON only in the raw landing zone.

Book ch05 · ShortQ5.30 Explain column pruning (projection pushdown). For a 200-column Parquet table, a query references 6 columns. What fraction of the physical storage does the Parquet reader access?

Column pruning: the engine passes the list of referenced columns down to the reader, which seeks only to those column chunks (offsets from the footer) and never touches the others. Fraction accessed = 6/200 = 0.03 = 3% of the data (equal-width columns assumed), plus the small footer. That is 97% less I/O, about 33× less.

Book ch05 · ShortQ5.31 What does it mean for a columnar format to use dictionary encoding? For a column containing the values "US", "GB", "DE", "FR" repeated across 500 million rows, explain how dictionary encoding reduces the column chunk size.

Dictionary encoding stores each distinct value once in a dictionary page and replaces every cell with a small integer code (bit-packed, then often run-length encoded).

  1. Plain: 500M × (2 chars + 4-byte length prefix, assumed Parquet PLAIN) = 500M × 6 B = 3 GB.
  2. Dictionary: 4 values need 2 bits each. 500M × 2 bits / 8 = 125 MB, plus a dictionary of a few bytes.
  3. Ratio = 3 GB / 125 MB = 24×. Counting only the 2 chars, it is 1 GB vs 125 MB = 8×.

Meaning: low-cardinality columns shrink by an order of magnitude, and RLE shrinks runs of the same value further.

Book ch05 · ShortQ5.32 YARN's ResourceManager HA uses ZooKeeper for failover. What role does ZooKeeper play, and what happens to running applications during the 30 to 60 second RM failover window?

ZooKeeper provides leader election through the ActiveStandbyElector (an ephemeral lock znode). It fences the old active RM so only one RM is active, and it serves as the RMStateStore holding application and attempt state. When the active RM dies, the standby wins the election, loads state from ZooKeeper and becomes active. During the window running containers keep running: NodeManagers and AMs keep working and retry connecting until they reach the new RM. No new containers can be allocated and no new jobs can be submitted until then. With work-preserving recovery, the new RM rebuilds its container state from NM re-registration, so applications continue without restart.

Book ch05 · AnalyticalQ5.35 AP: Splittability and Parallelism Analysis. A genomics pipeline ingests 2 TB of sequencing data per day. Option A: one 2 TB Gzip FASTQ file. Option B: 16,000 Gzip FASTQ files of 128 MB each. Option C: Parquet with 128 MB row groups (≈16,000 row groups). (a) Map tasks for each option and whether data-local execution is achievable. footer = [{c: (min(rg[c]), max(rg[c])) for c in rg} for rg in rgs]

def scan(col, thr, cols):
    read = rows = 0
    for rg, st in zip(rgs, footer):
        if st[col][1] <= thr:
            continue                     # pushdown: skip row group
        read += 1

Book ch05 · ProgrammingQ5.41 PE: DRF Fairness Simulation (Python). Simulate Dominant Resource Fairness with CPU and RAM for three jobs on a 32-CPU / 128 GB cluster: MapReduce (2 CPU, 4 GB, max 8 tasks), Spark (4 CPU, 16 GB, max 6), Samza (1 CPU, 2 GB, max 12); grant one task at a time to the job with the lowest dominant share.
def drf(C, R, jobs):
    a = {j[0]: [0, 0, 0] for j in jobs}          # tasks, cpu, ram
    uc = ur = 0
    while True:
        ok = [j for j in jobs if a[j[0]][0] < j[3]
              and uc + j[1] <= C and ur + j[2] <= R]
        if not ok:
            break
        n, c, r, _ = min(ok, key=lambda j: max(a[j[0]][1]/C, a[j[0]][2]/R))
        a[n][0] += 1; a[n][1] += c; a[n][2] += r
        uc += c; ur += r
    return a

Pool · DescriptiveQ6.9 D1. Explain the concept of a Resilient Distributed Dataset (RDD). What does "resilient" mean in this context? How does Spark recover a lost RDD partition without replication?

An RDD is an immutable, partitioned collection of records spread across the executors of a cluster. It is built only by deterministic transformations on stable storage or on other RDDs, and it can be cached in memory. Resilient means it is fault-tolerant: when a partition is lost, Spark can rebuild it automatically. Each RDD keeps its lineage, the graph of parent RDDs and the functions applied to them. When an executor dies, the scheduler reruns that function chain only for the lost partitions, starting from the source data or the nearest cached or checkpointed parent. No replica copies are needed.

Pool · DescriptiveQ6.10 D2. Differentiate between Spark transformations and actions. Give two concrete examples of each. Why does Spark not execute transformations immediately?
  • Transformations build a new RDD or DataFrame from an existing one and are lazy: they only record a step in the DAG. Examples: map(), filter() (also reduceByKey, join).
  • Actions trigger execution and return a result to the driver or write output. Examples: count(), collect() (also take, saveAsTextFile).
  • Why lazy: when Spark sees the whole chain, it can pipeline narrow operations into one pass, split stages only at shuffles, push filters down, and skip work the action never needs. It also avoids materialising intermediate results that nothing uses.
Pool · DescriptiveQ6.11 D3. Describe Spark's lazy evaluation model. What is the advantage of deferring computation until an action is called? Use the example rdd.filter(x > 1000).first() to illustrate.

Under lazy evaluation, transformations are only recorded as a logical plan (DAG). When an action is called, the DAGScheduler builds stages and runs them. The advantage is that Spark optimises the whole pipeline: it fuses operations, does less I/O and stops early. In rdd.filter(x > 1000).first(), filter computes nothing on its own. first() then launches a job that scans the first partition, filters as it streams, and stops at the first match. Book ch06 · ShortQ6.21 What is lineage-based fault tolerance? Compare it with replication-based fault tolerance on two dimensions: memory overhead and recovery latency.

With lineage-based fault tolerance, Spark logs the coarse-grained transformations that produced each RDD and recomputes lost partitions from them, instead of storing copies of the data.

  • Memory overhead: lineage stores only a small DAG of operations, so it is near zero. Replication stores r full copies (3× memory or disk) and costs network bandwidth on every write.
  • Recovery latency: replication is fast (read the surviving copy). Lineage has to recompute, which is slower and grows with lineage length and wide dependencies, but it only touches the lost partitions and runs in parallel. Checkpointing limits the worst case.

In a narrow transformation, each parent partition feeds at most one child partition: map, filter (also flatMap, union). In a wide transformation, a child partition needs data from many parent partitions: groupByKey, reduceByKey (also join, distinct). A wide transformation needs a shuffle: all map-side tasks must finish and write shuffle files before any reduce task can start. That synchronisation point cannot be pipelined, so the DAGScheduler cuts a new stage there. Narrow chains run within one stage, partition by partition.

Book ch06 · ShortQ6.24 Why is reduceByKey almost always preferable to groupByKey for aggregation? Give a numerical example of network traffic for 1 billion records, 200 partitions, where 30% of records share the same key.

reduceByKey applies the function map-side (a combiner) before the shuffle, so only partial results cross the network. groupByKey ships every record and builds full value lists on the reducer.

  1. Hot key: 30% × 109 = 300M records, spread over 200 partitions.
  2. groupByKey: shuffles all 109 records. At 100 B each (assumed) that is 100 GB, and one reducer receives all 300M hot-key values (30 GB), which risks OOM.
  3. reduceByKey: the hot key becomes 200 partial sums (one per partition). The other 700M records are assumed to be mostly unique keys, so they do not combine. Total ≈ 700M + 200 records ≈ 70 GB, and the hot-key reducer gets 200 records instead of 300M.

Meaning: at least 30% less network traffic, and the skewed reducer goes from 300M values to 200. The saving is larger when other keys also repeat.

Book ch06 · ShortQ6.25 What is a YARN ApplicationMaster for a Spark job? Which component of Spark architecture runs inside the AM container, and what does it do?

For a Spark-on-YARN job the AM is Spark's per-application YARN process. It negotiates executor containers from the ResourceManager (including dynamic allocation) and asks NodeManagers to launch them. In cluster mode the Spark Driver (SparkContext) runs inside the AM container. It builds the DAG, splits it into stages and tasks (DAGScheduler, TaskScheduler), sends tasks to executors, tracks block locations and lineage, and collects results. In client mode the driver runs on the client machine, and the AM (ExecutorLauncher) only requests containers.

Book ch06 · ShortQ6.26 Explain the four phases of the Catalyst optimizer. Which phase chooses between a sort-merge join and a broadcast hash join, and what criterion determines the choice?
  1. Analysis: resolves table and column names and types against the catalog, turning an unresolved plan into a resolved logical plan.
  2. Logical optimisation: rule-based rewrites such as predicate pushdown, column pruning and constant folding.
  3. Physical planning: generates candidate physical plans and picks one using cost and size estimates.
  4. Code generation: Tungsten whole-stage codegen compiles the plan to JVM bytecode.

Physical planning picks the join: broadcast hash join if one side's estimated size is ≤ spark.sql.autoBroadcastJoinThreshold (default 10 MB) or a broadcast hint is given; otherwise sort-merge join. AQE can switch to a broadcast join at runtime from actual sizes.

Book ch06 · ShortQ6.27 What is the unified memory model in Spark? For an executor with 32 GB JVM heap, spark.memory.fraction = 0.6 and spark.memory.storageFraction = 0.5, calculate the available storage memory, execution memory and user memory.

In the unified memory model, execution (shuffles, joins, sorts) and storage (cache) share one pool, M = (heap − 300 MB reserved) × memory.fraction. Storage's protected share is M × storageFraction. Each side can borrow the other's free space, and execution can evict cached blocks down to the protected share.

  1. Usable = 32,768 − 300 = 32,468 MB.
  2. Unified M = 0.6 × 32,468 = 19,480.8 MB ≈ 19.02 GB.
  3. Storage = 0.5 × M ≈ 9.51 GB; execution ≈ 9.51 GB.
  4. User memory = 0.4 × 32,468 = 12,987 MB ≈ 12.68 GB.

Meaning: ignoring the 300 MB reserve, the round figures are 19.2 / 9.6 / 9.6 / 12.8 GB, and only about 60% of the heap is available to Spark.

Book ch06 · ShortQ6.28 What is Tungsten whole-stage code generation? How does it differ from the interpreted, row-at-a-time Volcano model used by traditional query engines?

Whole-stage codegen fuses all operators in a stage (scan, filter, project, aggregate) into one generated Java function with a tight loop. Values stay in CPU registers, and data uses Tungsten's off-heap binary rows. The Volcano model calls next() through a chain of operator objects once per row per operator, which means virtual function calls, object allocation and poor cache use. Codegen removes that per-row interpretation overhead and runs close to hand-written code, often several times faster on CPU-bound queries.

Book ch06 · ShortQ6.29 Explain the Spark MLlib abstraction of Transformer vs. Estimator. Give one concrete example of each and explain what fit(df) produces for an Estimator.

A Transformer has transform(df), which maps one DataFrame to another by appending columns. Example: VectorAssembler (or Tokenizer, or a trained model). An Estimator has fit(df), which learns parameters from data. Example: LogisticRegression (or StringIndexer, StandardScaler). fit(df) returns a Model, which is itself a Transformer; for example a LogisticRegressionModel whose transform() adds prediction and probability columns. A Pipeline chains them, and fitting a Pipeline gives a PipelineModel.

Book ch06 · ShortQ6.30 What is data skew in a Spark wide transformation? Describe the observable symptom in the Spark UI that indicates a skew problem.

Data skew means a few keys hold a disproportionate share of records, so after the shuffle a few partitions are far larger than the rest and their tasks run much longer, or spill or OOM. Symptom in the Spark UI (Stage page, task summary): max task duration and max shuffle read size/records are many times the median. Most tasks finish quickly while one or a few stragglers keep the stage running, often with large spill (memory/disk) or GC time on those tasks.

Book ch06 · ShortQ6.31 What does MEMORY_ONLY_SER mean as an RDD storage level? Under what circumstances should you choose it over MEMORY_ONLY?

MEMORY_ONLY_SER caches each partition as serialised bytes (one byte array per partition, ideally Kryo) in the JVM heap. Partitions that do not fit are recomputed, not spilled. Choose it over MEMORY_ONLY when the deserialised objects do not fit in memory (Java objects are often 2 to 5× larger), or when GC pressure from millions of small objects is high. It saves memory and GC time at the cost of extra CPU to deserialise on each access. (In PySpark, data is always stored serialised.)

Book ch06 · ShortQ6.32 Explain what a checkpoint does in Spark. When is checkpointing necessary, and what are its costs?

rdd.checkpoint() (after sc.setCheckpointDir) writes the RDD to reliable storage (HDFS) and truncates its lineage, so recovery restarts from the checkpoint. It is necessary for long lineages (iterative algorithms, GraphX) where recomputation or stack depth explodes, after expensive wide shuffles, and in stateful streaming (required for updateStateByKey and for recovering from driver failure). Costs: an extra job that writes the full data to HDFS (I/O, replication, storage space), plus a recompute unless the RDD is persisted first.

SMB join: each mapper merges bucket i of table A with bucket i of table B using a sorted merge.

Preconditions: both tables bucketed on the join key, same number of buckets (or a multiple), and sorted by the join key (SORTED BY); settings like hive.optimize.bucketmapjoin.sortedmerge=true.

Data cube: a multidimensional pre-aggregation of a fact table over all combinations (cuboids) of its dimensions; n dimensions give 2n cuboids.

Book ch10 · ShortQ10.19 Describe the two phases of the Louvain community detection algorithm. What is the modularity objective Q, and why does maximising it detect communities?

Phase 1 (local moving): each node is moved to the neighbouring community giving the largest modularity gain ΔQ, repeated until no gain. Phase 2 (aggregation): each community becomes a super-node (edge weights summed) and phase 1 repeats until Q stops rising.

Q = (1/2m) Σij [Aij − kikj/2m] δ(ci, cj): fraction of edges inside communities minus the fraction expected in a random graph with the same degrees. Maximising it finds groups that are more densely connected internally than chance.

STL (Seasonal-Trend decomposition using LOESS) splits a series into trend + seasonal + remainder; flag large remainders. Best for contextual/seasonal anomalies, values unusual for that time of day/week (e.g. normal traffic at 3 a.m.).

Isolation Forest isolates points with random splits; anomalies need fewer splits (short path length). Best for point/global anomalies in feature space (sudden spikes, multivariate outliers), without modelling seasonality.

Book ch10 · ShortQ10.26 What is the difference between safe harbour de-identification and differential privacy for healthcare data? Give one scenario where safe harbour is sufficient and one where differential privacy would also be needed.

Safe harbour (HIPAA): remove the 18 listed identifiers (names, IDs, dates except year, small geographic units, etc.) from records; rule-based, applied to the dataset. Differential privacy: a mathematical guarantee (ε) that adding calibrated noise (e.g. Laplace) makes outputs nearly unchanged whether or not any one person is in the data.

Safe harbour enough: an internal research team under a data-use agreement analysing de-identified readmission records. DP also needed: publishing aggregate statistics or an open query interface (e.g. rare-disease counts by small region), where linkage or repeated queries could re-identify patients.

Book ch10 · ShortQ10.27 What was the core argument of Obermeyer & Emanuel (2016)? List two clinical tasks where they argued ML outperforms physician heuristics, and the metric used.

Argument: big data and ML will transform medicine; models built on large EHR data predict better than clinicians' rules of thumb, so ML will reshape prognosis, displace work in radiology and anatomic pathology, and improve diagnostic accuracy.

Tasks: (1) prognosis / mortality prediction (e.g. death in end-of-life care, cancer outcomes); (2) image-based diagnosis in radiology/pathology. Metric: AUROC (area under ROC curve / C-statistic).

Book ch10 · ShortQ10.28 Explain why Google Flu Trends over-predicted flu incidence in 2012–2013. Name all three causes identified by Lazer et al. (2014) and say which is most fundamental.

GFT predicted more than double the CDC's ILI level. Lazer et al.: (1) Big data hubris: treating search data as a substitute for, not supplement to, traditional surveillance; over-fitting ~50 M terms to ~1,000 data points, picking terms that matched winter seasonality rather than flu. (2) Algorithm dynamics: Google changed search (autocomplete, suggested health terms), shifting query behaviour opaque to the model. (3) Lack of transparency / not recalibrating with CDC data (closed, unreplicable methods).

Most fundamental: big data hubris, i.e. correlation without causal validation on a non-stationary data-generating process.

Book ch10 · ShortQ10.29 What is federated learning? Why is it used in multi-hospital clinical ML, and what is the primary limitation of the federated averaging algorithm?

Federated learning trains a shared model by sending the model to the data: each hospital trains locally and only weights/gradients go to a central server, which averages them. Used because HIPAA/GDPR forbid pooling patient records. Main limitation of FedAvg: non-IID data across hospitals (different populations, coding) makes the averaged model converge slowly or perform poorly for some sites; also high communication cost and gradient leakage risk.

Book ch10 · AnalyticalQ10.30 Influence Maximisation Calculation. A Facebook group for a dengue alert campaign has 1 million users; power-law degree distribution, α = 2.3; budget k = 5 seed posts. (a) Under the independent cascade model with p_uv = 0.05, will seeding the 5 highest-follower users or the 5 highest-PageRank users spread further? Use Kwak et al. (b) Greedy (Kempe et al.) guarantees (1 − 1/e) ≈ 0.632 of optimum. If σ(S*) = 200,000, what is the worst-case greedy influence? Is this meaningful for a public health campaign? (c) σ(S) is estimated by 10,000 Monte Carlo cascades; with 1M nodes, k = 5, 100 candidates per greedy step, how many cascade simulations are needed? Tractable on one machine?

(a) PageRank seeds are likely better. Kwak et al. showed follower count, PageRank and retweet influence rank users differently: high-follower accounts often have inactive/bot followers and overlapping audiences, while PageRank rewards being followed by well-connected users, so cascades with p = 0.05 travel further. Top-follower hubs in a power-law graph also overlap, giving redundant reach. Best: choose seeds in different communities.

(b) σ(Sgreedy) ≥ (1 − 1/e)·σ(S*)

  1. 1 − 1/e = 0.6321
  2. 0.6321 × 200,000 = 126,424 users

Meaning: worst case reaches ~126 K of 1 M users. Useful as a floor (in practice greedy is usually close to optimal), but it is relative to σ(S*), which depends on assumed puv; if p is wrong, the guarantee says nothing about real reach.

(c) Simulations = k × candidates × MC runs

  1. 5 × 100 × 10,000 = 5,000,000 cascades
  2. At ~0.1 s per cascade on a 1 M-node graph (assumed): 5 × 106 × 0.1 = 500,000 s ≈ 139 h ≈ 5.8 days

Meaning: barely tractable on one machine; use CELF lazy evaluation (up to ~700× fewer evaluations), parallelise simulations on Spark, or sketch-based methods (RIS).
