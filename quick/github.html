Week 5: YARN, file formats, compression

v1 deck discussion question (cut from the current slides)G5.1 LinkedIn's Capacity Scheduler allocates 40% of 5,000 nodes to the production queue. If a Spark job in the spark queue needs 2,000 containers but only 1,250 are available, describe the outcomes under (a) Capacity, (b) Fair and (c) FIFO schedulers.

(a) Capacity: the job immediately gets its guaranteed 1,250 containers. The other 750 can come from elastic borrowing of idle capacity in other queues, up to the spark queue's maximum-capacity. If other queues are busy, those 750 stay pending. Borrowed containers may later be preempted when their owning queue needs them back.

(b) Fair: the job is given its fair share, recomputed as jobs come and go (DRF on CPU and RAM). It can use idle resources beyond that share, and if it is below its share it can preempt jobs that are over theirs. So it ramps up toward 2,000 over time instead of waiting.

(c) FIFO: there are no queues or guarantees. The job receives whatever is free in arrival order (1,250 now) and waits for the remaining 750 as earlier jobs release containers. A large job ahead of it causes head-of-line blocking, and a job behind it is starved.

v1 deck discussion question (cut from the current slides)G5.2 LinkedIn's PYMK Spark job processes a 300-million-node social graph using 600 executors, each with 8 GB RAM. Calculate the total memory requested as YARN containers and identify the dominant resource if each node has 64 GB RAM and 16 vCPUs.

Total RAM = executors × RAM per executor; dominant resource = max(RAM share, CPU share)

  1. Total memory = 600 × 8 GB = 4,800 GB (≈4.7 TB) of container memory (plus Spark memory overhead).
  2. Each executor uses 4 vCPU (assumed, the case-study Spark executor spec {8 GB, 4 vCPU}).
  3. Per node: RAM share = 8/64 = 12.5%, CPU share = 4/16 = 25%.
  4. Over the whole cluster: RAM 4,800 / 320,000 GB = 1.5%, CPU 2,400 / 80,000 vCPU = 3%.

Meaning: the dominant resource is vCPU (25% > 12.5% per node), so DRF charges this job by CPU. With 1 vCPU per executor the CPU share would be 6.25% and RAM would be dominant instead.

v1 deck discussion question (cut from the current slides)G5.3 Compare YARN's two-level scheduling (RM allocates containers; AM places tasks) with Kubernetes's one-level scheduling (kube-scheduler places pods directly). Under what workloads does two-level scheduling outperform one-level?
  • Two-level (YARN): the RM only decides how much each application gets, as containers. Each framework's AM decides which task runs in which container using its own logic (data locality, stage DAG, speculative execution). The central scheduler stays light, and each framework schedules its own way.
  • One-level (Kubernetes): one central scheduler places every pod using generic filters and scores. It is simpler and uniform, but it does not know a framework's tasks.
  • Two-level wins for many short, data-local tasks, as in MapReduce or Spark batch jobs with thousands of tasks per second. The AM reuses a container for many tasks without a central decision each time, and applies HDFS locality and stage-aware placement. It also wins on multi-framework clusters with framework-specific needs (iterative ML, streaming, gang scheduling).
  • One-level is better for long-running services and microservices, where placement happens rarely and has to be uniform.
v1 deck: exam question he quotes from a top university courseG5.4 Harvard CS265 exam question: Prove that for a query selecting k columns from a c-column row-store table of n rows, the I/O complexity is Θ(n·c), but Θ(n·k) for a column store.

Assume fixed-width cells and that I/O is counted in cells, or pages of B cells (assumed).

  1. Row store: each row's c cells are stored together on a page, so one page holds B/c rows. Any query touching all n rows must read every page, even to get only k columns: n·c/B pages. The k needed cells cannot be read without reading their neighbours on the same page. The cost is at least n·c/B and at most n·c/B, so it is Θ(n·c), independent of k.
  2. Column store: each column is stored as its own contiguous file of n cells, which is n/B pages. The query opens only the k needed columns: k·n/B pages, and no other column is touched. That is both an upper and a lower bound (all n values of each selected column are needed), so it is Θ(n·k).

Meaning: the I/O ratio is c/k. For k = 4 and c = 80, that is 20× less I/O. This is the column-pruning gain in Parquet and ORC.

Course plan seed question (differs from the slides)G5.5 Data Lake Performance Migration: a Dhaka telecom stores 10 TB of daily call-detail records on HDFS as gzip-compressed CSV. A Hive query selecting 4 of 80 columns takes 6 hours. (a) Identify two specific reasons this configuration is slow. (b) Propose a migration strategy: new format, compression codec and partitioning scheme. (c) Estimate the expected I/O reduction (show calculation). (d) Which YARN scheduler would you use and why, given that multiple teams share the cluster? [Plan seed version: 10 TB of web click data stored as gzip CSV; propose a migration strategy (format, partitioning, codec).]

(a) 1. Gzip is not splittable, so each large file goes to one Mapper and the job has little parallelism and few data-local reads. 2. CSV is row-oriented, so selecting 4 columns still reads and parses all 80. A third reason: no partitioning, so every query scans everything.

(b) Convert to Parquet (or ORC for a Hive-only stack) with Snappy compression, which is fast and splittable at row-group level. Partition by date (dt=YYYY-MM-DD, optionally plus region), keep files of about 128 MB to 1 GB, and sort by a commonly filtered column so predicate pushdown can skip row groups. Migrate with a one-off INSERT OVERWRITE ... SELECT CTAS job. The web-click version has the same answer, partitioned by event date (and hour).

(c) I/O read = table size × (columns read / total columns), with equal column widths (assumed).

  1. Column pruning: 10 TB × 4/80 = 0.5 TB.
  2. Reduction = 1 − 4/80 = 95% (20×).
  3. Query time scales roughly with I/O (assumed): 6 h / 20 = 0.3 h ≈ 18 min. Date-partition pruning and predicate pushdown reduce it further.

Meaning: the same query reads about 1/20 of the data and finishes in minutes, not hours.

(d) Capacity Scheduler: each team gets its own queue with a guaranteed minimum share and an elastic maximum, so ad-hoc users cannot starve production ETL. Preemption returns borrowed capacity when the owning queue needs it. The Fair Scheduler (DRF) is an alternative when equal sharing matters more than guarantees.

v1 deck: his model T/F justificationsG5.6 True or false? Give the one-line justification he wants for full marks.

  2. Gzip files are natively splittable in Hadoop.
  1. False. Parquet is columnar, built for read-heavy analytical queries, not row-by-row writes.

Week 6: Spark

v1 deck discussion question (cut from the current slides)G6.1 A Spark job runs logistic regression over a 50 GB dataset on a 10-node cluster with 32 GB RAM/node. (a) Can the full dataset be cached at MEMORY_ONLY? (b) If not, which StorageLevel would you choose and why? (c) Estimate how many iterations are needed before the cached speedup (130×) pays for the initial caching cost (1 extra HDFS read).

(a) Total RAM = 10 × 32 = 320 GB, but Spark's unified memory is about (32 GB − 300 MB) × 0.6 ≈ 19 GB per node, so ≈190 GB in total, shared with execution. Raw, 50 GB would fit. As deserialised Java objects (assumed 3 to 5× larger), it becomes 150 to 250 GB, which does not reliably fit at MEMORY_ONLY. Partitions that do not fit are dropped and recomputed every iteration.

(b) MEMORY_ONLY_SER (with Kryo), which stores the data at about its raw 50 GB size, or MEMORY_AND_DISK_SER so overflow partitions spill to local disk instead of being recomputed from HDFS. It costs some CPU for deserialisation and uses much less memory with no recompute.

(c) Let T = one HDFS pass. Uncached cost = n·T. Cached cost = 2T for the first iteration (read plus caching) + (n − 1)·T/130 for the rest.

  1. Break-even: n = 2 + (n − 1)/130.
  2. n = 259/129 ≈ 2.01.
  3. So caching pays off from the 3rd iteration.

Meaning: for any iterative job (logistic regression usually runs 10 to 100 iterations), caching always pays.

v1 deck discussion question (cut from the current slides)G6.2 A groupByKey on an RDD with 1 billion records and 500 distinct keys produces 500 shuffle partitions. Identify two data skew scenarios that would cause OOM errors and propose a fix for each.

The average is 109/500 = 2M records per key, and groupByKey holds all of a key's values in memory on one task.

  1. Hot key: one key (for example a NULL/"unknown" customer, or a top merchant) holds 40% of the data, which is 400M values in a single task's iterator, so that task runs OOM. Fix: use reduceByKey/aggregateByKey (map-side combine) instead of groupByKey, or salt the hot key (key_0 to key_N), aggregate, then merge. Filter NULL keys out and handle them separately.
  2. Hash collisions in partitioning: with 500 keys over 500 partitions, hash(key) mod 500 sends several large keys to the same partition while others stay empty, so a few tasks hold 2 to 3 keys' worth of data and run OOM. Fix: use a custom partitioner or range partitioner, or increase partitions (for example 2,000), or enable AQE skew handling (spark.sql.adaptive.skewJoin.enabled) to split oversized partitions.
v1 deck discussion question (cut from the current slides)G6.3 Compare RDD lineage fault tolerance with HDFS 3× replication for a 10-iteration ML job. Under what failure rate does lineage become slower than replication?
  • Replication: every iteration writes its result 3× to HDFS, a fixed cost w per iteration whether or not anything fails. Recovery is fast (re-read a replica).
  • Lineage: zero overhead when there are no failures. A failure at iteration i recomputes the lost fraction f of up to i iterations, so the cost grows with lineage length.

Lineage is slower when the expected recompute cost exceeds the replication cost: p·f·T·Σi > 10·w, with Σi = 1+2+…+10 = 55, so p > 10w / (55·f·T).

  1. Assume w = 0.5T (a 3× HDFS write costs about half an iteration) and a worst-case full recompute (f = 1, wide dependencies): p > 5/55 ≈ 0.09, about one failure every 11 iterations.
  2. With one of 10 executors lost per failure (f = 0.1): p > 0.91, which almost never happens.

Meaning: lineage wins unless failures are very frequent (roughly one or more per job with long, wide lineage). Checkpointing every few iterations caps the lineage length.

v1 deck: exam question he quotes from a top university courseG6.4 Stanford CS246 exam question: Given the following Spark DAG, identify all stage boundaries and estimate the total shuffle volume for a 1 TB input dataset with 1,000 partitions.

The question does not include the DAG. Use this method on the DAG you are given.

  1. Stage boundaries fall at every wide dependency (groupByKey, reduceByKey, join without co-partitioning, distinct, repartition, sortBy). Chains of narrow operations (map, filter, flatMap, union, mapPartitions) are pipelined into one stage. Number of stages = number of shuffles + 1.
  2. Partition size = 1 TB / 1,000 = 1 GB per partition, so each stage runs 1,000 tasks.
  3. Shuffle volume per wide operation = the size of the map-side output going into it. With no reduction (groupByKey or join right after reading), that is about 1 TB per shuffle. With reduceByKey, map-side combine shrinks it to roughly the number of distinct keys per partition × record size. Filters before the shuffle scale it by their selectivity.
  4. Total = sum over all shuffles. For example, map → filter (keeps 50%) → reduceByKey → join: about 0.5 TB plus the join's shuffle input. Each shuffle creates M × R = 1,000 × 1,000 = 106 shuffle blocks.
Course plan seed question (differs from the slides)G6.5 Iterative I/O Cost Analysis: train K-Means on 50 GB of bKash transaction data for 100 iterations. HDFS read = 500 MB/s; RAM cache read = 5,000 MB/s. (a) Total HDFS I/O for MapReduce (all 100 iterations). (b) Total I/O for Spark (50 GB fits in cluster RAM). (c) Wall-clock time for each. (d) When would Spark NOT outperform MapReduce? [Plan seed version: same job, assuming 100 ms per 128 MB block.]

MapReduce I/O = iterations × (D read + D written) on HDFS. Spark = 1 HDFS read + (iterations − 1) RAM reads. 1 GB = 1,000 MB (assumed).

  1. (a) MR: 100 × (50 GB read + 50 GB written) = 10,000 GB (10 TB) of HDFS I/O.
  2. (b) Spark: 50 GB from HDFS once, plus 99 × 50 = 4,950 GB from the RAM cache.
  3. (c) MR: 100,000 MB / 500 MB/s = 200 s per iteration, × 100 = 20,000 s ≈ 5.6 h. Spark: 100 s + 99 × (50,000 / 5,000 = 10 s) = 100 + 990 = 1,090 s ≈ 18.2 min. Speedup ≈ 18×.
  4. Plan seed version: 50 GB / 128 MB = 400 blocks. MR: 400 × 100 ms × 100 iterations = 4,000 s ≈ 66.7 min. Spark: one read, 400 × 0.1 = 40 s, with cached passes treated as near zero. That gives ≈100× less I/O time.

Meaning: once the data is cached, every later iteration is about 10× cheaper, so total I/O falls by roughly the iteration count.

(d) Spark does not win when the data does not fit in memory (it spills or recomputes). It does not win for single-pass ETL with no reuse, under heavy GC or memory pressure, for very small jobs where startup dominates, or when the job is shuffle- or network-bound rather than read-bound.

Course plan seed question (differs from the slides)G6.6 RDD Failure Recovery Trace: a job computes input → filteredRDD → mappedRDD → reducedRDD over 10 partitions. Mid-execution, the Executor holding partitions 3 and 7 of reducedRDD crashes. Trace the complete recovery: what does the Driver detect, which partitions of which RDDs need to be recomputed, and what is the worst-case recovery cost if reducedRDD involves a wide dependency (groupByKey)?
  1. Detect: the driver stops receiving the executor's heartbeats (or gets a lost-executor event from the cluster manager). It marks the executor dead, the BlockManagerMaster drops its cached blocks, and its running tasks fail.
  2. Lineage lookup: the DAGScheduler sees that reducedRDD partitions 3 and 7 are missing and walks the lineage back.
  3. Narrow case: each partition depends on one parent partition, so only partitions 3 and 7 of filteredRDD, mappedRDD and reducedRDD are rebuilt from input splits 3 and 7. That is 2 tasks, pipelined, on other executors.
  4. Wide case (groupByKey): each reduced partition depends on all 10 mappedRDD partitions through the shuffle. If the shuffle map outputs are still on healthy executors (or an external shuffle service), only 2 reduce tasks re-run and fetch their shuffle blocks. Map outputs that lived on the dead executor cause a FetchFailed, and the parent shuffle-map stage re-runs for those map partitions.
  5. Worst case: all map outputs are lost or unreadable, so all 10 input → filtered → mapped partitions are recomputed and reshuffled, and then the 2 reduce partitions run. That is 10 + 2 = 12 tasks, about a full re-run of the map stage plus a full shuffle, compared with 2 tasks in the narrow case.

Meaning: a wide dependency makes the recovery cost grow with the whole parent stage. Checkpoint or persist after expensive shuffles to limit it.

Week 7: Hive and SQL-on-Hadoop

Course plan: marked "important exam topic"G7.1 Hive vs. traditional SQL (RDBMS) differences (marked "important exam topic"): compare schema enforcement, ACID, UPDATE/DELETE, indexing and latency.
  • Schema: RDBMS = schema-on-write (validated at insert); Hive = schema-on-read (applied at query time).
  • ACID: RDBMS has full ACID. Hive is limited: only ORC tables in transactional (ACID) mode.
  • UPDATE/DELETE: RDBMS supports both fully. Hive supports them on ACID tables only, through delta files and compaction.
  • Indexing: RDBMS uses B-tree indexes. Hive uses partitions + buckets (and ORC min/max stats).
  • Latency: RDBMS milliseconds (OLTP); Hive seconds-minutes (batch OLAP over TB-PB).
v1 deck: his own "Exam Tip" boxG7.2 A student says HiveQL is just SQL, so a SELECT COUNT(*) on a 1 TB Hive table will return in milliseconds. Correct them.

Wrong. Hive is a batch system. On MapReduce that query takes about 5–10 minutes: job start-up, a full scan of 1 TB, a shuffle to one reducer.

Use Presto/Trino, Impala or Spark SQL when you need interactive latency. Use Hive for large batch ETL.

His v1 slide calls this "the most common misconception". It is the latency row of his Hive vs SQL table.

v1 deck discussion question (cut from the current slides)G7.3 Spotify's co-occurrence query runs GROUP BY song_a, song_b over 2 billion playlist rows. Estimate the output size if there are 30M songs. Propose a partitioning + bucketing scheme for the playlist_songs Hive table that would reduce the shuffle size for this query.

Formula: distinct unordered pairs = C(n,2) = n(n-1)/2.

  1. Upper bound: C(30M,2) = 4.5 x 1014 pairs; At 12 B per row (two INT ids + 4-byte count, assumed) that is 5.4 PB.
  2. Realistic bound from the data: 2 B rows with 20 songs per playlist (assumed) gives 108 playlists x C(20,2)=190 = 1.9 x 1010 pairs. That is about 228 GB emitted before aggregation. The output is at most this, because most of the 4.5 x 1014 pairs never co-occur.

Scheme: Partition playlist_songs by week/dt, so only new weeks are processed incrementally. Bucket and sort by playlist_id, so the self-join (a.playlist_id = b.playlist_id) is a bucket/SMB join with no shuffle. Add a.song_id < b.song_id to halve the pairs. Map-side aggregation and a HAVING count threshold cut the shuffle further.

Meaning: real co-occurrences (hundreds of GB) bound the shuffle, not the 5.4 PB theoretical matrix.

v1 deck discussion question (cut from the current slides)G7.5 Spotify uses Luigi while other companies use Apache Airflow. Compare the two on: dependency declaration style, backfill capability, and UI/observability. Which would you choose for a 100-step daily pipeline?
  • Dependencies: In Luigi, each Task declares requires() and output() targets, and the graph is pulled backward from the target. In Airflow, you write an explicit DAG in Python, link operators with >> and attach the schedule to the DAG.
  • Backfill: Luigi re-runs a task when its output target is missing. It has no built-in scheduler or date ranges, so it needs cron. Airflow has native scheduling and airflow dags backfill over date ranges, plus catchup and retries per task.
  • UI: Luigi's central scheduler UI is basic (task status, graph). Airflow has a rich web UI: grid and graph views, logs per task, SLAs and alerts.
  • Choice: Pick Airflow for a 100-step daily pipeline. At that size, scheduling, backfill, retries and observability matter most.
v1 deck: exam question he quotes from a top university courseG7.6 Given a HiveQL query with two JOINs and a GROUP BY, draw the MapReduce DAG that Hive would generate, identifying the shuffle key at each stage.

Example (assumed): SELECT c.city, SUM(o.amt) FROM orders o JOIN customers c ON o.cust_id=c.cust_id JOIN products p ON o.prod_id=p.prod_id GROUP BY c.city.

Job1: Map(orders, customers) --shuffle key: cust_id--> Reduce: join1 -> tmp1
Job2: Map(tmp1, products)    --shuffle key: prod_id--> Reduce: join2 -> tmp2
Job3: Map(tmp2) emit (city, amt) --shuffle key: city--> Reduce: SUM -> output

Each common (reduce-side) join is one MR job keyed on its join column. The GROUP BY adds one job keyed on the group-by column. If both joins use the same key, they merge into one job. A small table becomes a map join (no shuffle stage).

Course plan seed question (differs from the slides)G7.7 Partitioning & Bucketing Design: 5 TB e-commerce transaction table (txn_id, user_id, product_id, amount, country, txn_date). Design a complete partitioning and bucketing strategy to optimise (i) daily revenue reports filtered by country and txn_date, (ii) JOINs with a 10 M-row user profile table keyed on user_id. Write the complete CREATE TABLE DDL. Justify the number of buckets and the partition column(s).

Partition on txn_date (every daily report filters on it). Reports also filter by country. Assume few countries, so either add country as a second partition level or rely on ORC min/max stats. Bucket on user_id (join key, high cardinality).

Bucket count formula: file size per bucket = (partition size) / N. Target 128-256 MB.

  1. Assume 3 years of data (assumed) = 1,095 daily partitions. 5 TB / 1,095 = 4.57 GB per day.
  2. N = 32: 4.57 GB / 32 = 143 MB per bucket file (about 1 HDFS block).
  3. User table: 10 M rows x 200 B (assumed) = 2 GB; Bucket it on user_id into the same 32 buckets, 62.5 MB each. A bucket map / SMB join then pairs bucket i with bucket i.
CREATE TABLE transactions (
  txn_id BIGINT, user_id BIGINT, product_id BIGINT,
  amount DECIMAL(12,2), country STRING)
PARTITIONED BY (txn_date DATE)
CLUSTERED BY (user_id) SORTED BY (user_id) INTO 32 BUCKETS
STORED AS ORC TBLPROPERTIES ('orc.compress'='SNAPPY');

CREATE TABLE users (user_id BIGINT, name STRING, city STRING)
CLUSTERED BY (user_id) SORTED BY (user_id) INTO 32 BUCKETS
STORED AS ORC;
SET hive.optimize.bucketmapjoin.sortedmerge=true;

Meaning: a daily-by-country report scans one 4.57 GB partition instead of 5 TB. The user join needs no shuffle. Do not partition by user_id (10 M directories) or by country+date with many countries. That avoids the small-file problem.

Course plan seed question (differs from the slides)G7.8 Query Compilation to MapReduce: write HiveQL to find the top 5 products by total revenue in 2023; trace how Hive compiles it into MapReduce stages (Map output, shuffle key, Reduce computation). How would switching from MapReduce to Tez change the plan? (Plan version also asks: monthly average amount per country for Q1 2024.)
SELECT product_id, SUM(amount) AS revenue
FROM transactions
WHERE txn_date BETWEEN '2023-01-01' AND '2023-12-31'
GROUP BY product_id
ORDER BY revenue DESC
LIMIT 5;

-- Plan item: monthly average per country, Q1 2024
SELECT country, MONTH(txn_date) AS mon, AVG(amount) AS avg_amt
FROM transactions
WHERE txn_date BETWEEN '2024-01-01' AND '2024-03-31'
GROUP BY country, MONTH(txn_date);
  • Job 1 Map: reads only the 2023 partitions (pruning) and emits (product_id, amount). A map-side partial SUM runs (combiner / hash aggregation).
  • Shuffle key: product_id.
  • Job 1 Reduce: computes SUM(amount) per product_id and writes (product_id, revenue) to a temp HDFS dir.
  • Job 2: Map reads the temp output and emits top-5 candidates. A single reducer sorts by revenue DESC and applies LIMIT 5.
  • Tez: the same operators become one DAG (Map -> Reduce -> Reduce) in one application. There is no temp HDFS write between jobs. Containers are reused. Latency drops.
His textbook: misconception boxG7.9 True or false, with a justification: Presto is about 10× faster than Hive+MapReduce, so a 50 TB nightly ETL pipeline should be moved from Hive to Presto.

False. Presto is fast because it keeps intermediate data in memory with no disk writes. A multi-hour job that outgrows RAM, or loses a worker, fails and must start again.

Hive on Tez or Spark writes to disk and HDFS, so failed tasks are simply retried. Use Hive for large batch ETL and Presto for interactive queries that finish in seconds.

Slides: Presto has an in-memory pipeline with no intermediate disk; Hive is for large ETL jobs and relies on MapReduce/HDFS for fault tolerance. The ETL warning is from the lecturer's textbook (ch 7).

  1. HiveQL supports full ACID on all table types.
  2. Hive runs HiveQL directly on HDFS with no translation.

v1 deck discussion question (cut from the current slides)G8.1 Netflix's Kafka cluster handles 1.3M events/sec at peak across 4,000 topics. If each topic has 12 partitions, calculate the minimum number of brokers needed assuming each broker handles 50,000 partitions and a replication factor of 3.

Formula: brokers = ceil(topics x partitions x RF / partitions per broker).

  1. Partitions = 4,000 x 12 = 48,000.
  2. Replicas = 48,000 x 3 = 144,000.
  3. 144,000 / 50,000 = 2.88 -> 3 brokers.
  4. Check: RF 3 also needs at least 3 brokers. It holds.

Meaning: 3 is the theoretical minimum. At 1.3M events/s (325 events/s per topic on average), Netflix runs many more brokers for throughput, disk and failure headroom.

v1 deck discussion question (cut from the current slides)G8.2 A Flink job joins three Kafka streams - assignments, exposures and outcomes - on user_id. Events may arrive out of order by up to 30 seconds. Design an event-time window strategy (window size, watermark lag, allowed lateness) and justify each choice.
  • Event time from each event's timestamp, keyed by user_id.
  • Watermark lag = 30 s (bounded out-of-orderness). It matches the maximum disorder, so windows close only after all expected events arrive.
  • Window: tumbling (or interval join) of e.g. 5-10 min (assumed) Make it long enough that an assignment, its exposure and the outcome fall in the same window. An interval join (outcome within X min after exposure) handles window boundaries better than fixed windows.
  • Allowed lateness ~1-2 min plus a side output for later events. This updates results for rare stragglers beyond 30 s without holding state forever.

Trade-off: larger lag or lateness gives more complete results but raises latency and state size.

v1 deck discussion question (cut from the current slides)G8.3 Netflix uses both Lambda (speed + batch) and Kappa (stream-only) architectures for different pipelines. Identify two workloads where Lambda is preferable to Kappa and explain why stream reprocessing alone is insufficient.
  • Recommendation model training / billing-royalty reports over years of viewing history: these need full-history joins and aggregations. Replaying years of Kafka (Netflix keeps ~7 days) is impossible or too slow. The batch layer over S3/Iceberg recomputes it cheaply.
  • Financial/content-licensing reconciliation: this must be exact and auditable, with late corrections from partners. A batch recompute over the complete dataset is the source of truth. The speed layer gives provisional real-time numbers.

Stream replay alone fails when history exceeds log retention, when the job needs complex global computations, or when accuracy needs a guarantee from full recomputation.

v1 deck: exam question he quotes from a top university courseG8.4 MIT exam question: Why does Kafka use sequential disk writes rather than a B-tree index? Quantify the throughput difference on spinning disk.

Kafka only appends to a log, and consumers read sequentially by offset, so it needs no random lookups. A B-tree needs random seeks (O(log n) per write, ~10 ms each on HDD). On a spinning disk, sequential I/O runs at ~100-200 MB/s. Random 4 KB I/O runs at ~100-200 IOPS = ~0.4-0.8 MB/s. Sequential is roughly 100-1,000x faster (classic figure: ~6000x for linear vs random). The OS page cache and read-ahead add more gain.

Course plan seed question (differs from the slides)G8.5 Pipeline Design for a Bank: a Bangladeshi commercial bank must (a) synchronise 10 million customer records nightly from Oracle to Hadoop; (b) detect fraudulent card-swipe events in real time with a decision within 200 ms; (c) power a risk dashboard with data no older than 5 minutes. (a) Sqoop incremental import (--incremental lastmodified, -m 8 parallel mappers) into Hive/ORC nightly. It is batch with high throughput, and YARN retries failed map tasks. Latency is not critical. 10M rows x 1 KB (assumed) = ~10 GB, which takes minutes with parallel mappers.

(b) Card switch publishes swipes to Kafka (keyed by card_id, replication 3, acks=all). Course plan seed question (differs from the slides)G8.6 Lambda to Kappa Migration: a team using Lambda complains that two code paths (batch + stream) double development cost; the CTO suggests Kappa. Analyse (a) what must be true about the stream processing engine for Kappa to be viable; (b) the risks of migrating; (c) under what conditions Kappa is not suitable (at least two concrete scenarios from Bangladesh financial or healthcare sectors).

(a) The engine must support exactly-once state, event-time processing with watermarks, large durable state with checkpoints, and enough throughput to replay months of history fast. Kafka must retain the full history (long retention, tiered storage or compacted topics).

(b) Risks: replaying years of data is slow and costly. Long retention costs storage. Complex queries (big joins, full-history aggregates) are harder in streaming. A bug in the single path affects everything. The team needs new skills. The migration period runs both stacks.

(c) Not suitable: (1) Bangladesh Bank regulatory reports need years of transactions recomputed exactly and auditable. Batch over a warehouse is cheaper and easier to defend. (2) bKash/bank year-end reconciliation or interest calculation over all accounts is one huge batch job, not a stream. (3) Hospital/DGHS epidemiology on historical patient records from many hospitals. The records arrive as monthly files, so they are not an event stream, and they need complex joins.

His textbook: misconception boxG8.7 A Flume HDFS sink rolls a new file every 10 seconds. What goes wrong, and what fixes it?
  1. 86,400 / 10 = 8,640 small files per day per agent, each far below one 128 MB block.
  2. Every file is a NameNode metadata entry, so NameNode heap fills, and each file later becomes its own small map task.
  3. Fix: roll every 300–600 s or at 128 MB (one block per file); at 600 s that is 144 files a day.
  4. Or compact nightly: INSERT OVERWRITE ... SELECT into large Parquet/ORC files.

Beyond the slides: from the lecturer's textbook (ch 8). The slides cover Flume's Source → Channel → Sink, and the small-files problem from partitioning.

v1 deck discussion question (cut from the current slides)G9.1 A Grafana dashboard shows daily API error counts for a Big Data pipeline. Identify three Tufte violations in a dashboard that uses a 3-D bar chart with a y-axis starting at 500, a heavy grid, and gradient fill colours. Redesign the chart applying data-ink principles.

Violations: (1) 3-D bars: non-data ink. Perspective distorts heights and raises the lie factor. (2) y-axis at 500: the truncated baseline exaggerates differences (lie factor > 1). (3) heavy grid and (4) gradient fill: chartjunk that adds ink but no data.

Redesign: flat 2-D bars (or a line, since the data is a daily time series) in one muted colour. Y-axis from 0. No grid, or one light reference line (e.g. SLO threshold). Direct labels, minimal axes. Highlight only anomalous days in an accent colour.

v1 deck discussion question (cut from the current slides)G9.2 The NYT COVID tracker uses a 7-day rolling average instead of raw daily counts. (a) What reporting artefact does this remove? (a) It removes the day-of-week reporting artefact: low counts at weekends/holidays, catch-up spikes on Mondays, and one-off batch dumps of backlogged cases.

(b) A 7-day window lags and flattens sudden onset or turning points (start of a new wave, a super-spreader event, effect of a lockdown). A 3-day window shows the change sooner but is noisier.

v1 deck discussion question (cut from the current slides)G9.3 Design a Shneiderman-compliant interactive dashboard for a ride-sharing company's trip data (1M trips/day, 5 cities). His textbook: misconception boxG9.4 True or false, with a justification: a Grafana availability panel with an auto-scaled y-axis is fine, because the tick labels show the true values.

False. Readers judge bar and line height, not tick labels. Auto-scaling to 99.975–99.995% makes a 0.01-point wobble span half the chart's height.

Example: 99.98% is drawn at 25% of the height and 99.99% at 75%, a 200% visual rise for a real change of 0.01 / 99.98 ≈ 0.010%. The lie factor is 200 / 0.010 ≈ 20,000.

Start availability and ratio charts at zero, or label the zoomed axis clearly.

Slides: lie factor, and the y-axis should start at 0. The auto-scaling dashboard case is from the lecturer's textbook (ch 9).

v1 deck discussion question (cut from the current slides)G10.1 Kwak et al. found Twitter's average shortest path is 4.12 hops over 41.7M users. If a misinformation tweet is retweeted by a high-PageRank account, estimate how many users it reaches within 3 hops assuming an average out-degree of 45. What graph property makes this estimate an overestimate?

Reach within h hops ≈ d + d2 + d3 (tree assumption)

  1. Hop 1: 45
  2. Hop 2: 452 = 2,025
  3. Hop 3: 453 = 91,125
  4. Total ≈ 45 + 2,025 + 91,125 = 93,195 users

Meaning: about 93 K users (0.2% of 41.7 M) in 3 hops. This is an overestimate because of clustering / triadic closure (high clustering coefficient, overlapping follower sets, reciprocity). Many hop-2/3 users are the same people counted again. Also, not every follower retweets.

v1 deck discussion question (cut from the current slides)G10.2 A Prophet model for weekly hospital admissions has strong annual and weekly seasonality but misses a sudden COVID-19 wave onset. Which Prophet component should detect this changepoint, and what prior hyperparameter controls the model's sensitivity to new changepoints?

The trend component g(t) (piecewise-linear/logistic trend with changepoints) should capture the onset. changepoint_prior_scale controls sensitivity (default 0.05; it is the scale of the Laplace prior on rate changes). Raising it (e.g. 0.5) makes the trend react more to the wave, but risks overfitting noise. Also relevant: n_changepoints and changepoint_range (default 0.8, so Prophet places no changepoints in the last 20% of history unless you raise it).
