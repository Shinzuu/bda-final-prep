Week 5 — YARN, File Formats and Compression

Short questions (2 marks)

1. ★ Which YARN component allocates resources across the whole cluster?

The ResourceManager (one per cluster). Only the RM sees the free resources on every node. The AM asks for resources for its own job only.

2. ★ In which Hadoop version did YARN arrive, and what did it replace?

Hadoop 2.0 (2013). YARN split the single JobTracker into a global ResourceManager and one ApplicationMaster per job. The reason: one JobTracker could run only MapReduce, and it could not scale.

3. ★ What does "splittable" mean for a file format?

Several Mappers can process different parts of the file at the same time. This works because reading can start anywhere in the file.

4. ★ Which format is columnar and best for read-heavy analytics?

Parquet. A query reads only the columns it needs. ORC is also columnar, but ORC is the format Hive prefers.

5. ★ True or false: Gzip files are natively splittable? Why?

False. A Gzip file must be decompressed from the start. So each file gets one Mapper, and the rest of the cluster sits idle.

6. ★ True or false: YARN lets Spark and Tez share one Hadoop cluster? Why?

True. Each framework brings its own ApplicationMaster. The RM hands out generic containers to any framework. Hadoop 1.x could run only MapReduce.

7. True or false: Parquet is row-oriented and write-optimised? Why?

False. Parquet is columnar and built for read-heavy analytics. "Row-based and append-friendly" describes Avro.

8. True or false: ORC is optimised for Hive and has among the highest compression? Why?

True. ORC is Hive's columnar format. It has the best compression, ACID support and vectorised reads.

9. ★ [New] What is a container? How many AMs run for 12 active jobs?

A container is a slice of one node: a fixed number of vcores plus a fixed amount of RAM. A task runs inside it. 12 AMs run, because every job gets exactly one ApplicationMaster.

10. ★ [New] What is predicate pushdown?

The reader checks the min/max stats in the Parquet footer. It skips row groups that cannot match the filter. The skipped data is never read from disk.

11. ★ [New] What is DRF (Dominant Resource Fairness)?

DRF is fairness over several resources (CPU and RAM). It equalises each user's largest share, called the dominant share. So CPU-heavy jobs and RAM-heavy jobs are treated fairly.

12. ★ [New] What is schema evolution? What happens to a new field?

Schema evolution means changing the schema (for example, adding a field) without breaking readers. In Avro, a reader ignores fields it does not know. A missing field takes its default value.

13. [New] How does the RM detect a dead NodeManager? Give the AM and RM limits.

The node's heartbeats stop. After more than 10 min, the RM declares the node lost. The AM gets at most 2 attempts. With RM HA, the RM fails over through ZooKeeper in under 60 s.

14. [New] Give the Parquet layout and the splittable codecs.

Layout: row groups (about 128 MB) contain column chunks, which contain pages. The stats sit in the footer. Splittable codecs: bzip2, and LZO with an index. Gzip, Snappy and Zstd are not splittable on their own.

Differences

Hadoop 1.x vs YARN

Hadoop 1.x: one JobTracker, runs MapReduce only, about 4,000 nodes, fixed slots.

YARN: RM plus one AM per job, runs any framework, 10,000+ nodes, containers.

ResourceManager vs ApplicationMaster

RM: one per cluster. It grants containers.

AM: one per job. It requests containers, runs tasks and retries failed tasks.

NM failure vs AM failure

NM failure: the RM sees missed heartbeats. The AM then re-requests the lost containers.

AM failure: the RM restarts the AM (at most 2 attempts).

Capacity vs Fair scheduler

Capacity: each queue has a guaranteed share. Queues can borrow idle capacity. Good for SLAs.

Fair: each job gets an equal share. Short jobs finish fast.

Row vs columnar store

Row (CSV, Avro): reads whole records. Good for writes.

Columnar (Parquet, ORC): reads only the columns a query needs.

Avro vs Parquet

Avro: row-based, supports schema evolution, used for ingest.

Parquet: columnar, supports predicate pushdown, used for analytics.

Parquet vs ORC

Both are columnar.

Parquet: used for Spark and ML.

ORC: used for Hive. Highest compression, ACID support.

Snappy vs Gzip

Snappy: fast, medium compression ratio. Used inside Parquet and Avro.

Gzip: slow, high compression ratio. Not splittable.

Descriptive (4 marks)

1. ★ Explain YARN's RM, NM and AM, and how they interact for a Spark job. (D1)

  • ResourceManager (one per cluster): its Scheduler grants containers. Its ApplicationsManager accepts jobs and starts each job's AM.
  • NodeManager (one per node): launches and monitors containers. It sends heartbeats to the RM.
  • ApplicationMaster (one per job): requests containers, tells NMs what to launch, and retries failed tasks.

Flow: the client submits the job to the RM. The RM starts the Spark AM. The AM asks for 100 containers of {4 cores, 8 GB}. The RM grants the 80 that are free. The NMs launch the executors. When the job ends, the AM unregisters.

Exam sentence: the RM decides who gets resources, the NM runs them, and the AM manages one job.

2. ★ What is columnar storage and why is it faster for few-column queries? Give numbers. (D2)

Columnar storage keeps each column's values together (Parquet, ORC). A row store (CSV) keeps whole records together. This makes columnar faster in three ways:

  • A query reads only its own columns.
  • Values of the same type sit side by side, so they compress better.
  • Footer min/max stats allow predicate pushdown, which skips row groups.

Example: 100 columns, 10 TB, and the query needs 3. CSV reads 10 TB. Parquet reads 10 × 3/100 = 300 GB. That is 97% less I/O, about 33×.

Exam sentence: columnar means you read only what you need, and it is compressed.

3. ★ Compare Avro and Parquet; explain schema evolution and when to use each. (D3)

Avro is row-based and stores its JSON schema with the data, so appends are cheap. Parquet is columnar with min/max stats, so scans of a few columns are cheap.

Schema evolution means the schema changes while old files and readers keep working. Avro does this by matching the writer schema against the reader schema. Missing fields get their defaults. Extra fields are ignored.

Use Avro for Kafka → HDFS ingest. Use Parquet for analytics in Spark, Presto and ML.

Exam sentence: Avro to write and evolve, Parquet to read and analyse.

4. [New] YARN two-level scheduling vs Kubernetes one-level: when is two-level better?

YARN: the RM grants containers, then each AM places its own tasks. Kubernetes: one scheduler places every pod. Two-level scheduling wins in four cases:

  • Many short tasks: the AM reuses its executors.
  • Data locality: the AM knows where its HDFS blocks are.
  • Many frameworks on one cluster.
  • Isolation: an AM crash hits only its own job.

Exam sentence: two-level scheduling keeps the central scheduler simple and lets each framework schedule smartly.

Long / scenario (6 marks)

1. ★ Telecom: 10 TB of daily CDR as gzip CSV. A Hive query on 4 of 80 columns takes 6 h. (a) Two reasons. (b) Migration. (c) I/O estimate. (d) Scheduler. (A1)

(a) First, CSV is a row store. All 80 columns are read from disk to use only 4. Second, gzip is not splittable. Each file gets one Mapper, and most of the cluster sits idle.

(b) Convert to ORC + Zlib, or Parquet + Snappy, partitioned by dt=/region=. For a filter like WHERE duration > 600, the footer min/max stats skip row groups that cannot match.

(c) Columns read: 10 TB × 4/80 = 500 GB. That is 95% less, or 20×. If the query is I/O-bound (assumed), 6 h ÷ 20 ≈ 18 min.

(d) Use the Capacity Scheduler. Each team gets a guaranteed queue (for example ETL 60%, streaming 30%, ad-hoc 10%), and idle capacity can be borrowed. With FIFO, one 6-hour job would block everyone behind it.

2. ★ NodeManager NM2, running 5 MapReduce containers, fails. Trace the detection, the RM state changes and the restart. (A2)

(a) Every NM sends heartbeats to the RM. When NM2 crashes, its heartbeats stop. The RM declares NM2 lost after the timeout of more than 10 min.

(b) The RM removes NM2's capacity from the scheduler. It marks NM2's 5 containers FAILED. It tells the job's AM in the next heartbeat/allocate exchange.

(c) The AM re-requests 5 containers. The RM grants them on healthy nodes such as NM1 or NM3, near the HDFS replicas. The tasks rerun from their splits. Finished map output on NM2's disk is also rerun, because reducers cannot fetch it. If the AM itself was on NM2, the RM restarts the AM (at most 2 attempts).

3. ★ [New] LinkedIn spark queue: a job needs 2,000 containers, but only 1,250 are free. What happens under (a) Capacity, (b) Fair, (c) FIFO?

(a) Capacity: the job gets the 1,250 free containers now. The other 750 come back by pre-emption from queues that borrowed the spark queue's guaranteed share (with a 30 s warning). Production keeps its 40%, so its SLA is safe.

(b) Fair: the job gets only its equal share among the running jobs. Its share grows as other jobs finish. Short jobs still finish quickly.

(c) FIFO: if the job was submitted first, it takes all 1,250 containers. Its last 750 tasks wait for a second wave. Every later job waits behind it. This is starvation.

4. ★ [New] LinkedIn case study (Part 2 lessons): three silos merged into one 5,000-node YARN cluster. (a) Why not Hadoop 1.x? (b) Utilisation and SLAs. (c) Pre-emption. (d) "YARN is the OS", and Samza.

(a) The Hadoop 1.x JobTracker ran only MapReduce (no Spark, no Samza). It was capped at about 4,000 nodes.

(b) The three silos were busy at different times, so each one sat idle part of the time. One shared cluster raised utilisation from 45% to 78%. 78 ÷ 45 = 1.73, so the same hardware does 73% more work. Capacity queues (production 40%) protect the SLAs.

(c) Aggressive pre-emption killed long Spark jobs, and hours of work were lost. The fix was a 30 s grace period plus checkpoint-on-preempt, so a job saves its state first.

(d) The RM is like an OS kernel, and the frameworks are like processes. Samza runs each stream task as a long-running container. If the container dies, YARN restarts it, and it continues from its Kafka offset.

5. ★ [New] bKash lake: Kafka → Avro; nightly Parquet + Snappy by dt=/region=; data older than 2 years → ORC + Zstd. The old system used gzip CSV. Justify.

(a) Avro for ingest: appends from Kafka are cheap. Schema evolution lets new fields be added safely.

(b) Parquet + Snappy nightly: queries read few columns, pushdown works, and the files are fast and splittable. Partition pruning works on dt=/region=.

(c) Cold data older than 2 years goes to ORC + Zstd for the best compression (60% smaller). 50 TB of CSV (assumed) × (1 − 0.60) = 20 TB.

(d) The old gzip CSV was slow because gzip is not splittable (1 Mapper per file).

Numericals

1. ★ Live exercise: 5,000 nodes (64 GB, 16 vCPU each); queues 40/25/15/10/10%; Hive container {4 GB, 2 vCPU}, Spark {8, 4}, Samza {2, 1}. Find the max containers, the bottleneck, and the nodes needed for 10,000 Hive mappers.

max = min(RAM ÷ c_ram, vCPU ÷ c_cpu); nodes = ceil(T ÷ per-node)

  1. Production (40%) = 2,000 nodes: by RAM 128,000/4 = 32,000; by CPU 32,000/2 = 16,000. Max is 16,000.
  2. Spark 5,000, samza 12,000, adhoc 4,000.
  3. CPU is the bottleneck: the container has 2 GB per vCPU, which is less than the node's 4 GB per vCPU.
  4. Per node: min(16, 8) = 8 containers. 10,000 ÷ 8 = 1,250 nodes.

Meaning: CPU runs out first. The 1,250 nodes fit inside production's 2,000.

2. ★ 100 columns, 10 TB, query on 3 columns; pushdown reads 50 GB.

read = D × k/N

  1. 10 TB × 3/100 = 300 GB, so 33× less.
  2. 50 GB of 10 TB = 0.5%, so 200× less.

Meaning: column pruning plus pushdown shrinks the scan hugely.

3. ★ A 10 GB file: how many Mappers as gzip CSV vs Parquet with 128 MB row groups?

  1. Gzip: 1 Mapper.
  2. Parquet: 10,240 / 128 = 80 Mappers.

Meaning: Parquet gives 80-way parallelism. Gzip forces one slow Mapper.

4. ★ A Spark AM requests 100 containers {4 cores, 8 GB}; the RM grants 80.

  1. Granted: 80 × 4 = 320 cores and 80 × 8 = 640 GB. That is 80% of the request.

Meaning: the job starts with whatever is free.

5. ★ [New] a2i: 200 nodes (64 GB, 16 vCPU each); queue B (30%) runs executors {8 GB, 4 vCPU}.

  1. 30% of 200 = 60 nodes → 3,840 GB and 960 vCPU.
  2. By RAM: 480 executors. By CPU: 240. So 240, and the queue is CPU-bound.

Meaning: half of the queue's RAM stays unused.

6. [New] PYMK: 600 executors of 8 GB on nodes with 64 GB / 16 vCPU. Total memory? Dominant resource?

  1. Memory: 600 × 8 = 4,800 GB.
  2. Per executor: 8/64 = 12.5% of RAM, and 4/16 = 25% of CPU (4 vCPU assumed). So CPU is dominant. 4 executors fit per node → 150 nodes.

Meaning: DRF would count this job by its CPU share, not its RAM share.

Week 6 — Spark: RDDs, DataFrames, In-Memory Computing

Short questions (2 marks)

1. ★ Why is Spark much faster than MapReduce for iterative algorithms? (Q1)

Spark caches intermediate data as RDDs in memory. MapReduce reads and writes HDFS in every iteration. The reason is not more cores or SSDs.

2. ★ How does Spark get RDD fault tolerance without full replication? (Q2)

Spark uses lineage. It recomputes a lost partition from its parent RDDs by replaying the transformations. This works because RDDs are immutable and the steps are deterministic.

3. ★ Which is NOT part of the Spark ecosystem: MLlib, GraphX, Structured Streaming, HBase? (Q3)

HBase. It is a separate NoSQL database. The ecosystem is Spark SQL, MLlib, Structured Streaming and GraphX.

4. ★ When is a transformation like map() or filter() executed? (Q4)

Lazily. Spark only records it in the DAG. It runs when an action (count, collect) is called. This lets Spark optimise the whole plan.

5. ★ True or false: Spark can only run on Hadoop YARN? (TF1)

False. The Cluster Manager can be YARN, Kubernetes, Mesos or Standalone. A local[n] mode also exists.

6. ★ True or false: RDDs are mutable and can be changed in place? (TF2)

False. RDDs are immutable. A transformation creates a new RDD. This is why lineage recovery is safe.

7. ★ True or false: DataFrames give schema-aware, named-column operations like SQL tables? (TF3)

True. A DataFrame has named columns and a schema. You can query it with SQL. Catalyst optimises it.

8. ★ True or false: MapReduce beats Spark for many-iteration ML? (TF4)

False. Spark caches the data and reuses it, so it is 10–100× faster. MapReduce re-reads HDFS in each iteration.

9. [New] True or false: rdd.collect() is a safe way to view a 300 GB result?

False. collect() pulls everything into Driver memory. Driver memory is far smaller, so the job fails with OOM. Use take(n) or saveAsTextFile().

10. [New] Which component builds the DAG and schedules tasks?

The Driver. The Cluster Manager (YARN) gives resources. Executors run the tasks.

11. What changes in toDebugString() after cache()? (Live exercise Q1)

The lineage stays the same. A storage level appears ([Memory Serialized 1x Replicated]). After an action, CachedPartitions also appear.

12. What do you see when you time count() uncached, then cached? (Live exercise Q2)

Run 1 is slowest. Run 2 is faster because Spark reuses the shuffle files. The cached run is fastest. Speedup = uncached ÷ cached. On a README the speedup is small.

13. How do reduceByKey and groupByKey differ in the Spark UI? (Live exercise Q3)

groupByKey shuffles more bytes because it has no local combine. reduceByKey sums inside each partition before the shuffle.

Differences

MapReduce vs Spark

MapReduce: writes intermediate data to HDFS.

Spark: keeps the working set in RAM, so it is 10–100× faster on iterative jobs.

HDFS replication vs RDD lineage

HDFS replication: always stores 3 copies.

RDD lineage: stores only the recipe and recomputes lost partitions when a failure happens.

Narrow vs wide dependency

Narrow: one parent partition, same stage.

Wide: many parent partitions, a shuffle, a new stage.

reduceByKey vs groupByKey

Both: shuffle.

reduceByKey: pre-aggregates in each partition (like a Combiner), so it sends far less data over the network.

DataFrame vs RDD

DataFrame: named columns and a schema, optimised by Catalyst.

RDD: schema-less objects.

Driver vs Executor

Driver: runs main(), builds the DAG and schedules tasks.

Executor: a worker JVM that runs tasks and caches data.

MEMORY_ONLY vs MEMORY_AND_DISK

MEMORY_ONLY: drops partitions that do not fit and recomputes them.

MEMORY_AND_DISK: spills those partitions to local disk.

coalesce vs repartition

coalesce: reduces partitions without a shuffle (narrow).

repartition: reshuffles everything (wide).

Hash vs range partitioner

Hash: hashCode % n. It is the default. It can hot-spot on skewed keys.

Range: ordered key ranges. sortByKey uses it.

Descriptive (4 marks)

1. ★ What is an RDD, what does "resilient" mean, and how is a lost partition recovered without replication? (D1)

An RDD (Resilient Distributed Dataset) is a read-only, partitioned collection of records. Spark creates it from stable storage (HDFS) or by transforming another RDD.

Resilient means the RDD rebuilds itself from lineage, the recorded chain of transformations. It does not rely on three copies.

Example: an Executor crashes and partition 2 of mappedRDD is lost. The Driver traces the lineage (mappedRDD ← filteredRDD ← input). It re-reads only input partition 2 from HDFS. It re-applies filter, then map. The job continues.

This works because RDDs are immutable and transformations are deterministic. Long chains should be checkpointed to HDFS.

Exam sentence: "The computation is the backup."

2. ★ Differentiate transformations and actions, with two examples each. Why are transformations not run immediately? (D2)

A transformation is lazy. It does no work. It only returns a new RDD and adds one node to the DAG. Examples: map, filter (also reduceByKey).

An action is eager. It triggers execution of the whole DAG. It returns a value to the Driver or writes output. Examples: count, saveAsTextFile (also collect).

Spark waits so that it sees the full plan. Then it can optimise the plan. It can pipeline narrow steps in memory without disk writes. It can compute only the partitions it needs.

Exam sentence: "Transformations build the plan; actions run it."

3. ★ Describe lazy evaluation and its advantage using rdd.filter(x > 1000).first(). (D3)

Lazy evaluation means transformations only add nodes to the DAG. Nothing is computed yet.

When an action arrives, Spark analyses the DAG. It optimises it (DAG scheduler, or Catalyst for DataFrames). It pipelines the steps. It runs only the partitions it needs.

In rdd.filter(x > 1000).first(), the filter alone reads nothing. first() makes Spark scan the first partition and stop at the first value above 1000. Spark never reads the other partitions. An eager engine would filter everything first.

Exam sentence: "Laziness lets Spark do the least work that answers the action."

Long / scenario (6 marks)

1. ★ [New] K-Means, 50 GB, 100 iterations, 100 ms per 128 MB block. (a) MapReduce I/O cost (b) Spark cost (c) compare (d) recovery when an executor crashes. (Teacher seed)

(a) 51,200 MB ÷ 128 = 400 blocks, so one pass takes 40 s. Every iteration reads and writes HDFS because MapReduce keeps no memory between jobs. One iteration = 80 s. 100 × 80 = 8,000 s ≈ 2.2 h, with 10 TB of disk I/O.

(b) Spark reads the disk once (40 s). Then it caches the points as an RDD, so the other 99 iterations read RAM. Assume RAM is 10× faster: 99 × 400 × 10 ms = 396 s. Total ≈ 436 s ≈ 7.3 min, with only 50 GB of disk I/O.

(c) Spark does 200× less disk I/O and takes about 18× less time. MapReduce pays the disk cost 100 times. Spark pays it once.

(d) The Driver sees missed heartbeats and marks that executor's tasks as failed. It follows the lineage. It recomputes only the lost partitions from HDFS on healthy executors. Wide dependencies cost more to recover, so checkpoint long chains.

2. ★ Same K-Means with HDFS 500 MB/s and RAM 5,000 MB/s: (a) MR I/O (b) Spark I/O (c) wall-clock (d) when Spark does not win. (A1)

(a)(b) MapReduce reads and writes 50 GB in each iteration: 100 × (50 + 50) = 10 TB. Spark reads 50 GB once and caches it. That is 200× less disk I/O.

(c) MapReduce: 10,000,000 MB ÷ 500 = 20,000 s ≈ 5.6 h. Spark: 100 s (disk) + 99 × 10 s (RAM) = 1,090 s ≈ 18 min. Spark is about 18× faster because 99 passes come from memory.

(d) Spark gains little in these cases: single-pass jobs (2–5×, no reuse), data larger than RAM, too little executor memory, or shuffle-bound jobs.

3. ★ input → filteredRDD → mappedRDD → reducedRDD, 10 partitions. The executor holding partitions 3 and 7 crashes. (a) detection (b) what is recomputed (c) worst case with groupByKey. (A2)

(a) The executor stops sending heartbeats. The Driver marks it lost. It records partitions 3 and 7 and the executor's shuffle files as gone. The DAG scheduler reads the lineage.

(b) The chain is narrow, so Spark rebuilds only partitions 3 and 7 of input, filteredRDD and mappedRDD. That is 2/10 = 20% of the work. With groupByKey, reduced partition 3 needs keys from all 10 mappedRDD partitions.

(c) Suppose the lost map outputs covered all 10 partitions. Then Spark re-reads all input and redoes filter, map and the whole shuffle. That is almost the whole job for 20% of the output. Recovery cost depends on fan-in, so checkpoint after the shuffle.

4. ★ [New] Fraud pipeline on 8 partitions: textFile → map(parse) → filter → map((sender,1)) → reduceByKey → filter → count(). (a) transformations vs action (b) stages (c) partition for hash 1,234,567 (d) recovery of a lost parsed partition. (Mock paper A)

(a)(b) Only count() is an action. The rest are lazy transformations, so work starts at count(). reduceByKey is wide because it needs a shuffle. So there are 2 stages, with the boundary at the shuffle.

(c) 1,234,567 % 8 = 7.

(d) Spark re-reads that HDFS block and re-applies map(parse). A narrow step has one parent. After reduceByKey, each partition needs all 8 parents, so a loss there costs much more.

5. ★ Case study (Part 2): Spark's rise, GraySort and the five lessons. (Discussion)

(a) Multiplier, not panacea. Memory helps only when data is reused. Iterative jobs get 10–100× (132× for logistic regression). Single-pass ETL bigger than RAM gets only 2–5×.

(b) Lineage beats 3× replication. Replication always costs storage, RAM and network. Lineage stores a small recipe. It costs something only when a failure happens, and failures are rare.

(c) Shuffle is the bottleneck. GraySort (100 TB, 23 min, 206 nodes) won through a sort-based shuffle and SSDs, not caching. Tune with reduceByKey and fewer wide steps.

(d) Benchmark marketing. GraySort hid JVM issues (many small files, high-cardinality groupBy). Open source: Databricks sells cloud and support, so it improves free Spark.

6. [New] groupByKey on 1 billion records, 500 keys: two skew cases that cause OOM, and a fix for each. (Lecturer textbook)

(a) On average a key has 2 M records. A hot key (30% = 300 M) sends all its values to one task, and that task runs out of memory. Fix: use reduceByKey/aggregateByKey, or salt the key and group in two phases.

(b) Hash collisions: several heavy keys land in the same partition (hashCode % n). Fix: use a custom partitioner or more partitions.

7. [New] Logistic regression, 50 GB, 10 nodes × 32 GB. (a) MEMORY_ONLY? (b) which StorageLevel? (c) when does caching pay (130× speedup)? (Old slides)

(a) 320 GB holds 50 GB of raw data. But Java objects are 2–5× bigger. Partitions that overflow are evicted and recomputed in every iteration.

(b) MEMORY_AND_DISK (or MEMORY_ONLY_SER).

(c) n = 2 + (n − 1)/130 → n ≈ 2.01. So caching pays from the 3rd iteration. Cache any data that is reused more than twice.

Numericals

1. ★ GraySort: Hadoop took 72 min on 2,100 nodes. Spark took 23 min on 206 nodes. What is the per-node efficiency?

efficiency = (T_old × N_old) ÷ (T_new × N_new)

  1. Speed: 72 ÷ 23 = 3.1×. Nodes: 2,100 ÷ 206 = 10.2×.
  2. 151,200 ÷ 4,738 → ≈ 32×.

Meaning: each Spark node did about 32 times the work of a Hadoop node.

speedup = T_old ÷ T_new

  1. 127 ÷ 0.96 = 132×.
  2. 1,270 s vs 9.6 s.

K-means: 150 ÷ 5 = 30×.

Meaning: caching turns minutes of iterations into seconds.

3. ★ [New] Check the claim "10 iterations over 100 GB at 100 MB/s ≈ 3 hours". (Mock B)

  1. Reads: 1,000,000 MB ÷ 100 = 10,000 s ≈ 2.8 h ≈ 3 h.
  2. With writes: 5.6 h.

Meaning: the claim counts only reads. Disk cost alone makes MapReduce slow.

4. ★ [New] Word count: 6 partitions × 2,000 (word,1) pairs, 40 distinct words. How many records are shuffled? (Mock final)

  1. groupByKey: 6 × 2,000 = 12,000.
  2. reduceByKey: 6 × 40 = 240.
  3. That is 98% fewer.

Meaning: the local combine is why reduceByKey is preferred.

5. [New] Lineage vs 3× replication: 10 iterations of 60 s, replication adds 20% (assumed). When does lineage lose?

  1. Replication: 12 s × 10 = 120 s per job, always.
  2. A narrow loss costs ≈ 6 s, so break-even is 20 failures.
  3. A wide loss without a checkpoint costs ≈ 300 s, so break-even is 0.4 failures per job.

Meaning: lineage wins for narrow chains. It loses on wide chains unless you checkpoint.

Week 7 — Hive, HiveQL and SQL-on-Hadoop

Short questions (2 marks)

1. ★ Where does Hive store table schema metadata (columns, types, partitions)?

Hive stores it in the Hive Metastore. The Metastore is a relational DB (MySQL/PostgreSQL). It is not the NameNode. The NameNode holds only HDFS file and block metadata.

2. ★ What does "schema-on-read" mean in Hive?

Hive applies the schema when you query the data, not when you store it. This works because Hive copies files raw to HDFS. The user still writes CREATE TABLE. Schema-on-read is not schema inference.

3. ★ Which technique stores data in HDFS sub-directories by column value to avoid full scans?

Partitioning. A WHERE on that column opens only the matching folders. Bucketing is different. It splits files inside a partition by hash, and it skips no directories.

4. ★ What is Presto's main speed advantage over Hive+MapReduce?

Presto runs in memory and writes no intermediate data to disk. Hive+MR writes to HDFS between every stage. The result is minutes for Hive+MR and seconds for Presto.

5. True or false: HiveQL supports full ACID on all table types, like MySQL? Why?

False. ACID (UPDATE/DELETE) works only on transactional ORC tables.

6. True or false: partitioning cuts query time by skipping irrelevant partitions? Why?

True. A WHERE on the partition key reads only the matching sub-directories. This is called partition pruning.

7. True or false: Hive executes HiveQL directly on HDFS with no translation? Why?

False. The Driver parses, plans and optimises the query. It then compiles it into MR, Tez or Spark jobs that run on YARN.

8. True or false: bucketing is especially useful for joining two large tables? Why?

True. Both tables use the same join key and the same bucket count. Hive can then join bucket i with bucket i (bucket map join). So there is no full shuffle.

9. ★ [New] Why can HiveQL not replace MySQL for quick queries?

Every HiveQL query becomes batch jobs. These take minutes, not milliseconds. For example, COUNT(*) on 1 TB takes 5–10 min on MapReduce.

10. [New] True or false: Presto is 10× faster, so move the 50 TB nightly ETL to it? Why?

False. Presto restarts the whole job if it outgrows RAM or loses a worker. Hive retries only the failed tasks. So Hive suits big ETL.

11. ★ [New] What problem did Hive solve?

Before Hive, a query was a Java MapReduce program of 100+ lines. Writing one took days. Hive (Facebook, 2008) lets analysts write SQL instead.

12. ★ [New] Why run the Metastore as a highly available service?

If the Metastore fails, no table can be queried. The HDFS data stays intact, but Hive cannot use it.

13. ★ [New] Moving to Presto, must the team redefine its tables?

No. Presto reads the same Hive Metastore. So the tables work as they are.

Differences

Schema-on-write vs schema-on-read ★

Schema-on-write: the schema is checked at INSERT. Bad rows are rejected.

Schema-on-read: data is copied raw. The schema is applied at SELECT. Bad values become NULL.

SQL (RDBMS) vs HiveQL ★

RDBMS: full ACID, indexes, milliseconds.

HiveQL: batch jobs, limited ACID, partitions/buckets instead of indexes, minutes.

Partitioning vs bucketing

Partitioning: one directory per low-cardinality value. It prunes on WHERE.

Bucketing: N files by hash(col) % N. It helps joins.

Hive+MR vs Presto

Hive+MR: writes intermediate results to HDFS (5–15 min).

Presto: pipelines data in memory (5–60 s, "10×").

MapReduce vs Tez

MapReduce: a chain of jobs, with HDFS writes between them.

Tez: one DAG with no HDFS writes. Same answer, lower latency.

Metastore vs NameNode

Metastore: table schemas, partitions, SerDe.

NameNode: file and block locations only.

Static vs dynamic partition insert

Static: the statement names the partition value.

Dynamic: Hive takes the value from the last SELECT columns. It fills many partitions at once.

Hive vs Spark SQL

Hive: batch jobs (minutes).

Spark SQL: Catalyst, in memory (seconds). Both share the Metastore.

Partition pruning vs predicate pushdown

Partition pruning: skips directories.

Predicate pushdown: skips ORC/Parquet row groups using min/max stats. The two stack.

1. ★ Explain the Hive architecture (HiveServer2, Driver, Metastore) and query compilation. Draw it. (D1)

2. ★ Differentiate partitioning and bucketing; when to use each; a Bangladesh e-commerce example. (D2)

Partitioning makes one sub-directory per value of a low-cardinality column (date, division). A filter on that column reads only the matching folders. Use it for columns that appear in WHERE.

Bucketing splits each partition into N files by hash(col) % N on a join key. Two tables may use the same key and the same N. Hive then joins bucket i with bucket i (bucket map join). Use it for big joins.

Never partition on user_id. Millions of folders cause partition explosion.

Example: Daraz orders use PARTITIONED BY (order_date) for daily reports and CLUSTERED BY (customer_id) INTO 32 BUCKETS. This matches a 32-bucket customers table.

Exam line: partition to skip, bucket to join.

3. ★ What is schema-on-read? Pros and cons vs schema-on-write; one data-quality example. (D3)

In schema-on-read, files are copied raw to HDFS. Hive applies the Metastore's schema at query time.

Pros: loading is fast (a plain copy). There is no ingest ETL. Data can land before the schema is final.

Cons: every query must parse the data, so queries are slower. Errors are silent.

Schema-on-write (MySQL) rejects bad rows at INSERT. Data is clean and queries are fast, but the design is rigid.

Example: a bKash log has "abc" in amount. Hive returns NULL. So SUM(amount) silently under-reports.

Exam line: Hive writes fast and reads slow. MySQL writes slow and reads fast.

Short questions (2 marks)

1. ★ Which tool moves data in bulk between an RDBMS (e.g. MySQL) and HDFS? (Q1)

Apache Sqoop (SQL-to-Hadoop). It is built for bulk table import and export. Flume collects logs. Kafka streams events.

2. ★ Kafka's data model is based on which storage abstraction? (Q2)

An append-only, immutable, distributed log (partitioned topics). New messages are only added at the end. Old messages stay readable and replayable.

3. ★ Which Lambda layer gives real-time, low-latency views? (Q3)

The Speed Layer. Its views cover data since the last batch and are seconds old. The Serving Layer only merges and serves views. It does not process data.

4. ★ How does Kappa differ from Lambda? (Q4)

Kappa removes the batch layer. It uses Kafka log replay for all reprocessing. So the team writes and maintains only one stream code path.

5. ★ True or false: Sqoop is designed for real-time streaming ingestion from transactional systems? Why? (T/F 1)

False. Sqoop is a batch tool. It runs MapReduce jobs on a schedule (e.g. nightly). Kafka handles real-time ingestion.

6. True or false: Kafka keeps messages for a set period, so consumers can replay from any past offset? Why? (T/F 2)

True. Kafka keeps the log for the retention period (e.g. 7 days). Each consumer controls its own offset. So a consumer can move its offset back and re-read.

7. ★ True or false: Lambda needs two separate code paths for the same logic? Why? (T/F 3)

True. The team writes the logic once for batch (Spark/Hive). It writes the same logic again for streaming (Flink/Spark Streaming). Both versions must stay in sync.

8. True or false: Flume is the preferred tool for collecting server logs into HDFS? Why? (T/F 4)

True. Flume agents run Source → Channel → Sink. They are built for continuous log collection. The channel buffers events between the web servers and HDFS.

9. [New] What happens to a message after it is read: queue vs Kafka?

A queue deletes the message. A late consumer misses it. Kafka keeps the message until retention ends. A late consumer starts at offset 0 and replays.

10. ★ [New] How do the fraud, balance and audit services each get every event?

Each service is its own consumer group with its own offsets. Inside one group, each partition goes to exactly one consumer.

11. [New] Why key GPS pings (or card swipes) by driver_id / card number?

The same key always goes to the same partition: hash(key) mod P. So one driver's events stay in order. Kafka guarantees order only within a partition.

12. [New] A Flume HDFS sink rolls a new file every 10 s. What goes wrong? Fix?

86,400 ÷ 10 = 8,640 small files per day. They fill NameNode memory and create tiny map tasks. Fix: roll every 300–600 s or at 128 MB, or compact the files nightly.

13. [New] Live exercise: what do an offset reset and a new group ID show?

seek_to_beginning re-reads all 1,000 events and gives identical counts (idempotent). A new group has no committed offset. So with earliest it starts at offset 0.

Descriptive (4 marks)

1. ★ Explain Lambda with a diagram. What are the three layers? What is its main disadvantage vs Kappa? (D1)

Lambda (Nathan Marz, 2011) serves accurate views and real-time views from the same immutable raw data. All new data goes to both layers at once.

  • Batch layer: keeps the full master dataset on HDFS. Spark/Hive jobs recompute batch views every hour or every night. The views are accurate but 1–24 h old.
  • Speed layer: Kafka + Flink/Spark Streaming process only the data since the last batch run. This gives real-time views that are seconds old and approximate.
  • Serving layer: answers a query as batch view + real-time view.
  • Disadvantage: dual code paths. The team writes the same logic twice and keeps both in sync (30–40% of engineering effort). It also runs two clusters.

Exam sentence: Lambda = batch + speed + serving. Its weakness is dual code paths.

2. ★ How does Kafka get high throughput and fault tolerance? Give the roles of topic, partition, offset, broker and replication factor. (D2)

  • Topic: a named log for one event type (e.g. bkash-txns).
  • Partition: an ordered slice of a topic. Partitions allow parallel reads and writes.
  • Offset: a message's position. Each consumer tracks its own offset.
  • Broker: a server that stores partitions on disk.
  • Replication factor R: 1 leader + R − 1 followers on other brokers.

Throughput: sequential append-only writes (600 MB/s vs < 1 MB/s for random writes). Zero-copy sendfile() cuts 4 copies to 2. Kafka also batches messages, and partition parallelism scales linearly.

Fault tolerance: if a broker dies, ZooKeeper/KRaft elects a follower as the new leader. So no data is lost. The log is durable on disk, and offsets let consumers resume.

Exam sentence: Kafka is a distributed, partitioned, replicated commit log.

3. ★ What is a data lake? Compare lake vs warehouse (schema, format, use). What is a data swamp, and how is it prevented? (D3)

A data lake stores raw data of any format at any scale. It needs no upfront schema.

A warehouse uses schema-on-write: data must fit the tables before loading. It holds clean relational tables and serves BI reports.

A lake uses schema-on-read: structure is applied at query time. It holds raw CSV, JSON, Parquet, logs and images on HDFS/S3. It serves data science and ML.

A data swamp is a lake without governance. It has no catalogue, unknown owners, duplicate versions, and PII mixed in. Prevent it with a catalogue at ingest, owners, access control, quality checks and ACID formats (Iceberg/Delta Lake).

Exam sentence: a lake without governance becomes a swamp.

Descriptive (4 marks)

1. ★ Explain the data-ink ratio with a before-and-after bar chart. (D1)

Tufte says: maximise data ink ÷ total ink. Data ink encodes values (bar heights, lines). All other ink is a candidate for deletion. The test: "if erasing it loses no information, erase it."

  • Before: 3-D bars, gradient fill, heavy gridlines, a thick border, a shouting title, and a legend for only one series. The 3-D effect even distorts the heights.
  • After: flat one-colour bars that start from zero. No grid (or one light reference line). No border or legend. A thin axis and a plain title.

Exam sentence: same data, less ink, clearer message.

2. ★ What is overplotting? Give three fixes and what each preserves. (D2)

Millions of points stack into a solid blob. An area with 10 points and an area with 10,000 look equally black. Density, shape and outliers are lost. Fixes:

  • Alpha transparency (α = 0.02): preserves relative density. It fails at very high density.
  • Hexbin: preserves counts per region (10 M points → ~10,000 cells).
  • KDE 2-D contours: preserve shape, modes and tails.

Exam sentence: overplotting hides density, so show transparency, counts or contours instead.

3. ★ What is a data cube, how does it give sub-second latency, and what is the trade-off? (D3)

A data cube is a set of pre-computed aggregate tables for dimension combinations (district × date × product × channel). Hive over 100 B rows takes minutes. A nightly Spark/Hive job builds a cube of millions of rows. Tableau/Superset query that cube in under 1 s.

Trade-off: staleness (up to 24 h, because the cube is rebuilt nightly), extra storage, and filters only on pre-chosen dimensions.

Exam sentence: a data cube trades freshness for speed.

Short questions (2 marks)

1. ★ What is Facebook's Prophet library designed for? (Q1)

Time series forecasting. It splits the series into trend, seasonality and holiday parts: y(t) = g(t) + s(t) + h(t) + ε(t).

2. ★ Which algorithm is most used for community detection in large social graphs? (Q2)

Louvain. It greedily maximises modularity in about O(n log n), so it scales to huge graphs. PageRank measures importance. K-Means clusters vectors. ARIMA is for time series.

3. ★ What does HIPAA regulate? (Q3)

The privacy and security of healthcare data (patient records, medical information) in the USA. Financial data falls under GLBA, not HIPAA.

4. ★ What did DeepMind's AlphaFold solve? (Q4)

Protein structure prediction. It predicts the 3D shape of a protein from its amino-acid sequence. It was trained on 170,000 PDB structures and won the Nobel Prize in 2024.

5. ★ True or false: Google Flu Trends successfully replaced CDC surveillance? Why? (TF1)

False. GFT over-predicted flu by 2× in 2012–13, and Google dropped it. Syndromic signals supplement clinical reporting. They do not replace it.

6. ★ True or false: shuffling a time series changes the analysis result? Why? (TF2)

True. The values are autocorrelated and carry trend and seasonality. Shuffling destroys this temporal signal.

7. ★ True or false: social network graphs are typically sparse? Why? (TF3)

True. Each user links to a few hundred users out of millions. Kwak's Twitter graph has a density of about 8.5 × 10−7.

8. ★ True or false: MRI and CT scans are structured because they are stored in files? Why? (TF4)

False. They are unstructured binary DICOM files. Deep learning (CNN) analyses them, not SQL.

9. ★ [New] Give the steps of the Louvain algorithm.

  1. Start with each node in its own community.
  2. Move each node to the neighbouring community that gives the biggest modularity gain.
  3. Collapse each community into a super-node.
  4. Repeat until modularity stops rising.

10. ★ [New] Why VADER for social text? Classify compounds 0.31, −0.02, −0.47.

VADER is a lexicon-and-rule tool tuned for social media. It handles CAPS, "!!!", "very", negation and emojis. It needs no training. The rule uses ±0.05: 0.31 is positive, −0.02 is neutral and −0.47 is negative.

11. ★ [New] Why did Google Flu Trends fail?

  • Big data hubris: r² = 0.97 in training did not generalise.
  • Algorithm confounding: Google's autocomplete changes altered searches.
  • Media amplification: flu news drove searches.

12. ★ [New] Why is Twitter called a news medium, not a social network?

Only 22.1% reciprocity: most follows are one-way. Followers follow a power law, with a few huge hubs. 85% of trending topics are headline news (Kwak 2010).

13. ★ [New] How does Isolation Forest find anomalies?

It builds random trees that split the data. Anomalies are isolated in fewer splits. So they have a shorter average path length.

14. Live exercise: why weekly_seasonality=False, and what does changepoint_prior_scale 0.05 → 0.5 change?

The data has one point per week. So there is no day-of-week pattern to learn. At 0.5 the trend bends more and chases noise, and the future uncertainty band widens.

Differences

Louvain vs PageRank

Louvain: finds which group a node belongs to (modularity).

PageRank: scores how important a node is.

ARIMA vs Prophet

ARIMA: needs a stationary series, hand-tuned (p, d, q) and handles one seasonality.

Prophet: fits trend automatically, handles several seasonalities and holidays, and scales to thousands of series.

Prophet vs LSTM

Prophet: interpretable and needs little data.

LSTM: a black box that needs lots of data and GPUs.

Twitter vs Facebook

Twitter: directed, 22.1% mutual, a news medium.

Facebook: mutual friendship (≈100%), a social network.

STL vs Isolation Forest

STL: splits the series into trend, season and residual, and flags a residual > k × IQR.

Isolation Forest: flags points that few random splits isolate.

ILINet vs syndromic surveillance

ILINet: confirmed physician reports. Accurate but 1–2 weeks late.

Syndromic (tweets, pharmacy, ED): early but noisy proxies.

HIPAA vs GDPR

HIPAA: US health data only, 18 identifiers.

GDPR: EU, all personal data. Requires minimisation, purpose limitation and erasure.

Differential privacy vs federated learning

Differential privacy (DP): adds noise to published aggregates.

Federated learning (FL): trains at each hospital and shares only model weights.

Safe harbour vs expert determination

Safe harbour: removes the fixed 18 identifiers.

Expert determination: uses statistical analysis to prove a low re-identification risk.

Descriptive (4 marks)

1. ★ Describe three social media analyses and one ethical risk of each at scale. (D1)

(a) Community detection (Louvain, modularity) groups users who talk more to each other than to the rest. It reveals interest groups, political factions or bot networks. Risk: profiling religious minorities or dissenters for surveillance.

(b) Sentiment analysis (VADER compound, −1 to +1) scores each post with a Spark UDF. The scores are averaged by topic and time. Risk: a government flags negative posts to suppress dissent.

(c) Influence maximisation (Kempe greedy, (1 − 1/e) ≈ 63% guarantee, NP-hard) picks the k seed users who spread news furthest. Risk: microtargeting vulnerable users with ads or misinformation.

Mitigation: transparency and purpose limitation.

2. ★ ARIMA vs Prophet: when prefer Prophet, when is ARIMA still better? (D2)

ARIMA(p, d, q) predicts today from the last p values (AR). It differences the series d times to make it stationary (I). It corrects with the last q errors (MA). An expert must choose p, d and q.

Prophet adds simple pieces, g + s + h + ε: a trend that bends at changepoints, Fourier seasonality and a holiday list. Stan fits the model.

Prefer Prophet for many series (nobody can hand-tune 10,000), multiple seasonalities, holidays (Eid), missing data, outliers and interpretability.

ARIMA still wins on short, stationary, non-seasonal, small datasets. There its few parameters fit well.

Exam sentence: Prophet scales and explains; ARIMA suits small stationary series.

3. ★ Three healthcare integration and privacy challenges, each with a mitigation. (D3)

(a) Re-identification when linking EHR, genomics and wearables. Joined records expose names, NID and phone numbers. Mitigation: de-identification (safe harbour removes the 18 HIPAA identifiers; pseudonymous linking keys).

(b) Data silos across hospitals in different formats. Law and consent stop raw records leaving (PDPA Bangladesh requires consent for NID-linked data). Mitigation: federated learning, which trains at each hospital and shares only weights.

(c) Leaks from small aggregate counts. "2 deaths in one upazila" can reveal a person. Mitigation: differential privacy (calibrated noise on totals).

Exam sentence: linkage → de-identification; silos → federated learning; aggregates → differential privacy.

4. ★ A Prophet model of weekly admissions misses a sudden COVID wave. Which component should catch it, and which hyperparameter controls it? (Discussion Q2)

The trend g(t) must catch it. The trend is piecewise linear and changes slope at changepoints. Seasonality only repeats known yearly and weekly cycles, so it cannot explain a new wave.

Prophet puts a sparse prior on the slope changes. This keeps most changes near 0 and avoids overfitting. changepoint_prior_scale (default 0.05) sets the width of that prior.

At 0.05 the trend is stiff, and the model treats the sudden rise as noise. Raising it to 0.5 lets the trend bend fast, but risks overfitting.

Exam sentence: trend g(t) detects it; changepoint_prior_scale controls sensitivity.
