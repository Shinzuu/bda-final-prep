(c) Caches intermediate data as RDDs in memory. Each iteration reads from RAM instead of re-reading HDFS. The hardware is the same, so (a) is wrong. Spark still shuffles, so (d) is wrong.

Pool · Plan · MCQQ6.2 Q2. How does Spark achieve fault tolerance in RDDs without full data replication? (a) Checkpointing to HDFS every 60 seconds (b) Tracking lineage and recomputing lost partitions from parent RDDs (c) Copying each RDD partition twice across two Executors (d) Using a write-ahead log on the Driver node

(b) Lineage + recomputation. Each RDD records the transformations that built it, so a lost partition is recomputed from its parents. (c) describes HDFS-style replication. (a) is periodic checkpointing, which is optional in Spark.

(d) HBase. It is a separate NoSQL database running on HDFS (Week 4). Spark can read from it, but it is not part of the Spark stack (Core, SQL, Streaming, MLlib, GraphX).

In Spark, a transformation such as map() or filter() is: (a) Immediately executed when called and materialised to memory (b) Lazily evaluated, only executed when a subsequent action is called (c) Automatically persisted to HDFS after execution (d) Only available in the Scala API, not in PySpark

(b) Lazily evaluated. A transformation only adds a step to the DAG, and nothing runs until an action (count, collect, save) is called. rdd.filter(...) alone does nothing; rdd.filter(...).count() runs the job.

True. A DataFrame is a distributed table with a schema (named, typed columns) that the Catalyst optimiser can plan like SQL.

False. For iterative ML, Spark is 10 to 100× faster because it caches the training data in memory, while MapReduce re-reads HDFS every iteration.

Pool · DescriptiveQ6.9 D1. Explain the concept of a Resilient Distributed Dataset (RDD). What does "resilient" mean in this context? How does Spark recover a lost RDD partition without replication?

An RDD is an immutable, partitioned collection of records spread across the executors of a cluster. It is built only by deterministic transformations on stable storage or on other RDDs, and it can be cached in memory. Resilient means it is fault-tolerant: when a partition is lost, Spark can rebuild it automatically. Each RDD keeps its lineage, the graph of parent RDDs and the functions applied to them. When an executor dies, the scheduler reruns that function chain only for the lost partitions, starting from the source data or the nearest cached or checkpointed parent. No replica copies are needed.

Pool · DescriptiveQ6.10 D2. Differentiate between Spark transformations and actions. Give two concrete examples of each. Why does Spark not execute transformations immediately?
  • Transformations build a new RDD or DataFrame from an existing one and are lazy: they only record a step in the DAG. Examples: map(), filter() (also reduceByKey, join).
  • Actions trigger execution and return a result to the driver or write output. Examples: count(), collect() (also take, saveAsTextFile).
  • Why lazy: when Spark sees the whole chain, it can pipeline narrow operations into one pass, split stages only at shuffles, push filters down, and skip work the action never needs. It also avoids materialising intermediate results that nothing uses.
Pool · DescriptiveQ6.11 D3. Describe Spark's lazy evaluation model. What is the advantage of deferring computation until an action is called? Use the example rdd.filter(x > 1000).first() to illustrate.

Under lazy evaluation, transformations are only recorded as a logical plan (DAG). When an action is called, the DAGScheduler builds stages and runs them. The advantage is that Spark optimises the whole pipeline: it fuses operations, does less I/O and stops early. In rdd.filter(x > 1000).first(), filter computes nothing on its own. first() then launches a job that scans the first partition, filters as it streams, and stops at the first match. It scans more partitions only if none match. An eager engine would filter the entire dataset and materialise the result just to return one element.

Pool · Plan · AnalyticalQ6.12 A1. Iterative I/O Cost Analysis: train K-Means on 50 GB of bKash transaction data for 100 iterations. HDFS read = 500 MB/s; RAM cache read = 5,000 MB/s. (a) Total HDFS I/O for MapReduce (all 100 iterations). (b) Total I/O for Spark (50 GB fits in cluster RAM). (c) Wall-clock time for each. (d) When would Spark NOT outperform MapReduce? [Plan seed version: same job, assuming 100 ms per 128 MB block.]

MapReduce I/O = iterations × (D read + D written) on HDFS. Spark = 1 HDFS read + (iterations − 1) RAM reads. 1 GB = 1,000 MB (assumed).

  1. (a) MR: 100 × (50 GB read + 50 GB written) = 10,000 GB (10 TB) of HDFS I/O.
  2. (b) Spark: 50 GB from HDFS once, plus 99 × 50 = 4,950 GB from the RAM cache.
  3. (c) MR: 100,000 MB / 500 MB/s = 200 s per iteration, × 100 = 20,000 s ≈ 5.6 h. Spark: 100 s + 99 × (50,000 / 5,000 = 10 s) = 100 + 990 = 1,090 s ≈ 18.2 min. Speedup ≈ 18×.
  4. Plan seed version: 50 GB / 128 MB = 400 blocks. MR: 400 × 100 ms × 100 iterations = 4,000 s ≈ 66.7 min. Spark: one read, 400 × 0.1 = 40 s, with cached passes treated as near zero. That gives ≈100× less I/O time.

Meaning: once the data is cached, every later iteration is about 10× cheaper, so total I/O falls by roughly the iteration count.

(d) Spark does not win when the data does not fit in memory (it spills or recomputes). It does not win for single-pass ETL with no reuse, under heavy GC or memory pressure, for very small jobs where startup dominates, or when the job is shuffle- or network-bound rather than read-bound.

Pool · Plan · AnalyticalQ6.13 A2. RDD Failure Recovery Trace: a job computes input → filteredRDD → mappedRDD → reducedRDD over 10 partitions. Mid-execution, the Executor holding partitions 3 and 7 of reducedRDD crashes. Trace the complete recovery: what does the Driver detect, which partitions of which RDDs need to be recomputed, and what is the worst-case recovery cost if reducedRDD involves a wide dependency (groupByKey)?
  1. Detect: the driver stops receiving the executor's heartbeats (or gets a lost-executor event from the cluster manager). It marks the executor dead, the BlockManagerMaster drops its cached blocks, and its running tasks fail.
  2. Lineage lookup: the DAGScheduler sees that reducedRDD partitions 3 and 7 are missing and walks the lineage back.
  3. Narrow case: each partition depends on one parent partition, so only partitions 3 and 7 of filteredRDD, mappedRDD and reducedRDD are rebuilt from input splits 3 and 7. That is 2 tasks, pipelined, on other executors.
  4. Wide case (groupByKey): each reduced partition depends on all 10 mappedRDD partitions through the shuffle. If the shuffle map outputs are still on healthy executors (or an external shuffle service), only 2 reduce tasks re-run and fetch their shuffle blocks. Map outputs that lived on the dead executor cause a FetchFailed, and the parent shuffle-map stage re-runs for those map partitions.
  5. Worst case: all map outputs are lost or unreadable, so all 10 input → filtered → mapped partitions are recomputed and reshuffled, and then the 2 reduce partitions run. That is 10 + 2 = 12 tasks, about a full re-run of the map stage plus a full shuffle, compared with 2 tasks in the narrow case.

Meaning: a wide dependency makes the recovery cost grow with the whole parent stage. Checkpoint or persist after expensive shuffles to limit it.

(b) If not, which StorageLevel would you choose and why? (c) Estimate how many iterations are needed before the cached speedup (130×) pays for the initial caching cost (1 extra HDFS read).

As deserialised Java objects (assumed 3 to 5× larger), it becomes 150 to 250 GB, which does not reliably fit at MEMORY_ONLY. Partitions that do not fit are dropped and recomputed every iteration.

(b) MEMORY_ONLY_SER (with Kryo), which stores the data at about its raw 50 GB size, or MEMORY_AND_DISK_SER so overflow partitions spill to local disk instead of being recomputed from HDFS. It costs some CPU for deserialisation and uses much less memory with no recompute.

(c) Let T = one HDFS pass. Uncached cost = n·T. Cached cost = 2T for the first iteration (read plus caching) + (n − 1)·T/130 for the rest.

  1. Break-even: n = 2 + (n − 1)/130.
  2. n = 259/129 ≈ 2.01.
  3. So caching pays off from the 3rd iteration.

Meaning: for any iterative job (logistic regression usually runs 10 to 100 iterations), caching always pays.

v1 deck · DiscussionQ6.16 A groupByKey on an RDD with 1 billion records and 500 distinct keys produces 500 shuffle partitions. Identify two data skew scenarios that would cause OOM errors and propose a fix for each.

The average is 109/500 = 2M records per key, and groupByKey holds all of a key's values in memory on one task.

  1. Hot key: one key (for example a NULL/"unknown" customer, or a top merchant) holds 40% of the data, which is 400M values in a single task's iterator, so that task runs OOM. Fix: use reduceByKey/aggregateByKey (map-side combine) instead of groupByKey, or salt the hot key (key_0 to key_N), aggregate, then merge. Filter NULL keys out and handle them separately.
  2. Hash collisions in partitioning: with 500 keys over 500 partitions, hash(key) mod 500 sends several large keys to the same partition while others stay empty, so a few tasks hold 2 to 3 keys' worth of data and run OOM. Fix: use a custom partitioner or range partitioner, or increase partitions (for example 2,000), or enable AQE skew handling (spark.sql.adaptive.skewJoin.enabled) to split oversized partitions.
v1 deck · DiscussionQ6.17 Compare RDD lineage fault tolerance with HDFS 3× replication for a 10-iteration ML job. Under what failure rate does lineage become slower than replication?
  • Replication: every iteration writes its result 3× to HDFS, a fixed cost w per iteration whether or not anything fails. Recovery is fast (re-read a replica).
  • Lineage: zero overhead when there are no failures. A failure at iteration i recomputes the lost fraction f of up to i iterations, so the cost grows with lineage length.

Lineage is slower when the expected recompute cost exceeds the replication cost: p·f·T·Σi > 10·w, with Σi = 1+2+…+10 = 55, so p > 10w / (55·f·T).

  1. Assume w = 0.5T (a 3× HDFS write costs about half an iteration) and a worst-case full recompute (f = 1, wide dependencies): p > 5/55 ≈ 0.09, about one failure every 11 iterations.
  2. With one of 10 executors lost per failure (f = 0.1): p > 0.91, which almost never happens.

Meaning: lineage wins unless failures are very frequent (roughly one or more per job with long, wide lineage). Checkpointing every few iterations caps the lineage length.

v1 deck · AnalyticalQ6.18 Stanford CS246 exam question: Given the following Spark DAG, identify all stage boundaries and estimate the total shuffle volume for a 1 TB input dataset with 1,000 partitions.

The question does not include the DAG. Use this method on the DAG you are given.

  1. Stage boundaries fall at every wide dependency (groupByKey, reduceByKey, join without co-partitioning, distinct, repartition, sortBy). Chains of narrow operations (map, filter, flatMap, union, mapPartitions) are pipelined into one stage. Number of stages = number of shuffles + 1.
  2. Partition size = 1 TB / 1,000 = 1 GB per partition, so each stage runs 1,000 tasks.
  3. Shuffle volume per wide operation = the size of the map-side output going into it. With no reduction (groupByKey or join right after reading), that is about 1 TB per shuffle. With reduceByKey, map-side combine shrinks it to roughly the number of distinct keys per partition × record size. Filters before the shuffle scale it by their selectivity.
  4. Total = sum over all shuffles. For example, map → filter (keeps 50%) → reduceByKey → join: about 0.5 TB plus the join's shuffle input. Each shuffle creates M × R = 1,000 × 1,000 = 106 shuffle blocks.

Book ch06 · ShortQ6.20 Define a Resilient Distributed Dataset. List its five defining properties and explain the purpose of each.

An RDD is an immutable, partitioned, fault-tolerant distributed collection, defined by five properties:

  1. List of partitions: the units of parallelism, one task per partition.
  2. Compute function for each partition: how to build a partition from its parents.
  3. List of dependencies on parent RDDs (narrow or wide): this is the lineage used for recovery and stage planning.
  4. Optional Partitioner for key-value RDDs (hash or range): it says which key goes to which partition, which avoids re-shuffles.
  5. Optional preferred locations per partition (for example HDFS block hosts): used for data-local scheduling.
Book ch06 · ShortQ6.21 What is lineage-based fault tolerance? Compare it with replication-based fault tolerance on two dimensions: memory overhead and recovery latency.

With lineage-based fault tolerance, Spark logs the coarse-grained transformations that produced each RDD and recomputes lost partitions from them, instead of storing copies of the data.

  • Memory overhead: lineage stores only a small DAG of operations, so it is near zero. Replication stores r full copies (3× memory or disk) and costs network bandwidth on every write.
  • Recovery latency: replication is fast (read the surviving copy). Lineage has to recompute, which is slower and grows with lineage length and wide dependencies, but it only touches the lost partitions and runs in parallel. Checkpointing limits the worst case.
Book ch06 · ShortQ6.22 Explain the concept of lazy evaluation in Spark. What is the performance benefit of deferring computation until an action is called?

Transformations only record a step in the DAG; nothing runs until an action (count, collect, write) asks for a result. Because the whole plan is known before execution, Spark can pipeline narrow operations into one pass over the data with no intermediate materialisation, split stages only at shuffles, push filters and projections down (Catalyst), and skip unneeded work (for example take(1) scans only one partition). The result is less I/O, memory and network traffic.

Book ch06 · ShortQ6.23 Distinguish narrow transformations from wide transformations. Give two examples of each, and explain why wide transformations create stage boundaries in the DAG.

In a narrow transformation, each parent partition feeds at most one child partition: map, filter (also flatMap, union). In a wide transformation, a child partition needs data from many parent partitions: groupByKey, reduceByKey (also join, distinct). A wide transformation needs a shuffle: all map-side tasks must finish and write shuffle files before any reduce task can start. That synchronisation point cannot be pipelined, so the DAGScheduler cuts a new stage there. Narrow chains run within one stage, partition by partition.

Book ch06 · ShortQ6.24 Why is reduceByKey almost always preferable to groupByKey for aggregation? Give a numerical example of network traffic for 1 billion records, 200 partitions, where 30% of records share the same key.

reduceByKey applies the function map-side (a combiner) before the shuffle, so only partial results cross the network. groupByKey ships every record and builds full value lists on the reducer.

  1. Hot key: 30% × 109 = 300M records, spread over 200 partitions.
  2. groupByKey: shuffles all 109 records. At 100 B each (assumed) that is 100 GB, and one reducer receives all 300M hot-key values (30 GB), which can run out of memory (OOM).
  3. reduceByKey: the hot key becomes 200 partial sums (one per partition). The other 700M records are assumed to be mostly unique keys, so they do not combine. Total ≈ 700M + 200 records ≈ 70 GB, and the hot-key reducer gets 200 records instead of 300M.

Meaning: at least 30% less network traffic, and the skewed reducer goes from 300M values to 200. The saving is larger when other keys also repeat.

Book ch06 · ShortQ6.25 What is a YARN ApplicationMaster for a Spark job? Which component of Spark architecture runs inside the AM container, and what does it do?

For a Spark-on-YARN job the AM is Spark's per-application YARN process. It negotiates executor containers from the ResourceManager (including dynamic allocation) and asks NodeManagers to launch them. In cluster mode the Spark Driver (SparkContext) runs inside the AM container. It builds the DAG, splits it into stages and tasks (DAGScheduler, TaskScheduler), sends tasks to executors, tracks block locations and lineage, and collects results. In client mode the driver runs on the client machine, and the AM (ExecutorLauncher) only requests containers.

Book ch06 · ShortQ6.26 Explain the four phases of the Catalyst optimizer. Which phase chooses between a sort-merge join and a broadcast hash join, and what criterion determines the choice?
  1. Analysis: resolves table and column names and types against the catalog, turning an unresolved plan into a resolved logical plan.
  2. Logical optimisation: rule-based rewrites such as predicate pushdown, column pruning and constant folding.
  3. Physical planning: generates candidate physical plans and picks one using cost and size estimates.
  4. Code generation: Tungsten whole-stage codegen compiles the plan to JVM bytecode.

Physical planning picks the join: broadcast hash join if one side's estimated size is ≤ spark.sql.autoBroadcastJoinThreshold (default 10 MB) or a broadcast hint is given; otherwise sort-merge join. AQE can switch to a broadcast join at runtime from actual sizes.

Book ch06 · ShortQ6.27 What is the unified memory model in Spark? For an executor with 32 GB JVM heap, spark.memory.fraction = 0.6 and spark.memory.storageFraction = 0.5, calculate the available storage memory, execution memory and user memory.

In the unified memory model, execution (shuffles, joins, sorts) and storage (cache) share one pool, M = (heap − 300 MB reserved) × memory.fraction. Storage's protected share is M × storageFraction. Each side can borrow the other's free space, and execution can evict cached blocks down to the protected share.

  1. Usable = 32,768 − 300 = 32,468 MB.
  2. Unified M = 0.6 × 32,468 = 19,480.8 MB ≈ 19.02 GB.
  3. Storage = 0.5 × M ≈ 9.51 GB; execution ≈ 9.51 GB.
  4. User memory = 0.4 × 32,468 = 12,987 MB ≈ 12.68 GB.

Meaning: ignoring the 300 MB reserve, the round figures are 19.2 / 9.6 / 9.6 / 12.8 GB, and only about 60% of the heap is available to Spark.

Book ch06 · ShortQ6.28 What is Tungsten whole-stage code generation? How does it differ from the interpreted, row-at-a-time Volcano model used by traditional query engines?

Whole-stage codegen fuses all operators in a stage (scan, filter, project, aggregate) into one generated Java function with a tight loop. Values stay in CPU registers, and data uses Tungsten's off-heap binary rows. The Volcano model calls next() through a chain of operator objects once per row per operator, which costs virtual function calls, object allocation and poor cache use. Codegen removes that per-row interpretation overhead and runs close to hand-written code, often several times faster on CPU-bound queries.

Book ch06 · ShortQ6.29 Explain the Spark MLlib abstraction of Transformer vs. Estimator. Give one concrete example of each and explain what fit(df) produces for an Estimator.

A Transformer has transform(df), which maps one DataFrame to another by appending columns. Example: VectorAssembler (or Tokenizer, or a trained model). An Estimator has fit(df), which learns parameters from data. Example: LogisticRegression (or StringIndexer, StandardScaler). fit(df) returns a Model, which is itself a Transformer. For example, a LogisticRegressionModel's transform() adds prediction and probability columns. A Pipeline chains them, and fitting a Pipeline gives a PipelineModel.

Book ch06 · ShortQ6.30 What is data skew in a Spark wide transformation? Describe the observable symptom in the Spark UI that indicates a skew problem.

Data skew means a few keys hold a disproportionate share of records, so after the shuffle a few partitions are far larger than the rest and their tasks run much longer, or spill or OOM. Symptom in the Spark UI (Stage page, task summary): max task duration and max shuffle read size/records are many times the median. Most tasks finish quickly while one or a few stragglers keep the stage running, often with large spill (memory/disk) or GC time on those tasks.

Book ch06 · ShortQ6.31 What does MEMORY_ONLY_SER mean as an RDD storage level? Under what circumstances should you choose it over MEMORY_ONLY?

MEMORY_ONLY_SER caches each partition as serialised bytes (one byte array per partition, ideally Kryo) in the JVM heap. Partitions that do not fit are recomputed, not spilled. Choose it over MEMORY_ONLY when the deserialised objects do not fit in memory (Java objects are often 2 to 5× larger), or when GC pressure from millions of small objects is high. It saves memory and GC time at the cost of extra CPU to deserialise on each access. (In PySpark, data is always stored serialised.)

Book ch06 · ShortQ6.32 Explain what a checkpoint does in Spark. When is checkpointing necessary, and what are its costs?

rdd.checkpoint() (after sc.setCheckpointDir) writes the RDD to reliable storage (HDFS) and truncates its lineage, so recovery restarts from the checkpoint. It is necessary for long lineages (iterative algorithms, GraphX) where recomputation or stack depth explodes, after expensive wide shuffles, and in stateful streaming (required for updateStateByKey and for recovering from driver failure). Costs: an extra job that writes the full data to HDFS (I/O, replication, storage space), plus a recompute unless the RDD is persisted first.

Book ch06 · ShortQ6.33 A Spark job with 8 stages takes 4 hours. The Spark UI shows Stage 3 ran for 3.5 hours, with 199 tasks completing in 2 minutes and one task running for 3.5 hours. What is the most likely cause, and how would you diagnose it?

The most likely cause is data skew in a shuffle (a hot key in a join, groupBy or reduceByKey) that sends a huge partition to one task. The 3.5 h task versus 2 min is about 105× the normal task (210/2), and it makes up 87.5% of the job time.

Diagnose: on the Stage 3 task table, compare the straggler's shuffle read size/records with the median, and check its spill and GC time. Then find the key with df.groupBy(key).count().orderBy(desc). A bad host is ruled out if a re-run or speculation shows the same task is slow again. Fix: salting, AQE skew join, a broadcast join, or filtering NULL keys.

Book ch06 · AnalyticalQ6.35 AP: Stage and Shuffle Analysis. A job reads a log from HDFS, parses each line into (session_id, page_url, duration_seconds), filters duration > 5 s, computes total duration per session, keeps sessions with total > 60 s, joins with a 200 MB session-metadata table (session_id, user_id, country), groups by country and writes to HDFS. (a) Draw the RDD lineage DAG. (b) Identify all stage boundaries and why. (c) Which narrow transformations pipeline into one task pass, and the I/O saving. (d) How Catalyst handles the 200 MB join and why it avoids a shuffle. (e) With 20 billion log records, spark.sql.shuffle.partitions = 200 and a 150-billion-record join output, is 200 appropriate and how would you set it?

(a)

HadoopRDD(textFile) -> map(parse) -> filter(dur > 5) -> map((sid, dur))
  => reduceByKey(sum)                [shuffle 1]
  -> filter(total > 60)
  -> join(meta)  [broadcast: no shuffle | else shuffle 2]
  -> map((country, total))
  => reduceByKey / groupBy(country)  [shuffle]
  -> saveAsTextFile(HDFS)

(b) Stage 1: read, parse, filter, map. It ends at reduceByKey per session, a wide dependency because all records of a session must meet. Stage 2: aggregate, filter > 60, join, map to country. (c) parse → filter → map in stage 1, and filter → (broadcast) join → map in stage 2, are each pipelined in one task: each record flows through all of them in memory with no intermediate write. (a) With memory.fraction = 0.6 and storageFraction = 0.5, storage and execution memory per executor. (b) With 40 executors, aggregate storage memory; does 180 GB fit? (c) With Kryo 3× compression, recheck. (d) If it still does not fit, two configuration changes with parameter names and values. (e) Performance consequence of MEMORY_AND_DISK instead of MEMORY_ONLY when it does not fit.

Unified M = (heap − 300 MB) × 0.6; storage = execution = 0.5 × M

  1. (a) (24,576 − 300) × 0.6 = 14,565.6 MB ≈ 14.22 GB. Storage ≈ 7.11 GB, execution ≈ 7.11 GB (7.2 / 7.2 GB ignoring the reserve).
  2. (b) 40 × 7.11 = 284.5 GB (288 GB rounded) of protected storage, and up to 40 × 14.22 ≈ 569 GB if storage borrows idle execution memory. 180 GB < 284.5 GB, so it fits.
  3. (c) 180 / 3 = 60 GB serialised, which is about 21% of storage memory. It fits easily and leaves room for execution.

Meaning: the cache fits with headroom. Only an object-expanded (deserialised) form would be at risk.

(d) If it did not fit: 1. raise spark.memory.fraction from 0.6 to 0.75 (more unified memory); 2. raise spark.memory.storageFraction to 0.7 (more protected cache); or 3. increase spark.executor.memory to 32g, or spark.executor.instances to 60.

With MEMORY_ONLY, those partitions would be recomputed from the source every pass, which is much worse.

Book ch06 · AnalyticalQ6.37 AP: Data Skew Diagnosis and Salting. Join a 5 TB transactions table (partitioned by store_id) with a 2 TB products table on product_id. Shares: IPHONE-15-PRO 28.3%, SAMSUNG-S24 11.7%, AIRPODS-PRO 6.2%, all other 4.2M products 53.8%. Total 50 billion records. (a) With 200 shuffle partitions, records for the IPHONE-15-PRO task vs the average task. (b) The average task runs 4 minutes: estimate stage latency with and without skew mitigation. (c) Design a salting strategy for the top-3 keys with salt factor 30; show a key before and after salting. (d) Explain the two-phase aggregation needed after salting and why. (e) How a skew join hint is handled differently from a standard sort-merge join.

Task time ∝ records per task (assumed)

  1. (a) Average = 50×109 / 200 = 250M records. IPHONE task = 0.283 × 50×109 = 14.15 billion records, which is 56.6× the average.
  2. (b) Without mitigation: 56.6 × 4 min = 226.4 min ≈ 3.8 h (SAMSUNG 23.4× = 93.6 min, AIRPODS 12.4× = 49.6 min). With salting (30): IPHONE shard = 14.15B / 30 = 471.7M = 1.89× average, so ≈ 7.5 min; SAMSUNG 195M and AIRPODS 103M are below average. Stage ≈ 7.5 min instead of 226 min, about 30× faster (no hash collisions between salted keys, assumed).

(c) Transactions side: if product_id is in {IPHONE-15-PRO, SAMSUNG-S24, AIRPODS-PRO}, the key becomes product_id + "_" + rand(0..29); other keys get _0. Products side: explode the 3 hot rows into 30 copies, _0 to _29 (other rows get _0). Example: (IPHONE-15-PRO, txn 98123, 1299) becomes (IPHONE-15-PRO_17, txn 98123, 1299), which joins with product row IPHONE-15-PRO_17. The hot key's data is now spread over 30 tasks.

(d) For aggregations: phase 1 aggregates by the salted key (30 partial results per hot key, computed in parallel); phase 2 strips the salt and aggregates again by the real key to merge the partials. It is necessary because salting splits one logical key across 30 groups; without phase 2 the results would be 30 partial rows per product instead of one correct total.

(e) A standard sort-merge join hash-partitions both sides by key, so the whole hot key lands in one task. With a skew hint or AQE skew join, the optimiser uses statistics to spot oversized partitions, splits the skewed partition into several sub-partitions, and replicates the matching partition of the other side to each one. The hot key is joined in parallel with no manual salting or query rewrite.

Book ch06 · ProgrammingQ6.40 PE: Word Frequency with the RDD API (PySpark). Read a text file from HDFS, tokenise (lowercase, strip punctuation), count each word, return the top 20 words; measure the performance difference between reduceByKey and groupByKey.
import re, time
tok = lambda l: [w for w in re.split(r"[^a-z]+", l.lower()) if w]
pairs = sc.textFile("hdfs:///data/wikipedia_sample.txt") \
          .flatMap(tok).map(lambda w: (w, 1)).cache()
pairs.count()                                   # materialise cache
t = time.time()
top_r = pairs.reduceByKey(lambda a, b: a + b).takeOrdered(20, lambda kv: -kv[1])
t_r = time.time() - t
t = time.time()
top_g = pairs.groupByKey().mapValues(len).takeOrdered(20, lambda kv: -kv[1])
t_g = time.time() - t
assert top_r == top_g; print(top_r, t_r, t_g)

Key idea: reduceByKey combines map-side and shuffles about one record per word per partition. groupByKey shuffles every (word, 1) pair, so it is slower and writes more shuffle data (compare in the Spark UI). takeOrdered avoids a full sort.

Book ch06 · ProgrammingQ6.41 PE: Iterative k-Means with RDD Caching (PySpark). Implement k-means with the raw RDD API (not MLlib): (1) cache the input RDD; (2) measure wall-clock time per iteration; (3) report the speedup of cached vs uncached iterations (K = 10, 20 iterations).
data = sc.textFile("hdfs:///data/clustering_input.csv") \
         .map(lambda l: [float(x) for x in l.split(",")])
data.persist(StorageLevel.MEMORY_ONLY)
cent, times = data.takeSample(False, 10, seed=42), []   # 1st action fills cache
for it in range(20):
    t = time.time()
    stats = data.map(lambda p: (closest(p, cent), (p, 1))) \
                .reduceByKey(lambda a, b: (add(a[0], b[0]), a[1] + b[1])) \
                .mapValues(lambda s: [x / s[1] for x in s[0]]).collectAsMap()
    cent = [stats.get(i, cent[i]) for i in range(10)]
    times.append(time.time() - t)
print("speedup", times[0] / (sum(times[1:]) / 19))

Key idea: the first pass reads HDFS (and fills the cache), and passes 2 to 20 read from memory. Speedup = t1 / mean(t2..20). For a true uncached baseline, run again without persist(). reduceByKey keeps the shuffle to K partial sums per partition.
