Pool · MCQQ8.1 Which tool is specifically designed to transfer data in bulk between an RDBMS (e.g., MySQL) and HDFS? (a) Apache Flume (b) Apache Kafka (c) Apache Sqoop (d) Apache NiFi

(c) Apache Sqoop (SQL-to-Hadoop) runs parallel bulk imports and exports as map-only MapReduce jobs. Flume moves logs to HDFS. Kafka streams data in real time. NiFi is a visual dataflow tool.

Pool · MCQQ8.2 Apache Kafka's data model is based on which fundamental storage abstraction? (a) B-tree indexes for fast point lookups (b) Column-family storage (like HBase) (c) Append-only immutable distributed logs (partitioned topics) (d) Document storage with secondary indexes

(c). A topic is split into partitions, each an append-only, ordered, immutable log addressed by offset. Sequential writes give Kafka its throughput.

Pool · MCQQ8.3 In the Lambda architecture, which layer handles real-time, low-latency query views? (a) Batch Layer (b) Serving Layer (c) Speed Layer (d) Ingestion Layer

(c) Speed Layer. It processes recent data incrementally for low-latency views. The Batch Layer has high latency. The Serving Layer only merges and serves views and does not process data.

Pool · MCQQ8.4 The Kappa architecture differs from the Lambda architecture primarily by: (a) Adding a third processing layer for machine learning (b) Using only relational databases for both batch and stream storage (c) Eliminating the batch layer and using Kafka log replay for all reprocessing (d) Replacing Hadoop with Spark in the batch layer while keeping the speed layer

(c). Kappa keeps one stream-processing code path. To reprocess history, replay the Kafka log through a new job version. (d) is a common mistake: Kappa removes the batch layer entirely.

Pool · v1 deck · T/FQ8.5 Apache Sqoop is designed for real-time streaming ingestion from transactional systems.

False. Sqoop is a batch tool. It launches MapReduce jobs for bulk RDBMS-HDFS transfers, usually scheduled nightly. Real-time ingestion uses Kafka (or CDC tools).

Pool · T/FQ8.6 Kafka retains messages for a configurable period, allowing consumers to replay events from any past offset.

True. Messages stay on disk for the retention period (time or size), consumed or not. A consumer can seek to any retained offset and re-read.

Pool · v1 deck · T/FQ8.7 The Lambda architecture requires maintaining two separate code paths implementing the same business logic.

True. The batch layer (Spark/Hive) and speed layer (Spark Streaming/Flink) must both implement the same logic (e.g. daily transaction count). Maintaining both is Lambda's main engineering cost.

Pool · T/FQ8.8 Apache Flume is the preferred tool for collecting and aggregating server log data into HDFS.

True. Flume agents (source - channel - sink) collect, aggregate and move streaming log and event data reliably into HDFS/HBase.

Pool · DescriptiveQ8.9 D1. Explain the Lambda architecture with a labelled diagram. What are its three layers? What is its primary engineering disadvantage compared to the Kappa architecture?
  • Batch layer: stores the immutable master dataset (HDFS). It periodically recomputes batch views over all data. Views are accurate but high latency.
  • Speed layer: processes only recent data in real time (Storm/Spark Streaming/Flink). It gives real-time views that cover the batch gap.
  • Serving layer: indexes batch views (HBase/Druid/Cassandra) and merges them with real-time views to answer queries.
            +--> Batch layer (HDFS + Spark/Hive) --> batch views --+
Data --> Kafka                                                     +--> Serving layer --> Query
            +--> Speed layer (Flink/Spark Str.) --> real-time views-+

Disadvantage: the same logic needs two code paths. That doubles development, testing and debugging, and the results can drift apart. Kappa has one streaming code path.

Pool · DescriptiveQ8.10 D2. Describe how Apache Kafka achieves high throughput and fault tolerance. Explain the roles of topics, partitions, offsets, brokers, and replication factor in the Kafka data model.
  • Topic: a named stream (category) of messages.
  • Partition: a topic splits into ordered append-only logs. It is the unit of parallelism (one consumer per partition per group).
  • Offset: the sequential id of a message within a partition. Consumers track it, which enables replay.
  • Broker: a Kafka server that stores partitions. A cluster spreads partitions across brokers.
  • Replication factor: copies of each partition on different brokers. One leader plus followers (ISR). If the leader fails, a follower takes over.

Throughput: sequential disk I/O, OS page cache, zero-copy sendfile(), batching and compression, partition parallelism. Fault tolerance: replication with ISR, acks=all, and committed consumer offsets so restarts resume.

Pool · DescriptiveQ8.11 D3. What is a data lake? How does it differ from a data warehouse in terms of schema enforcement, storage format, and typical use cases? What is a data swamp and how is it prevented?

Data lake: a central low-cost store (HDFS/S3) that holds raw data of any type at any scale.

  • Schema: a lake uses schema-on-read. A warehouse uses schema-on-write.
  • Format: a lake holds raw files (CSV, JSON, logs, images, Parquet/ORC). A warehouse holds cleaned, structured relational tables.
  • Use cases: a lake serves data science, ML and exploration. A warehouse serves BI reports, dashboards and governed KPIs.

Data swamp: a lake with no metadata, quality checks or ownership. Users cannot find or trust the data. Prevent it with a data catalogue/metadata (Hive Metastore, Atlas), zones (raw/processed/curated), quality checks before promotion, ownership and access control (Ranger), and retention policies.

Pool · Plan · AnalyticalQ8.12 A1. Pipeline Design for a Bank: a Bangladeshi commercial bank must (a) synchronise 10 million customer records nightly from Oracle to Hadoop; (b) detect fraudulent card-swipe events in real time with a decision within 200 ms; (c) power a risk dashboard with data no older than 5 minutes. Specify the tool (Sqoop, Flume, Kafka, Spark Streaming) at each stage and justify by latency, throughput and fault tolerance. Which architecture (Lambda or Kappa) fits best, and why?

(a) Sqoop incremental import (--incremental lastmodified, -m 8 parallel mappers) into Hive/ORC nightly. It is batch with high throughput, and YARN retries failed map tasks. Latency is not critical. 10M rows x 1 KB (assumed) = ~10 GB, which takes minutes with parallel mappers.

A low-latency stream processor scores each event (Kafka Streams/Flink, or Spark Structured Streaming in continuous or short micro-batch mode) with per-card state. The decision takes <200 ms. (c) Spark Streaming 1-minute micro-batches from Kafka aggregate exposure into a serving store (HBase/Druid) that the dashboard reads. Data is at most a few minutes old, under the 5-min limit.

Architecture: Lambda fits. The batch layer (Sqoop + Hive) gives regulators accurate, auditable nightly data. The speed layer (Kafka + streaming) covers fraud and the dashboard. Flume is not needed, since nothing collects logs, unless server logs are also ingested.

Pool · Plan · AnalyticalQ8.13 A2. Lambda to Kappa Migration: a team using Lambda complains that two code paths (batch + stream) double development cost; the CTO suggests Kappa. Analyse (a) what must be true about the stream processing engine for Kappa to be viable; (b) the risks of migrating; (c) under what conditions Kappa is not suitable (at least two concrete scenarios from Bangladesh financial or healthcare sectors).

(a) The engine must support exactly-once state, event-time processing with watermarks, large durable state with checkpoints, and enough throughput to replay months of history fast. Kafka must retain the full history (long retention, tiered storage or compacted topics).

(b) Risks: replaying years of data is slow and costly. Long retention costs storage. Complex queries (big joins, full-history aggregates) are harder in streaming. A bug in the single path affects everything. The team needs new skills. The migration period runs both stacks.

(c) Not suitable: (1) Bangladesh Bank regulatory reports need years of transactions recomputed exactly and auditable. Batch over a warehouse is cheaper and easier to defend. (2) bKash/bank year-end reconciliation or interest calculation over all accounts is one huge batch job, not a stream. (3) Hospital/DGHS epidemiology on historical patient records from many hospitals. The records arrive as monthly files, so they are not an event stream, and they need complex joins.

v1 deck · DiscussionQ8.14 Netflix's Kafka cluster handles 1.3M events/sec at peak across 4,000 topics. If each topic has 12 partitions, calculate the minimum number of brokers needed assuming each broker handles 50,000 partitions and a replication factor of 3.

Formula: brokers = ceil(topics x partitions x RF / partitions per broker).

  1. Partitions = 4,000 x 12 = 48,000.
  2. Replicas = 48,000 x 3 = 144,000.
  3. 144,000 / 50,000 = 2.88 -> 3 brokers.
  4. Check: RF 3 also needs at least 3 brokers. It holds.

Meaning: 3 is the theoretical minimum. At 1.3M events/s (325 events/s per topic on average), Netflix runs many more brokers for throughput, disk and failure headroom.

v1 deck · DiscussionQ8.15 A Flink job joins three Kafka streams - assignments, exposures and outcomes - on user_id. Events may arrive out of order by up to 30 seconds. Design an event-time window strategy (window size, watermark lag, allowed lateness) and justify each choice.
  • Event time from each event's timestamp, keyed by user_id.
  • Watermark lag = 30 s (bounded out-of-orderness). It matches the maximum disorder, so windows close only after all expected events arrive.
  • Window: tumbling (or interval join) of e.g. 5-10 min (assumed) Make it long enough that an assignment, its exposure and the outcome fall in the same window. An interval join (outcome within X min after exposure) handles window boundaries better than fixed windows.
  • Allowed lateness ~1-2 min plus a side output for later events. This updates results for rare stragglers beyond 30 s without holding state forever.

Trade-off: larger lag or lateness gives more complete results but raises latency and state size.

v1 deck · DiscussionQ8.16 Netflix uses both Lambda (speed + batch) and Kappa (stream-only) architectures for different pipelines. Identify two workloads where Lambda is preferable to Kappa and explain why stream reprocessing alone is insufficient.
  • Recommendation model training / billing-royalty reports over years of viewing history: these need full-history joins and aggregations. Replaying years of Kafka (Netflix keeps ~7 days) is impossible or too slow. The batch layer over S3/Iceberg recomputes it cheaply.
  • Financial/content-licensing reconciliation: this must be exact and auditable, with late corrections from partners. A batch recompute over the complete dataset is the source of truth. The speed layer gives provisional real-time numbers.

Stream replay alone fails when history exceeds log retention, when the job needs complex global computations, or when accuracy needs a guarantee from full recomputation.

v1 deck · ShortQ8.17 MIT exam question: Why does Kafka use sequential disk writes rather than a B-tree index? Quantify the throughput difference on spinning disk.

Kafka only appends to a log, and consumers read sequentially by offset, so it needs no random lookups. A B-tree needs random seeks (O(log n) per write, ~10 ms each on HDD). On a spinning disk, sequential I/O runs at ~100-200 MB/s. Random 4 KB I/O runs at ~100-200 IOPS = ~0.4-0.8 MB/s. Sequential is roughly 100-1,000x faster (classic figure: ~6000x for linear vs random). The OS page cache and read-ahead add more gain.

Book ch08 · ShortQ8.18 What is the N^2 problem in point-to-point ETL integration? With 30 systems, how many direct connections are required in the worst case? How does an event bus reduce this number?

Every system connects directly to every other, so connections grow as O(N2). Formula: N(N-1)/2.

  1. 30 x 29 / 2 = 435 connections (870 if each direction is a separate pipeline).
  2. With an event bus (Kafka), each system connects once: 30 connections (O(N)).

Meaning: a 31st system needs 1 new connector instead of 30.

Book ch08 · ShortQ8.19 Describe the three components of an Apache Flume agent. What is the difference between a Memory Channel and a File Channel in terms of durability?

Source receives events (exec/tail, syslog, Avro, spooling dir). Channel buffers them. Sink writes to HDFS/HBase/next agent. Memory Channel is fast, but events are lost if the agent crashes. File Channel writes events to local disk with checkpoints. It is durable across crashes but slower.

Book ch08 · ShortQ8.20 What is the difference between an Apache Kafka topic and a Kafka partition? Why must messages with the same key be routed to the same partition?

A topic is the logical stream name. A partition is one ordered append-only log shard of that topic. It is the unit of parallelism and storage. Kafka guarantees order only within a partition. Hashing the key (hash(key) mod partitions) to one partition keeps all events of an entity (e.g. one account) in order. It also lets one consumer hold that entity's state.

Book ch08 · ShortQ8.21 Explain what a Kafka offset is. Who is responsible for tracking offsets in the Kafka data model - the broker or the consumer? What is the benefit of this design?

An offset is the sequential position of a message in a partition. The consumer tracks and commits its offset, which Kafka stores in the __consumer_offsets topic. Benefits: the broker stays stateless per message (no per-message ack bookkeeping), so it scales. Consumers can rewind and replay. Many groups read independently.

Book ch08 · ShortQ8.22 What is a Kafka consumer group? If a topic has 6 partitions and a consumer group has 4 consumers, how many partitions does each consumer process (assuming uniform assignment)?

A consumer group is a set of consumers that share one group.id. Each partition goes to exactly one member, so the group divides the work. Each group gets the full stream.

  1. 6 / 4 = 1 remainder 2.
  2. 2 consumers get 2 partitions, 2 consumers get 1 (average 1.5).
Book ch08 · ShortQ8.23 Explain the Linux sendfile() system call and its role in Kafka's consumer throughput. How many memory copies does a traditional message broker require compared to Kafka?

sendfile() moves data from the page cache directly to the socket inside the kernel (zero-copy), skipping user space. The traditional path makes 4 copies (disk -> page cache -> application buffer -> socket buffer -> NIC) with 4 context switches. Kafka makes 2 copies (disk -> page cache -> NIC via DMA). It makes no CPU copy to user space. Data keeps the same on-disk format, so one cached copy serves many consumers.

Book ch08 · ShortQ8.24 Describe the Lambda architecture's three layers. What is the purpose of the Serving Layer?

Batch layer: holds the immutable master dataset and recomputes accurate batch views periodically. Speed layer: processes recent data in real time for low-latency views. Serving layer: indexes and stores the batch views and merges them with real-time views. Queries then get complete, up-to-date answers (e.g. HBase, Druid, Cassandra).

Book ch08 · ShortQ8.25 What is the "dual-code-path problem" in the Lambda architecture? Why does it create a maintenance burden?

Teams must write the same business logic twice: once for the batch engine (Spark/Hive) and once for the streaming engine (Flink/Spark Streaming). Every change must be made, tested and deployed in both. The two can diverge and give different numbers. Teams also need skills in two frameworks. This roughly doubles development and debugging cost.

Book ch08 · ShortQ8.26 In the Kappa architecture, how is historical reprocessing accomplished? Describe the step-by-step reprocessing workflow when business logic changes.
  1. Keep the full event history in Kafka (long retention or tiered storage).
  2. Deploy v2 of the stream job with a new consumer group starting at offset 0.
  3. v2 writes to a new output table while v1 keeps serving.
  4. When v2 catches up to the head of the log, compare outputs.
  5. Switch readers to the v2 table.
  6. Stop v1 and delete its output.
Book ch08 · ShortQ8.27 What is a data lake? List four symptoms that indicate a data lake has become a data swamp.

A data lake is a central store (HDFS/S3) for raw data of any format, with schema-on-read. Swamp symptoms: (1) no catalogue/metadata, so users cannot find datasets; (2) duplicate, conflicting copies of the same data; (3) no owner or lineage, so nobody knows the source or freshness; (4) poor quality (nulls, bad formats), so users stop trusting it. Also: no access control, and stale data is never deleted.

Book ch08 · ShortQ8.28 What is an open table format (e.g., Delta Lake or Apache Iceberg)? Name three features that open table formats add to a standard Parquet-on-S3 data lake.

A metadata/transaction layer over Parquet files. It makes a folder of files behave like a database table. It adds: (1) ACID transactions (atomic commits, concurrent writers, UPDATE/DELETE/MERGE); (2) time travel / snapshot versioning; (3) schema evolution and enforcement. It also adds hidden partitioning and file-level statistics for skipping.

Book ch08 · ShortQ8.29 Compare Apache Sqoop and Apache Kafka on: (a) data direction, (b) latency, (c) replay capability, and (d) the underlying parallelism mechanism.
  • (a) Direction: Sqoop moves data between an RDBMS and HDFS/Hive (import/export). Kafka moves data from any producer to any consumers (pub/sub).
  • (b) Latency: Sqoop is batch, taking minutes to hours. Kafka is real time, taking milliseconds.
  • (c) Replay: Sqoop has none, so re-run the import against the source. Kafka replays any retained offset.
  • (d) Parallelism: Sqoop uses map-only MapReduce tasks that split the table by --split-by column ranges. Kafka uses topic partitions and consumer groups.

Book ch08 · AnalyticalQ8.32 AP Consumer Group Rebalancing: topic with 12 partitions; group of 6 consumers, 2 partitions each. (a) Consumer 3 crashes without graceful shutdown: what does Kafka do, who takes its partitions, how long does rebalance take (default session.timeout.ms = 45 s)? (b) Two new consumers join simultaneously: how are the 12 partitions reassigned under the default RangeAssignor? (c) A new version is deployed with 12 instances (one per partition); what happens if 4 extra instances are accidentally started (16 total)?

(a) No heartbeats arrive, so the group coordinator marks consumer 3 dead after session.timeout.ms = 45 s. It then triggers a rebalance. The 2 partitions of consumer 3 go unprocessed for ~45 s + rebalance time (a few seconds). RangeAssignor with 5 consumers: 12 / 5 = 2 remainder 2, so 2 consumers get 3 partitions and 3 get 2. With the eager protocol, all partitions are revoked and reassigned (stop-the-world). Processing resumes from the last committed offset, so some messages are processed again.

(b) Assume the original 6 healthy consumers grow to 8. 12 / 8 = 1 remainder 4. Consumers (sorted by member id) C1-C4 get 2 partitions (P0-1, P2-3, P4-5, P6-7), C5-C8 get 1 (P8, P9, P10, P11). (If you start from the 5 left after (a): 7 consumers, 12 / 7 = 1 remainder 5, so five get 2 and two get 1.)

(c) A group gives each partition to only one consumer, so 12 consumers get 1 partition each and 4 sit idle (hot standbys). They add no throughput, and adding them causes a rebalance. They take over if an active consumer fails.

Book ch08 · ProgrammingQ8.36 PE Kafka Producer and Consumer (Python, kafka-python, local single-broker Docker): producer of 50,000 synthetic mobile payment events (txn_id, sender, receiver, amount_usd, timestamp_ms) keyed by sender; consumer in group analytics-v1 computing (i) total volume in USD, (ii) top-10 senders by count, (iii) average transaction amount per minute; reset offsets to the beginning and re-run to verify identical results (idempotency); second group fraud-v1 verifying both groups independently read all messages from offset 0.
from kafka import KafkaConsumer
from collections import Counter, defaultdict
import json
def run(group):
    c = KafkaConsumer("mobile-payments", bootstrap_servers="localhost:9092",
        group_id=group, auto_offset_reset="earliest", consumer_timeout_ms=5000,
        value_deserializer=lambda b: json.loads(b))
    c.poll(0); c.seek_to_beginning()           # reset offsets for re-runs
    tot, cnt, per_min = 0.0, Counter(), defaultdict(list)
    for m in c:
        e = m.value; tot += e["amount_usd"]; cnt[e["sender"]] += 1
        per_min[e["timestamp_ms"] // 60000].append(e["amount_usd"])
    return round(tot, 2), cnt.most_common(10), {k: sum(v)/len(v) for k, v in per_min.items()}
assert run("analytics-v1") == run("analytics-v1") == run("fraud-v1")

Key idea: the producer uses key=sender, so a sender's events share a partition. Offsets belong to each consumer group. A new group or seek_to_beginning replays the same immutable log and gives identical results.

served = batch.filter(F.col("hour_ts") < cur).unionByName(live)
(served.filter(F.col("hour_ts") >= F.expr("current_timestamp() - INTERVAL 24 HOURS"))
  .groupBy("pickup_zone").agg(F.sum("rides"), F.sum("fare")).show())

Key idea: the same aggregation runs in both layers (the dual code path). The serving layer drops the batch value for the current hour and takes the real-time one.
