Pool · MCQQ7.1 In Hive, where is table schema metadata (column names, types, partition info) stored? (a) HDFS NameNode (b) Hive Metastore (relational DB such as MySQL) (c) HBase (d) ZooKeeper

(b) Hive Metastore. A relational DB (MySQL/PostgreSQL/Derby) sits behind the Metastore. It holds schemas, types and partition locations. The NameNode holds only HDFS block and file metadata.

Pool · MCQQ7.2 What does schema-on-read mean in the context of Hive? (a) Schema is validated when data is inserted into the table (b) Schema is applied when data is queried, not when it is stored on HDFS (c) Schema is stored separately from data in HDFS metadata (d) Schema is inferred automatically from column names in the file header

(b). Hive loads files as they are. The SerDe applies the table schema at query time. (a) is schema-on-write. (d) is auto schema inference (as in Spark CSV), which is different.

Pool · MCQQ7.3 Which Hive optimization technique physically organises data into separate HDFS sub-directories by a column's value to avoid full table scans? (a) Bucketing (b) Indexing (c) Partitioning (d) Compression

(c) Partitioning. Each value gets its own directory (e.g. dt=2024-01-01/). A WHERE on that column then gives partition pruning. Bucketing hashes rows into files inside a partition. It helps joins and sampling, but it does not skip directories.

Pool · MCQQ7.4 Presto's primary performance advantage over Hive+MapReduce for interactive queries is: (a) Presto supports more SQL functions than HiveQL (b) Presto has better native integration with HBase and Cassandra (c) Presto executes queries entirely in memory without writing intermediate results to disk (d) Presto has native Python UDF support

(c). Hive-on-MR writes intermediate data to HDFS between every MR job. Presto pipelines stages in memory across long-running workers. This removes the disk I/O and the job start-up cost.

Pool · v1 deck · T/FQ7.5 HiveQL supports full ACID transactions on all table types, just like MySQL.

False. ACID works only on ORC-backed transactional tables created with TBLPROPERTIES ('transactional'='true'). Plain text and Parquet external tables have no UPDATE or DELETE.

Pool · T/FQ7.6 Partitioning in Hive reduces query time by eliminating irrelevant data partitions from the HDFS scan.

True. A filter on the partition column makes the planner read only the matching directories (partition pruning). Far less data is scanned.

Pool · v1 deck · T/FQ7.7 Hive directly executes a HiveQL query on HDFS without any intermediate translation step.

False. The Driver parses HiveQL and builds and optimises a logical plan. It then compiles the plan into a DAG of MapReduce, Tez or Spark jobs. This happens before any data is read.

Pool · v1 deck · T/FQ7.8 Bucketing in Hive is particularly useful for optimising JOIN operations between two large tables.

True. Both tables are bucketed on the join key, with the same bucket count or a multiple. A bucket map join / SMB join then joins matching bucket numbers directly. This avoids a full shuffle-sort.

Plan · DescriptiveQ7.9 Hive vs. traditional SQL (RDBMS) differences (marked "important exam topic"): compare schema enforcement, ACID, UPDATE/DELETE, indexing and latency.
  • Schema: RDBMS = schema-on-write (validated at insert); Hive = schema-on-read (applied at query time).
  • ACID: RDBMS has full ACID. Hive is limited: only ORC tables in transactional (ACID) mode.
  • UPDATE/DELETE: RDBMS supports both fully. Hive supports them on ACID tables only, through delta files and compaction.
  • Indexing: RDBMS uses B-tree indexes. Hive uses partitions + buckets (and ORC min/max stats).
  • Latency: RDBMS milliseconds (OLTP); Hive seconds-minutes (batch OLAP over TB-PB).
Pool · DescriptiveQ7.10 D1. Explain the Hive architecture: what is the role of HiveServer2, the Driver, and the Metastore? How is a HiveQL query compiled into executable jobs? Draw the component diagram.

Components: HiveServer2 is a Thrift/JDBC/ODBC service. It accepts queries from many concurrent clients (Beeline, BI tools) and authenticates them. The Driver manages the query lifecycle: compiler, optimiser, executor. The Metastore is the catalogue (in MySQL/PostgreSQL). It holds table schemas, SerDes and partition locations.

Compilation: (1) Parse HiveQL to an AST. (2) Run semantic analysis, resolving tables and columns via the Metastore. (3) Build a logical plan of operators. (4) Optimise it (predicate pushdown, partition pruning, join reordering, CBO). (5) Build the physical plan, a DAG of MapReduce/Tez/Spark tasks. (6) Submit it to YARN, which reads and writes HDFS.

Client (Beeline/JDBC/BI)
        |
   HiveServer2 --- Metastore (MySQL)
        |
     Driver: Parser -> Planner -> Optimizer -> Executor
        |
   MR / Tez / Spark jobs on YARN
        |
      HDFS (data files)
Pool · DescriptiveQ7.11 D2. Differentiate between partitioning and bucketing in Hive. When would you choose each? Describe a scenario in Bangladesh e-commerce data where both are used together.
  • Partitioning: one directory per value of a low-cardinality column (date, division). It enables partition pruning. The partition count grows with the data. Too many partitions cause the small-file problem.
  • Bucketing: rows are hashed into a fixed number of files (hash(col) mod N) on a high-cardinality column (user_id). It helps bucket map / SMB joins and sampling. It does not skip directories.
  • Choose: partition on columns used in WHERE filters that have few distinct values. Bucket on join or group keys that have many values.
  • Scenario: A Daraz-style orders table is PARTITIONED BY (order_date), so a daily sales report reads one day. It is also CLUSTERED BY (customer_id) INTO 64 BUCKETS, so joins with the bucketed customers table avoid a shuffle.
Pool · v1 deck · DescriptiveQ7.12 D3. What is schema-on-read? What are its advantages and disadvantages compared to schema-on-write in a traditional RDBMS such as MySQL? Give one example where schema-on-read causes a data quality problem.

Schema-on-read: Hive stores raw files unchanged. It applies a schema only at query time, through the SerDe.

  • Advantages: fast loading (copy the files); the same data can have multiple schemas; it handles semi-structured, unstructured and evolving data; no upfront modelling.
  • Disadvantages: there is no validation at load, so bad rows surface late. Every query pays the parsing cost. Constraints are weaker (no PK/FK). Queries run slower than on an optimised RDBMS.
  • Example: A CSV has some rows with amount "1,200" or a missing column. Hive silently returns NULL for the INT column (or shifts columns). SUM(amount) is then wrong, with no error. MySQL would reject the insert.
Pool · Plan · AnalyticalQ7.13 A1. Partitioning & Bucketing Design: 5 TB e-commerce transaction table (txn_id, user_id, product_id, amount, country, txn_date). Design a complete partitioning and bucketing strategy to optimise (i) daily revenue reports filtered by country and txn_date, (ii) JOINs with a 10 M-row user profile table keyed on user_id. Write the complete CREATE TABLE DDL. Justify the number of buckets and the partition column(s).

Partition on txn_date (every daily report filters on it). Reports also filter by country. Assume few countries, so either add country as a second partition level or rely on ORC min/max stats. Bucket on user_id (join key, high cardinality).

Bucket count formula: file size per bucket = (partition size) / N. Target 128-256 MB.

  1. Assume 3 years of data (assumed) = 1,095 daily partitions. 5 TB / 1,095 = 4.57 GB per day.
  2. N = 32: 4.57 GB / 32 = 143 MB per bucket file (about 1 HDFS block).
  3. User table: 10 M rows x 200 B (assumed) = 2 GB; Bucket it on user_id into the same 32 buckets, 62.5 MB each. A bucket map / SMB join then pairs bucket i with bucket i.
CREATE TABLE transactions (
  txn_id BIGINT, user_id BIGINT, product_id BIGINT,
  amount DECIMAL(12,2), country STRING)
PARTITIONED BY (txn_date DATE)
CLUSTERED BY (user_id) SORTED BY (user_id) INTO 32 BUCKETS
STORED AS ORC TBLPROPERTIES ('orc.compress'='SNAPPY');

CREATE TABLE users (user_id BIGINT, name STRING, city STRING)
CLUSTERED BY (user_id) SORTED BY (user_id) INTO 32 BUCKETS
STORED AS ORC;
SET hive.optimize.bucketmapjoin.sortedmerge=true;

Meaning: a daily-by-country report scans one 4.57 GB partition instead of 5 TB. The user join needs no shuffle. Do not partition by user_id (10 M directories) or by country+date with many countries. That avoids the small-file problem.

Pool · Plan · AnalyticalQ7.14 A2. Query Compilation to MapReduce: write HiveQL to find the top 5 products by total revenue in 2023; trace how Hive compiles it into MapReduce stages (Map output, shuffle key, Reduce computation). How would switching from MapReduce to Tez change the plan? (Plan version also asks: monthly average amount per country for Q1 2024.)
SELECT product_id, SUM(amount) AS revenue
FROM transactions
WHERE txn_date BETWEEN '2023-01-01' AND '2023-12-31'
GROUP BY product_id
ORDER BY revenue DESC
LIMIT 5;

-- Plan item: monthly average per country, Q1 2024
SELECT country, MONTH(txn_date) AS mon, AVG(amount) AS avg_amt
FROM transactions
WHERE txn_date BETWEEN '2024-01-01' AND '2024-03-31'
GROUP BY country, MONTH(txn_date);
  • Job 1 Map: reads only the 2023 partitions (pruning) and emits (product_id, amount). A map-side partial SUM runs (combiner / hash aggregation).
  • Shuffle key: product_id.
  • Job 1 Reduce: computes SUM(amount) per product_id and writes (product_id, revenue) to a temp HDFS dir.
  • Job 2: Map reads the temp output and emits top-5 candidates. A single reducer sorts by revenue DESC and applies LIMIT 5.
  • Tez: the same operators become one DAG (Map -> Reduce -> Reduce) in one application. There is no temp HDFS write between jobs. Containers are reused. Latency drops.
v1 deck · AnalyticalQ7.15 Given a HiveQL query with two JOINs and a GROUP BY, draw the MapReduce DAG that Hive would generate, identifying the shuffle key at each stage.

Example (assumed): SELECT c.city, SUM(o.amt) FROM orders o JOIN customers c ON o.cust_id=c.cust_id JOIN products p ON o.prod_id=p.prod_id GROUP BY c.city.

Job1: Map(orders, customers) --shuffle key: cust_id--> Reduce: join1 -> tmp1
Job2: Map(tmp1, products)    --shuffle key: prod_id--> Reduce: join2 -> tmp2
Job3: Map(tmp2) emit (city, amt) --shuffle key: city--> Reduce: SUM -> output

Each common (reduce-side) join is one MR job keyed on its join column. The GROUP BY adds one job keyed on the group-by column. If both joins use the same key, they merge into one job. A small table becomes a map join (no shuffle stage).

Pool · v1 deck · DiscussionQ7.16 Spotify's co-occurrence query runs GROUP BY song_a, song_b over 2 billion playlist rows. Estimate the output size if there are 30M songs. Propose a partitioning + bucketing scheme for the playlist_songs Hive table that would reduce the shuffle size for this query.

Formula: distinct unordered pairs = C(n,2) = n(n-1)/2.

  1. Upper bound: C(30M,2) = 4.5 x 1014 pairs; At 12 B per row (two INT ids + 4-byte count, assumed) that is 5.4 PB.
  2. Realistic bound from the data: 2 B rows with 20 songs per playlist (assumed) gives 108 playlists x C(20,2)=190 = 1.9 x 1010 pairs. That is about 228 GB emitted before aggregation. The output is at most this, because most of the 4.5 x 1014 pairs never co-occur.

Scheme: Partition playlist_songs by week/dt, so only new weeks are processed incrementally. Bucket and sort by playlist_id, so the self-join (a.playlist_id = b.playlist_id) is a bucket/SMB join with no shuffle. Add a.song_id < b.song_id to halve the pairs. Map-side aggregation and a HAVING count threshold cut the shuffle further.

Meaning: real co-occurrences (hundreds of GB) bound the shuffle, not the 5.4 PB theoretical matrix.

v1 deck · DiscussionQ7.18 Spotify uses Luigi while other companies use Apache Airflow. Compare the two on: dependency declaration style, backfill capability, and UI/observability. Which would you choose for a 100-step daily pipeline?
  • Dependencies: In Luigi, each Task declares requires() and output() targets, and the graph is pulled backward from the target. In Airflow, you write an explicit DAG in Python, link operators with >> and attach the schedule to the DAG.
  • Backfill: Luigi re-runs a task when its output target is missing. It has no built-in scheduler or date ranges, so it needs cron. Airflow has native scheduling and airflow dags backfill over date ranges, plus catchup and retries per task.
  • UI: Luigi's central scheduler UI is basic (task status, graph). Airflow has a rich web UI: grid and graph views, logs per task, SLAs and alerts.
  • Choice: Pick Airflow for a 100-step daily pipeline. At that size, scheduling, backfill, retries and observability matter most.
Book ch07 · ShortQ7.19 What is the LATERAL VIEW EXPLODE construct in HiveQL? A table orders has a column tags ARRAY<STRING>. Write a HiveQL query that counts the total number of times each tag appears across all orders.

EXPLODE is a UDTF. It turns one array into one row per element. LATERAL VIEW joins those rows back to the source row, so the other columns stay available.

FROM orders
LATERAL VIEW EXPLODE(tags) t AS tag
GROUP BY tag;

Book ch07 · ShortQ7.22 What problem does Apache Tez solve that Hive-on-MapReduce does not? For a HiveQL query that compiles to three MapReduce jobs with 500 MB of intermediate data at each stage boundary, calculate the HDFS I/O saved by using Tez instead.

Tez runs the whole query as one DAG. There is no HDFS write or read between jobs. Jobs do not restart repeatedly. Containers are reused. Edges are flexible, so a Map is not forced before every Reduce.

Formula: saved = boundaries x (write + read).

  1. 3 jobs = 2 boundaries.
  2. Per boundary: write 500 MB + read 500 MB = 1,000 MB.
  3. Total = 2 x 1,000 = 2,000 MB (2 GB) logical. With HDFS replication 3, the writes are 3 x 500, so 2 x (1,500 + 500) = 4 GB physical.

Meaning: Tez passes the 500 MB between stages over local disk or memory, not HDFS. (If "each boundary" counts the final output too, 3 boundaries = 3 GB logical. Assumed not.)

Book ch07 · ShortQ7.23 What is Hive LLAP? Describe the three components of LLAP architecture and explain why LLAP enables sub-second latency for repeated queries over the same table.

LLAP (Live Long And Process): long-running daemons on each node that run Hive fragments and cache data. Components: (1) LLAP daemons, persistent processes with executor threads; (2) an in-memory columnar cache (off-heap, ORC data + metadata); (3) the Tez AM / coordinator, which plans the DAG and sends fragments to daemons (I/O elevator threads do async reads).

Queries run in under a second because there is no container start-up (JVMs are warm and JIT-compiled). Repeated queries read hot columns from RAM, not HDFS.

Book ch07 · ShortQ7.24 What is the difference between rule-based optimisation (RBO) and cost-based optimisation (CBO) in Hive? Give one example where RBO would produce a suboptimal plan that CBO would avoid.

RBO applies fixed rewrite rules (predicate pushdown, column pruning) whatever the data size. CBO (Apache Calcite) uses table and column statistics to estimate cost. It picks the join order and join type.

Example: big_fact JOIN medium JOIN tiny_dim written in that order. RBO joins in the written order (fact x medium first), which causes a huge shuffle. CBO sees the row counts. It joins the filtered tiny dim first and turns it into a map join. Intermediate data shrinks.

Book ch07 · ShortQ7.25 Explain Hive's Sort-Merge Bucket Join. What preconditions must both tables satisfy, and why does this join require no shuffle at query time?

SMB join: each mapper merges bucket i of table A with bucket i of table B in a sorted merge.

Preconditions: both tables are bucketed on the join key, have the same number of buckets (or a multiple), and are sorted by the join key (SORTED BY). Settings such as hive.optimize.bucketmapjoin.sortedmerge=true are on.

There is no shuffle because the data was already hash-partitioned and sorted at write time. Matching keys always sit in matching bucket files.

Book ch07 · ShortQ7.26 What is the Presto Connector SPI? Name three data sources that Presto can query through connectors, and explain what interface the connector must implement for each source.

The Service Provider Interface is the plugin API that lets Presto query any source. Sources include Hive/HDFS, MySQL/PostgreSQL (JDBC) and Kafka (also Cassandra, MongoDB).

Each connector implements the same interfaces. ConnectorMetadata covers schemas, tables, columns and stats. ConnectorSplitManager divides data into splits for parallelism (HDFS blocks, JDBC ranges, Kafka partitions). ConnectorRecordSetProvider / PageSourceProvider reads rows from a split. A PageSink is optional, for writes.

Book ch07 · ShortQ7.27 A data engineer argues that Presto should replace Hive entirely because Presto is always faster. Write a detailed counter-argument using a specific workload scenario where Hive is the correct choice.

Presto is faster for interactive queries. It keeps intermediate state in memory and has weak mid-query fault tolerance. Scenario: a nightly ETL over 200 TB of clickstream with large joins and aggregations that runs 5 hours. In Presto, one worker failure or a join that exceeds memory kills the whole query. It restarts from zero. Hive-on-Tez spills to disk and retries only the failed tasks. It writes ACID/ORC tables with dynamic partitions and maximises throughput on YARN. Use Hive for long batch ETL and Presto for ad-hoc reads on the same Metastore.

Book ch07 · ShortQ7.28 HiveServer2 replaced the original Hive command-line tool. What two problems with the original tool did HiveServer2 address, and what interface (protocol) does HiveServer2 expose to clients?

(1) No multi-client concurrency: the old CLI/HiveServer1 ran one session per process. (2) No authentication or security: there was no Kerberos/LDAP, and users reached the Metastore and HDFS directly. HiveServer2 exposes a Thrift-based RPC service. JDBC/ODBC drivers (Beeline) use it, over binary or HTTP transport.

Book ch07 · ShortQ7.29 What is vectorized execution in Hive? Explain the difference from the Volcano (row-at-a-time) execution model, and identify which file format is best suited for vectorized execution in Hive.

Vectorized execution processes a batch of ~1,024 rows per operator call, column by column in primitive arrays. Volcano calls next() once per row through every operator, which means virtual calls and poor CPU cache use. Batches give tight loops, SIMD and fewer function calls, so CPU use drops several times over. The best format is ORC (columnar, Hive's native vectorized reader).

Book ch07 · ShortQ7.30 A Presto query fails with "Query exceeded maximum memory." Explain: (a) why this error occurs; (b) why the same query would not fail in Hive-on-Tez; (c) what you should do to fix the problem without switching engines.

(a) Presto holds hash-join build sides and aggregation state in memory. When that exceeds query.max-memory or the per-node limits, Presto kills the query. (b) Hive-on-Tez spills to disk and works in smaller tasks. It is slower, but it finishes. (c) Fix it by raising query.max-memory(-per-node) and enabling spill-to-disk. Put the smaller table on the build side or use a partitioned (not broadcast) join. Filter or pre-aggregate earlier. Add workers, or split the query by partition.

Book ch07 · ShortQ7.31 Explain Hive's Map Join strategy. What is the default table size threshold for a Map Join, and what happens during query execution that eliminates the shuffle?

Hive loads the small table into an in-memory hash table and ships it to every mapper (distributed cache). Each mapper joins its split of the large table locally. Default threshold: 25 MB (hive.mapjoin.smalltable.filesize; hive.auto.convert.join.noconditionaltask.size is 10 MB). A local task builds the hash table before the map phase. The join is map-only, with no shuffle or reduce.

Book ch07 · ShortQ7.32 What is a Presto federated query? Write the SQL statement structure (not actual data) for a query that joins a Hive table with a MySQL table. What does the Presto Coordinator need to execute this query?

A federated query joins data from different systems in one SQL statement. Each table is addressed as catalog.schema.table.

SELECT h.col, m.col
FROM hive.sales.orders h
JOIN mysql.crm.customers m
  ON h.customer_id = m.customer_id
WHERE h.dt = '...';

The Coordinator needs catalog configs for both connectors (Hive Metastore URI + HDFS access; MySQL JDBC URL and credentials). It needs metadata and statistics from each to plan. It needs split managers to assign splits to workers.

Book ch07 · AnalyticalQ7.34 AP Window Function Design: table user_daily_activity(user_id, activity_date, minutes_streamed (0 if not active), country). (a) HiveQL for each user and date: 7-day rolling average of minutes_streamed. (b) Using LAG, number of days since each user last had non-zero minutes_streamed. (c) Using NTILE(10), divide users into deciles by total minutes in the past 30 days and compute churn rate per decile. (d) How would (a)-(c) be compiled by Hive-on-Tez vs Hive-on-MapReduce; how many jobs/stages each?
-- (a)
SELECT user_id, activity_date,
 AVG(minutes_streamed) OVER (PARTITION BY user_id ORDER BY activity_date
   ROWS BETWEEN 6 PRECEDING AND CURRENT ROW) AS avg7
FROM user_daily_activity;
-- (b) previous active day per user
SELECT user_id, activity_date,
 DATEDIFF(activity_date, LAG(activity_date) OVER (PARTITION BY user_id ORDER BY activity_date)) AS gap_days
FROM user_daily_activity WHERE minutes_streamed > 0;
-- (c) churned = no activity in the last 7 days (assumed)

  FROM user_daily_activity WHERE activity_date >= DATE_SUB(CURRENT_DATE,30) GROUP BY user_id)

FROM (SELECT *, NTILE(10) OVER (ORDER BY tot) d FROM t) x GROUP BY d;

(d) Each window needs a shuffle on its PARTITION BY key plus a sort on ORDER BY. MapReduce: (a) 1 job, (b) 1 job, (c) 3 jobs (GROUP BY user, global NTILE with a single reducer, GROUP BY decile). Book ch07 · AnalyticalQ7.35 AP Join Strategy Selection. Tables: transactions 80 billion rows, 12 TB compressed, bucketed on customer_id (500 buckets); customers 200 million rows, 80 GB, bucketed on customer_id (500 buckets); dim_country 250 rows, 40 KB, not bucketed; dim_category 8,000 rows, 2 MB, not bucketed. (a) transactions JOIN dim_country: optimal strategy and why; estimate network traffic for the alternative Common Join. (b) transactions JOIN customers (both 500 buckets on customer_id): optimal strategy; what additional condition must hold for SMB join? (c) Three-table join transactions JOIN customers JOIN dim_category: join order and strategy for each; justify via CBO cost minimisation. (d) What ANALYZE TABLE statistics would the CBO use to choose these strategies without hints?

(a) Map (broadcast) join: 40 KB is far below the 25 MB threshold. A common join shuffles both sides: about 12 TB + 40 KB = ~12 TB over the network. Map join: 12 TB / 256 MB splits = 49,152 mappers (assumed 256 MB splits) x 40 KB = ~1.9 GB (less with a per-node distributed cache). Meaning: about 6,500x less traffic.

(b) Bucket map join / Sort-Merge Bucket join: Both tables share the key and the bucket count (500). SMB needs one extra condition: both tables must be SORTED BY customer_id within buckets, with SMB settings enabled. 80 GB / 500 = 160 MB per bucket. Bucket i of transactions merges with bucket i of customers. There is no shuffle.

(c) Order: first (transactions SMB-join customers) using the existing bucketing (no shuffle). Then map-join dim_category (2 MB broadcast) in the same map stage. CBO picks the plan with the lowest estimated rows shuffled / bytes read. Neither join shuffles the 12 TB fact table.

(d) ANALYZE TABLE ... COMPUTE STATISTICS [FOR COLUMNS]: row count, total/raw data size, number of files. Column stats: NDV (distinct values), null count, min/max, avg/max column length. It also uses Metastore info on bucketing and sort columns. Size against the threshold picks the map join. Bucketing metadata picks SMB. NDV gives the join cardinality for ordering.

Book ch07 · ProgrammingQ7.40 PE Window Function Analytics Pipeline (HiveQL): table daily_sales(region STRING, product_id STRING, sale_date STRING, revenue DOUBLE). Produce a report with (a) 7-day moving average revenue per region-product; (b) revenue rank within region for each date; (c) day-over-day revenue growth %; (d) cumulative revenue per region from the start of the month.
SELECT region, product_id, sale_date, revenue,
 AVG(revenue) OVER (PARTITION BY region, product_id ORDER BY sale_date
   ROWS BETWEEN 6 PRECEDING AND CURRENT ROW) AS ma7,
 RANK() OVER (PARTITION BY region, sale_date ORDER BY revenue DESC) AS rnk,
 100.0*(revenue - LAG(revenue) OVER w) / NULLIF(LAG(revenue) OVER w, 0) AS dod_pct,
 SUM(revenue) OVER (PARTITION BY region, SUBSTR(sale_date,1,7) ORDER BY sale_date
   ROWS UNBOUNDED PRECEDING) AS mtd
FROM daily_sales
WINDOW w AS (PARTITION BY region, product_id ORDER BY sale_date);

Key idea: four window functions in one pass. A ROWS frame gives the moving average, LAG gives growth, and SUBSTR(date,1,7) is the month key for month-to-date.

import time, requests
H = {"X-Presto-User": "analyst", "X-Presto-Catalog": "hive"}
def profile(sql, host="http://coord:8080"):
    t0 = time.time()
    d = requests.post(f"{host}/v1/statement", data=sql, headers=H).json()
    while d.get("nextUri"):
        time.sleep(0.5)
        d = requests.get(d["nextUri"], headers=H).json()
    s = d["stats"]
    print(s["state"], f"{time.time()-t0:.2f}s",
          s.get("processedBytes"), s.get("processedRows"),
          s.get("completedSplits"), s.get("peakMemoryBytes"))

Key idea: POST to /v1/statement. Follow nextUri until it disappears (FINISHED/FAILED). Then read the stats block.
