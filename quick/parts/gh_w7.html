Pool · MCQQ7.1 In Hive, where is table schema metadata (column names, types, partition info) stored? (a) HDFS NameNode (b) Hive Metastore (relational DB such as MySQL) (c) HBase (d) ZooKeeper

(b) Hive Metastore. Schemas, types and partition locations live in a relational DB (MySQL/PostgreSQL/Derby) behind the Metastore; the NameNode only holds HDFS block/file metadata.

Pool · MCQQ7.2 What does schema-on-read mean in the context of Hive? (a) Schema is validated when data is inserted into the table (b) Schema is applied when data is queried, not when it is stored on HDFS (c) Schema is stored separately from data in HDFS metadata (d) Schema is inferred automatically from column names in the file header

(b). Files are loaded as-is; the table schema is applied at query time by the SerDe. (a) is schema-on-write; (d) is auto schema inference (as in Spark CSV), a different thing.

Pool · MCQQ7.3 Which Hive optimization technique physically organises data into separate HDFS sub-directories by a column's value to avoid full table scans? (a) Bucketing (b) Indexing (c) Partitioning (d) Compression

(c) Partitioning. Each value gets its own directory (e.g. dt=2024-01-01/) so a WHERE on that column gives partition pruning. Bucketing hashes rows into files inside a partition; it helps joins/sampling but does not skip directories.

Pool · MCQQ7.4 Presto's primary performance advantage over Hive+MapReduce for interactive queries is: (a) Presto supports more SQL functions than HiveQL (b) Presto has better native integration with HBase and Cassandra (c) Presto executes queries entirely in memory without writing intermediate results to disk (d) Presto has native Python UDF support

(c). Hive-on-MR materialises intermediate data to HDFS between every MR job; Presto pipelines stages in memory across long-running workers, removing that disk I/O and job start-up cost.

Pool · v1 deck · T/FQ7.5 HiveQL supports full ACID transactions on all table types, just like MySQL.

False. ACID only works on ORC-backed transactional tables created with TBLPROPERTIES ('transactional'='true'); plain text/Parquet external tables have no UPDATE/DELETE.

Pool · T/FQ7.6 Partitioning in Hive reduces query time by eliminating irrelevant data partitions from the HDFS scan.

True. A filter on the partition column lets the planner read only the matching directories (partition pruning), so far less data is scanned.

Pool · v1 deck · T/FQ7.7 Hive directly executes a HiveQL query on HDFS without any intermediate translation step.

False. The Driver parses HiveQL, builds and optimises a logical plan and compiles it into a DAG of MapReduce, Tez or Spark jobs before any data is touched.

Pool · v1 deck · T/FQ7.8 Bucketing in Hive is particularly useful for optimising JOIN operations between two large tables.

True. If both tables are bucketed on the join key (same/multiple bucket count), a bucket map join / SMB join joins matching bucket numbers directly, avoiding a full shuffle-sort.

Plan · DescriptiveQ7.9 Hive vs. traditional SQL (RDBMS) differences (marked "important exam topic"): compare schema enforcement, ACID, UPDATE/DELETE, indexing and latency.
  • Schema: RDBMS = schema-on-write (validated at insert); Hive = schema-on-read (applied at query time).
  • ACID: RDBMS full; Hive limited - only ORC tables in transactional (ACID) mode.
  • UPDATE/DELETE: RDBMS fully supported; Hive limited (ACID tables only, via delta files + compaction).
  • Indexing: RDBMS uses B-tree indexes; Hive relies on partitions + buckets (and ORC min/max stats).
  • Latency: RDBMS milliseconds (OLTP); Hive seconds-minutes (batch OLAP over TB-PB).
Pool · DescriptiveQ7.10 D1. Explain the Hive architecture: what is the role of HiveServer2, the Driver, and the Metastore? How is a HiveQL query compiled into executable jobs? Draw the component diagram.

Components: HiveServer2 = Thrift/JDBC/ODBC service that accepts queries from many concurrent clients (Beeline, BI tools) with authentication. Driver = manages the query lifecycle: compiler, optimiser, executor. Metastore = catalogue (in MySQL/PostgreSQL) holding table schemas, SerDes, partition locations.

Pool · DescriptiveQ7.11 D2. Differentiate between partitioning and bucketing in Hive. When would you choose each? Describe a scenario in Bangladesh e-commerce data where both are used together.
  • Partitioning: one directory per value of a low-cardinality column (date, division); enables partition pruning. Number of partitions grows with data; too many = small-file problem.
  • Bucketing: rows hashed into a fixed number of files (hash(col) mod N) on a high-cardinality column (user_id); helps bucket map / SMB joins and sampling, does not skip directories.
  • Choose: partition on columns used in WHERE filters with few distinct values; bucket on join/group keys with many values.
  • Scenario: Daraz-style orders table PARTITIONED BY (order_date) so daily sales reports read one day; CLUSTERED BY (customer_id) INTO 64 BUCKETS so joins with the bucketed customers table avoid a shuffle.
Pool · v1 deck · DescriptiveQ7.12 D3. What is schema-on-read? What are its advantages and disadvantages compared to schema-on-write in a traditional RDBMS such as MySQL? Give one example where schema-on-read causes a data quality problem.

Schema-on-read: raw files are stored unchanged and a schema is applied only when queried (via SerDe).

  • Advantages: very fast loading (just copy files); same data can have multiple schemas; handles semi-/unstructured and evolving data; no upfront modelling.
  • Disadvantages: no validation at load, so bad rows are found late; parsing cost at every query; weaker constraints (no PK/FK); slower queries than an optimised RDBMS.
  • Example: a CSV where some rows have amount "1,200" or a missing column - Hive silently returns NULL for the INT column (or shifts columns), so SUM(amount) is wrong with no error. MySQL would reject the insert.
Pool · Plan · AnalyticalQ7.13 A1. Partitioning & Bucketing Design: 5 TB e-commerce transaction table (txn_id, user_id, product_id, amount, country, txn_date). Design a complete partitioning and bucketing strategy to optimise (i) daily revenue reports filtered by country and txn_date, (ii) JOINs with a 10 M-row user profile table keyed on user_id. Write the complete CREATE TABLE DDL. Justify the number of buckets and the partition column(s).

Partition on txn_date (filter in every daily report); country is used as a filter too, but assume few countries, so either add it as a second partition level or rely on ORC min/max stats. Bucket on user_id (join key, high cardinality).

Bucket count, formula: file size per bucket = (partition size) / N; target 128-256 MB.

  1. Assume 3 years of data (assumed) = 1,095 daily partitions; 5 TB / 1,095 = 4.57 GB per day.
  2. N = 32: 4.57 GB / 32 = 143 MB per bucket file (about 1 HDFS block).
  3. User table: 10 M rows x 200 B (assumed) = 2 GB; bucket it on user_id into the same 32 buckets = 62.5 MB each, so bucket map / SMB join pairs bucket i with bucket i.
CREATE TABLE transactions (
  txn_id BIGINT, user_id BIGINT, product_id BIGINT,
  amount DECIMAL(12,2), country STRING)
PARTITIONED BY (txn_date DATE)
CLUSTERED BY (user_id) SORTED BY (user_id) INTO 32 BUCKETS
STORED AS ORC TBLPROPERTIES ('orc.compress'='SNAPPY');

CREATE TABLE users (user_id BIGINT, name STRING, city STRING)
CLUSTERED BY (user_id) SORTED BY (user_id) INTO 32 BUCKETS
STORED AS ORC;
SET hive.optimize.bucketmapjoin.sortedmerge=true;

Meaning: a daily-by-country report scans one 4.57 GB partition instead of 5 TB; the user join needs no shuffle. Not partitioning by user_id (10 M directories) or by country+date with many countries avoids the small-file problem.

Pool · Plan · AnalyticalQ7.14 A2. Query Compilation to MapReduce: write HiveQL to find the top 5 products by total revenue in 2023; trace how Hive compiles it into MapReduce stages (Map output, shuffle key, Reduce computation). How would switching from MapReduce to Tez change the plan? (Plan version also asks: monthly average amount per country for Q1 2024.)
SELECT product_id, SUM(amount) AS revenue
FROM transactions
WHERE txn_date BETWEEN '2023-01-01' AND '2023-12-31'
GROUP BY product_id
ORDER BY revenue DESC
LIMIT 5;

-- Plan item: monthly average per country, Q1 2024
SELECT country, MONTH(txn_date) AS mon, AVG(amount) AS avg_amt
FROM transactions
WHERE txn_date BETWEEN '2024-01-01' AND '2024-03-31'
GROUP BY country, MONTH(txn_date);
  • Job 1 Map: reads only the 2023 partitions (pruning), emits (product_id, amount); map-side partial SUM (combiner / hash aggregation).
  • Shuffle key: product_id.
  • Job 1 Reduce: SUM(amount) per product_id; writes (product_id, revenue) to a temp HDFS dir.
  • Job 2: Map reads temp output, emits top-5 candidates; single reducer sorts by revenue DESC and applies LIMIT 5.
  • Tez: same operators become one DAG (Map -> Reduce -> Reduce) in one application; no temp HDFS write between jobs, containers reused, so lower latency.
v1 deck · AnalyticalQ7.15 Given a HiveQL query with two JOINs and a GROUP BY, draw the MapReduce DAG that Hive would generate, identifying the shuffle key at each stage.

Example (assumed): SELECT c.city, SUM(o.amt) FROM orders o JOIN customers c ON o.cust_id=c.cust_id JOIN products p ON o.prod_id=p.prod_id GROUP BY c.city.

Job1: Map(orders, customers) --shuffle key: cust_id--> Reduce: join1 -> tmp1
Job2: Map(tmp1, products)    --shuffle key: prod_id--> Reduce: join2 -> tmp2
Job3: Map(tmp2) emit (city, amt) --shuffle key: city--> Reduce: SUM -> output

Each common (reduce-side) join is one MR job keyed on its join column; the GROUP BY adds one job keyed on the group-by column. If both joins used the same key they merge into one job; a small table becomes a map join (no shuffle stage).

Pool · v1 deck · DiscussionQ7.16 Spotify's co-occurrence query runs GROUP BY song_a, song_b over 2 billion playlist rows. Estimate the output size if there are 30M songs. Propose a partitioning + bucketing scheme for the playlist_songs Hive table that would reduce the shuffle size for this query.

Formula: distinct unordered pairs = C(n,2) = n(n-1)/2.

  1. Upper bound: C(30M,2) = 4.5 x 1014 pairs; at 12 B per row (two INT ids + 4-byte count, assumed) = 5.4 PB.
  2. Realistic bound from data: 2 B rows, 20 songs per playlist (assumed) = 108 playlists x C(20,2)=190 = 1.9 x 1010 pairs = about 228 GB emitted before aggregation; the output is at most this, since most of the 4.5 x 1014 pairs never co-occur.

Scheme: partition playlist_songs by week/dt (only new weeks processed incrementally); bucket and sort by playlist_id so the self-join (a.playlist_id = b.playlist_id) is a bucket/SMB join with no shuffle; add a.song_id < b.song_id to halve pairs; map-side aggregation and a HAVING count threshold cut shuffle further.

Meaning: the shuffle is bounded by real co-occurrences (hundreds of GB), not the 5.4 PB theoretical matrix.

v1 deck · DiscussionQ7.18 Spotify uses Luigi while other companies use Apache Airflow. Compare the two on: dependency declaration style, backfill capability, and UI/observability. Which would you choose for a 100-step daily pipeline?
  • Dependencies: Luigi = each Task declares requires() and output() targets; the graph is pulled backward from the target. Airflow = explicit DAG in Python with operators linked by >>, schedule attached to the DAG.

Book ch07 · ShortQ7.22 What problem does Apache Tez solve that Hive-on-MapReduce does not? For a HiveQL query that compiles to three MapReduce jobs with 500 MB of intermediate data at each stage boundary, calculate the HDFS I/O saved by using Tez instead.

Tez runs the whole query as one DAG: no HDFS write/read between jobs, no repeated job start-up, container reuse, and flexible edges (no forced Map before every Reduce).

Formula: saved = boundaries x (write + read).

  1. 3 jobs = 2 boundaries.
  2. Per boundary: write 500 MB + read 500 MB = 1,000 MB.
  3. Total = 2 x 1,000 = 2,000 MB (2 GB) logical; with HDFS replication 3 the writes are 3 x 500, so 2 x (1,500 + 500) = 4 GB physical.

Meaning: Tez passes the 500 MB between stages over local disk/memory instead of HDFS. (If "each boundary" counts the final output too, 3 boundaries = 3 GB logical, assumed not.)

Book ch07 · ShortQ7.23 What is Hive LLAP? Describe the three components of LLAP architecture and explain why LLAP enables sub-second latency for repeated queries over the same table.

LLAP (Live Long And Process): long-running daemons on each node that execute Hive fragments with caching. Components: (1) LLAP daemons - persistent processes with executor threads; (2) in-memory columnar cache (off-heap, ORC data + metadata); (3) Tez AM / coordinator that plans the DAG and sends fragments to daemons (with I/O elevator threads for async reads).

Sub-second because there is no container start-up (JVMs are warm, JIT-compiled) and repeated queries read hot columns from RAM instead of HDFS.

Book ch07 · ShortQ7.24 What is the difference between rule-based optimisation (RBO) and cost-based optimisation (CBO) in Hive? Give one example where RBO would produce a suboptimal plan that CBO would avoid.

RBO applies fixed rewrite rules (predicate pushdown, column pruning) regardless of data size. CBO (Apache Calcite) uses table/column statistics to estimate cost and picks join order and join type.

Example: big_fact JOIN medium JOIN tiny_dim written in that order - RBO joins in written order (fact x medium first, huge shuffle); CBO sees row counts, joins the filtered tiny dim first and turns it into a map join, shrinking intermediate data.

Book ch07 · ShortQ7.25 Explain Hive's Sort-Merge Bucket Join. What preconditions must both tables satisfy, and why does this join require no shuffle at query time?

SMB join: each mapper merges bucket i of table A with bucket i of table B using a sorted merge.

Preconditions: both tables bucketed on the join key, same number of buckets (or a multiple), and sorted by the join key (SORTED BY); settings like hive.optimize.bucketmapjoin.sortedmerge=true.

No shuffle because the data was already hash-partitioned and sorted at write time: matching keys are guaranteed to be in matching bucket files.

Book ch07 · ShortQ7.26 What is the Presto Connector SPI? Name three data sources that Presto can query through connectors, and explain what interface the connector must implement for each source.

The Service Provider Interface is the plugin API that lets Presto query any source. Sources: Hive/HDFS, MySQL/PostgreSQL (JDBC), Kafka (also Cassandra, MongoDB).

Each connector implements the same interfaces: ConnectorMetadata (schemas, tables, columns, stats), ConnectorSplitManager (divide data into splits for parallelism - HDFS blocks, JDBC ranges, Kafka partitions), and ConnectorRecordSetProvider / PageSourceProvider (read rows from a split); optionally a PageSink for writes.

Book ch07 · ShortQ7.27 A data engineer argues that Presto should replace Hive entirely because Presto is always faster. Write a detailed counter-argument using a specific workload scenario where Hive is the correct choice.

Presto is faster for interactive queries but keeps intermediate state in memory with weak mid-query fault tolerance. Scenario: a nightly ETL over 200 TB of clickstream with large joins and aggregations running 5 hours. In Presto, one worker failure or a join exceeding memory kills the whole query; it restarts from zero. Hive-on-Tez spills to disk, retries only failed tasks, writes ACID/ORC tables with dynamic partitions, and maximises throughput on YARN. So Hive for long batch ETL, Presto for ad-hoc reads on the same Metastore.

Book ch07 · ShortQ7.28 HiveServer2 replaced the original Hive command-line tool. What two problems with the original tool did HiveServer2 address, and what interface (protocol) does HiveServer2 expose to clients?

(1) No multi-client concurrency - the old CLI/HiveServer1 ran one session per process. (2) No authentication/security - no Kerberos/LDAP, users accessed the Metastore and HDFS directly. HiveServer2 exposes a Thrift-based RPC service used by JDBC/ODBC drivers (Beeline), over binary or HTTP transport.

Book ch07 · ShortQ7.29 What is vectorized execution in Hive? Explain the difference from the Volcano (row-at-a-time) execution model, and identify which file format is best suited for vectorized execution in Hive.

Vectorized execution processes a batch of ~1,024 rows per operator call, column by column in primitive arrays. Volcano calls next() once per row through every operator (virtual calls, poor CPU cache use). Batches give tight loops, SIMD, fewer function calls - several times less CPU. Best format: ORC (columnar, Hive's native vectorized reader).

Book ch07 · ShortQ7.30 A Presto query fails with "Query exceeded maximum memory." Explain: (a) why this error occurs; (b) why the same query would not fail in Hive-on-Tez; (c) what you should do to fix the problem without switching engines.

(a) Presto holds hash-join build sides and aggregation state in memory; when it exceeds query.max-memory / per-node limits the query is killed. (b) Hive-on-Tez spills to disk and processes in smaller tasks, so it is slower but finishes. (c) Fix: raise query.max-memory(-per-node), enable spill-to-disk, put the smaller table on the build side / use partitioned (not broadcast) join, filter or pre-aggregate earlier, add workers, or split the query by partition.

Book ch07 · ShortQ7.31 Explain Hive's Map Join strategy. What is the default table size threshold for a Map Join, and what happens during query execution that eliminates the shuffle?

The small table is loaded into an in-memory hash table, shipped to every mapper (distributed cache), and each mapper joins its split of the large table locally. Default threshold: 25 MB (hive.mapjoin.smalltable.filesize; hive.auto.convert.join.noconditionaltask.size is 10 MB). A local task builds the hash table before the map phase, so the join is map-only: no shuffle or reduce.

Book ch07 · AnalyticalQ7.34 AP Window Function Design: table user_daily_activity(user_id, activity_date, minutes_streamed (0 if not active), country). (a) HiveQL for each user and date: 7-day rolling average of minutes_streamed. (b) Using LAG, number of days since each user last had non-zero minutes_streamed. (c) Using NTILE(10), divide users into deciles by total minutes in the past 30 days and compute churn rate per decile. (d) How would (a)-(c) be compiled by Hive-on-Tez vs Hive-on-MapReduce; how many jobs/stages each?
-- (a)
SELECT user_id, activity_date,
 AVG(minutes_streamed) OVER (PARTITION BY user_id ORDER BY activity_date
   ROWS BETWEEN 6 PRECEDING AND CURRENT ROW) AS avg7
FROM user_daily_activity;
-- (b) previous active day per user
SELECT user_id, activity_date,
 DATEDIFF(activity_date, LAG(activity_date) OVER (PARTITION BY user_id ORDER BY activity_date)) AS gap_days
FROM user_daily_activity WHERE minutes_streamed > 0;
-- (c) churned = no activity in the last 7 days (assumed)
WITH t AS (SELECT user_id, SUM(minutes_streamed) tot,

  FROM user_daily_activity WHERE activity_date >= DATE_SUB(CURRENT_DATE,30) GROUP BY user_id)
SELECT d, AVG(IF(last_act < DATE_SUB(CURRENT_DATE,7) OR last_act IS NULL,1,0)) churn_rate
FROM (SELECT *, NTILE(10) OVER (ORDER BY tot) d FROM t) x GROUP BY d;

(d) Each window = a shuffle on its PARTITION BY key + sort on ORDER BY. MapReduce: (a) 1 job, (b) 1 job, (c) 3 jobs (GROUP BY user, global NTILE with a single reducer, GROUP BY decile), each writing to HDFS. Book ch07 · AnalyticalQ7.35 AP Join Strategy Selection. Tables: transactions 80 billion rows, 12 TB compressed, bucketed on customer_id (500 buckets); customers 200 million rows, 80 GB, bucketed on customer_id (500 buckets); dim_country 250 rows, 40 KB, not bucketed; dim_category 8,000 rows, 2 MB, not bucketed. (a) transactions JOIN dim_country: optimal strategy and why; estimate network traffic for the alternative Common Join. (b) transactions JOIN customers (both 500 buckets on customer_id): optimal strategy; what additional condition must hold for SMB join? (c) Three-table join transactions JOIN customers JOIN dim_category: join order and strategy for each; justify via CBO cost minimisation. (d) What ANALYZE TABLE statistics would the CBO use to choose these strategies without hints?

(a) Map (broadcast) join: 40 KB is far below the 25 MB threshold. Common join shuffles both sides: about 12 TB + 40 KB = ~12 TB over the network. Map join: 12 TB / 256 MB splits = 49,152 mappers (assumed 256 MB splits) x 40 KB = ~1.9 GB (less with per-node distributed cache). Meaning: about 6,500x less traffic.

(b) Bucket map join / Sort-Merge Bucket join: same key, same bucket count (500). Extra condition for SMB: both tables must be SORTED BY customer_id within buckets (and SMB settings enabled); 80 GB / 500 = 160 MB per bucket, so bucket i of transactions merges with bucket i of customers, no shuffle.

(c) Order: (transactions SMB-join customers) first using the existing bucketing (no shuffle), then map-join dim_category (2 MB broadcast) in the same map stage. CBO picks the plan with the lowest estimated rows shuffled / bytes read: neither join shuffles the 12 TB fact table.

(d) ANALYZE TABLE ... COMPUTE STATISTICS [FOR COLUMNS]: row count, total/raw data size, number of files; column stats: NDV (distinct values), null count, min/max, avg/max column length. Plus Metastore info on bucketing/sort columns. Size vs threshold picks map join; bucketing metadata picks SMB; NDV gives join cardinality for ordering.

import time, requests
H = {"X-Presto-User": "analyst", "X-Presto-Catalog": "hive"}
def profile(sql, host="http://coord:8080"):
    t0 = time.time()
    d = requests.post(f"{host}/v1/statement", data=sql, headers=H).json()
    while d.get("nextUri"):
        time.sleep(0.5)
        d = requests.get(d["nextUri"], headers=H).json()
    s = d["stats"]
    print(s["state"], f"{time.time()-t0:.2f}s",
          s.get("processedBytes"), s.get("processedRows"),
          s.get("completedSplits"), s.get("peakMemoryBytes"))

Key idea: POST to /v1/statement, follow nextUri until it disappears (FINISHED/FAILED), then read the stats block.
