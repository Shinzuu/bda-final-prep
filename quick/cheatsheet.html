CSE 4345 BDA — Cheat sheet, Weeks 5–10

★ = very likely · "X | Y" = X side vs Y side

Week 5 — YARN, file formats, compression

YARN

★YARN: Hadoop 2.0 (2013), split JobTracker into RM + per-job AM, any framework, 10,000+ nodes

★ResourceManager (RM): 1 per cluster, sees all nodes, Scheduler grants containers, ApplicationsManager starts AMs

NodeManager (NM): 1 per node, launches + monitors containers, heartbeats to RM

★ApplicationMaster (AM): 1 per job (12 jobs = 12 AMs), requests containers, tells NMs what to launch, retries tasks

★Container: slice of one node, fixed vcores + RAM, task runs inside

★YARN flow: submit→RM, RM starts AM, AM asks 100 {4c, 8 GB}, RM grants 80 free, NMs launch, AM unregisters

★Multi-framework: Spark, Tez, Samza, MR share one cluster, own AM each, generic containers; 1.x = MR only

★NM failure: heartbeats stop, lost after >10 min, containers FAILED, AM re-requests on healthy nodes near replicas, map output rerun

AM failure: RM restarts AM, max 2 attempts; RM HA: ZooKeeper failover <60 s

★Capacity Scheduler: guaranteed queue %, borrow idle, pre-empt back, SLAs (ETL 60 / stream 30 / ad-hoc 10)

★Fair Scheduler: equal share per running job, grows as jobs end, short jobs fast

FIFO: first job takes all, later jobs wait, starvation

★Pre-emption: reclaims borrowed share, 30 s grace + checkpoint-on-preempt (LinkedIn fix)

★DRF: Dominant Resource Fairness, CPU + RAM, equalise each user's largest share

Two-level (YARN) vs one-level (K8s): AM places own tasks, locality, executor reuse, AM crash hits one job

Formats & codecs

★Splittable: many Mappers read parts in parallel, start anywhere in file

★Row vs columnar: CSV/Avro whole records, write-friendly | Parquet/ORC needed columns only, compress better

★Parquet: columnar, read-heavy, Spark/ML, row groups ~128 MB → column chunks → pages, footer min/max stats

★Predicate pushdown: footer min/max, skip row groups that cannot match, never read from disk

ORC: columnar, Hive, highest compression, ACID, vectorised reads

★Avro: row, JSON schema with data, cheap appends, Kafka→HDFS ingest

★Schema evolution: writer vs reader schema, missing field → default, unknown field → ignored

★Gzip: high ratio, slow, NOT splittable → 1 Mapper/file, cluster idles

Snappy: fast, medium ratio, inside Parquet/Avro; Zstd: best cold-storage ratio

Splittable codecs: bzip2, LZO + index; not gzip, Snappy, Zstd alone

Cases

★LinkedIn: 3 silos → 1 YARN 5,000 nodes, util 45→78% (1.73×), prod queue 40%, YARN = OS, Samza long-running + Kafka offset

★Telecom CDR: gzip CSV 4/80 cols 6 h; fix ORC/Parquet + dt=/region=, 10 TB×4/80 = 500 GB (20×, ≈18 min), Capacity

★bKash lake: Kafka→Avro ingest, nightly Parquet+Snappy dt=/region=, >2 yrs ORC+Zstd (−60%), old gzip CSV slow

★Scheduler 2,000 needed / 1,250 free: Capacity pre-empts 750, Fair equal share, FIFO 2 waves + starvation

X vs Y

Hadoop 1.x vs YARN: JobTracker MR only ~4,000 nodes slots | RM + AM, any framework, containers

RM vs AM: cluster, grants | job, requests + retries

Parquet vs ORC: Spark/ML | Hive, ACID, best compression

Avro vs Parquet: row, write, evolve | columnar, read, analyse

Formulas

max containers = min(RAM ÷ c_ram, vCPU ÷ c_cpu)

nodes needed = ceil(tasks ÷ per-node) (Hive {4 GB,2 vCPU} on 64 GB/16: 8/node → 1,250 nodes)

bytes read = D × k ÷ N (10 TB × 3/100 = 300 GB, 33×)

Mappers = size ÷ 128 MB (10 GB Parquet 80 vs gzip 1)

granted share = granted ÷ requested (80/100 → 320 cores, 640 GB)

queue executors = min(queue RAM ÷ c_ram, queue vCPU ÷ c_cpu) (a2i 60 nodes → 240, CPU-bound)

dominant share = max(RAM %, CPU %) (8/64=12.5%, 4/16=25% → CPU)

Week 6 — Spark

★Spark vs MR iterative: caches RDDs in RAM vs HDFS read/write each iteration, 10–100×

★RDD: Resilient Distributed Dataset, read-only, partitioned, from HDFS or another RDD

★Lineage: recipe of transformations, recompute lost partition only, immutable + deterministic, "computation is the backup"

★Transformation: lazy, new RDD, DAG node (map, filter, reduceByKey)

★Action: eager, runs DAG, value to Driver / output (count, collect, saveAsTextFile)

★Lazy eval: whole-plan optimise, pipeline narrow steps; filter(x>1000).first() scans 1st partition only

★Narrow vs wide: 1 parent, same stage | many parents, shuffle, new stage boundary

★Ecosystem: Spark SQL, MLlib, Structured Streaming, GraphX — NOT HBase

★Cluster Manager: YARN, Kubernetes, Mesos, Standalone, local[n] — not YARN only

★DataFrame: named columns, schema, SQL, Catalyst optimiser

Driver: main(), builds DAG, schedules tasks; Executors: worker JVMs, run tasks, cache data

collect() on 300 GB: Driver OOM; use take(n), saveAsTextFile()

cache/persist: MEMORY_ONLY evict + recompute, MEMORY_AND_DISK spill, MEMORY_ONLY_SER compact; objects 2–5× raw

toDebugString after cache(): same lineage + storage level, CachedPartitions after action

★reduceByKey: local combine before shuffle (Combiner); groupByKey ships every pair

Skew: hot key → one task OOM, fix reduceByKey/aggregateByKey or salt key; collisions → custom partitioner

Hash vs range partitioner: hashCode % n, default, hot-spots | ordered ranges, sortByKey

coalesce vs repartition: fewer partitions no shuffle (narrow) | full reshuffle (wide)

Checkpoint: save to HDFS, cut long/wide lineage

Scenarios

★Executor crash: missed heartbeats, Driver marks lost, rebuild lost partitions from lineage on healthy executors

★Narrow chain loss (parts 3, 7): only 2/10 = 20% redone; after groupByKey fan-in all 10 → checkpoint after shuffle

★K-Means 50 GB ×100: MR 10 TB I/O ≈ 5.6 h; Spark read once + 99 RAM ≈ 18 min, 200× less disk

★Spark does not win: single pass (2–5×), data > RAM, little executor memory, shuffle-bound

★Fraud pipeline: only count() action, reduceByKey wide → 2 stages, 1,234,567 % 8 = 7

★GraySort / 5 lessons: multiplier not panacea, lineage > replication, shuffle bottleneck (sort shuffle + SSD), benchmark marketing, Databricks open source

LR 50 GB on 10×32 GB: MEMORY_ONLY evicts (2–5× bloat) → MEMORY_AND_DISK; cache pays from 3rd iteration

Live UI: run 2 faster (shuffle reuse), cached fastest; groupByKey more shuffle bytes

X vs Y

Replication vs lineage: 3 copies always | recipe, cost only on failure

DataFrame vs RDD: schema + Catalyst | schema-less objects

Formulas

per-node efficiency = (T_old × N_old) ÷ (T_new × N_new) (72×2,100 ÷ 23×206 ≈ 32×)

speedup = T_old ÷ T_new (127 ÷ 0.96 = 132×)

I/O time = data ÷ bandwidth (1,000,000 MB ÷ 100 MB/s = 10,000 s)

shuffled groupByKey = parts × pairs; reduceByKey = parts × distinct keys (12,000 vs 240)

cache break-even: n = 2 + (n − 1) ÷ speedup, so n ≈ 2: caching pays from the 3rd iteration

blocks = size ÷ 128 MB; partition = hash % n

lineage break-even failures = replication cost ÷ recompute cost (120 s ÷ 6 s = 20)

Week 7 — Hive & SQL-on-Hadoop

★Hive: Facebook 2008, SQL instead of 100+ line Java MR, compiles to MR/Tez/Spark on YARN

★Metastore: RDBMS (MySQL/PostgreSQL), schemas, partitions, HDFS paths, SerDe; not NameNode

★Metastore HA: down = no table queryable, HDFS data intact

★Schema-on-read: raw copy, schema at query, bad value → NULL silently, still CREATE TABLE

★Schema-on-write: checked at INSERT, bad rows rejected, clean, rigid (MySQL)

★Hive architecture: HiveServer2 (JDBC/ODBC, auth, Beeline) → Driver → Metastore → MR/Tez/Spark → YARN → HDFS

★Compile: Parser→AST → Semantic (Metastore check) → Logical plan → Optimizer (pruning) → Physical jobs

★Partitioning: sub-dir per low-cardinality value (date, country), WHERE prunes; never user_id (explosion)

★Bucketing: N files by hash(col) % N, same key + N → bucket map join, no full shuffle

★HiveQL vs SQL: batch minutes, limited ACID, no indexes | ms, full ACID

ACID: UPDATE/DELETE only transactional ORC tables

★Not MySQL replacement: COUNT(*) on 1 TB 5–10 min

★Presto: in-memory pipeline, vectorised 1,024-row batches, cost-based optimizer, connectors; 5–60 s

★Presto same Metastore: no table redefinition; bad for 50 TB ETL (job restarts, Hive retries tasks)

Tez: one DAG, streaming edges, no intermediate HDFS

★Top-5 query: 2 MR jobs (GROUP BY SUM + combiner, then 1 reducer sort/LIMIT); Tez = 1 DAG

★Monthly AVG: combiner keeps (sum, count), never avg of avgs; Q1 = 91×5 = 455 of 5,475 parts

★DDL: PARTITIONED BY (txn_date, country) (not in col list), CLUSTERED BY (user_id) INTO 32 BUCKETS, STORED AS ORC

Live: partitionBy("dt"), /*+ BROADCAST(s) */, EXPLAIN PartitionFilters

★Spotify Discover Weekly: 3 B events/day Kafka→HDFS, Hive co-occurrence, Spark ALS, 30 M playlists, implicit feedback, weekly parts 8 h→2 h

★Spotify Q1: partition by week, bucket by playlist_id → bucket-local self-join; Luigi (requires/output) vs Airflow (scheduler, backfill, retries, alerts)

X vs Y

Hive+MR vs Presto: HDFS between stages 5–15 min | in-memory 5–60 s

Static vs dynamic partition: named value | from last SELECT columns

Hive vs Spark SQL: batch | Catalyst in memory, same Metastore

Pruning vs pushdown: skip directories | skip row groups by min/max, stack

Partition vs bucket: skip | join

Formulas

fraction read = matched ÷ total partitions (1/36 = 2.8%)

bucket = key mod N (1,000,007 mod 32 = 7)

file size = S ÷ (P × N) (4,000 GB ÷ 116,800 ≈ 34 MB)

map-side reduction = rows ÷ groups (50 M ÷ 200 = 250,000×)

ALS size = (users + items) × k × 4 B (105 M × 200 B = 21 GB)

pairs = n(n − 1) ÷ 2 (30 M songs ≈ 4.5×10^14)

Week 8 — Kafka, pipelines, Lambda/Kappa, lakes

★Sqoop: SQL-to-Hadoop, bulk RDBMS↔HDFS, batch MR, parallel PK ranges, incremental check-column + last-value

★Flume: logs → HDFS, Source → Channel → Sink; roll 10 s = 8,640 small files → roll 300–600 s / 128 MB

★Kafka: distributed, partitioned, replicated append-only commit log

★Topic / partition / offset / broker / R: event type | ordered slice | position | server | leader + R−1 followers

Kafka throughput: sequential append, zero-copy sendfile(), batching, partition parallelism

Kafka fault tolerance: follower elected leader (ZooKeeper/KRaft), durable log, offsets resume

★Consumer groups: each group own offsets, every group gets every event; 1 partition → 1 consumer in group

Key by id: hash(key) mod P, same partition, order only within partition

Retention / replay: kept e.g. 7 days, seek back; queue deletes after read

Live: seek_to_beginning idempotent; new group + earliest → offset 0

★Lambda (Marz 2011): batch (full data, accurate, hours) + speed (recent, seconds) + serving (merge)

★Lambda weakness: dual code paths, kept in sync, 30–40% effort, two clusters

★Kappa: no batch layer, one stream path, reprocess by log replay (v2 from offset 0, catch up, swap)

★Kappa needs: replay faster than live, stateful joins + event-time + exactly-once (Flink), long retention / Iceberg

★Kappa risks / unsuitable: history > retention lost, slow replay, 2× compute; bKash EOD reconciliation, 10-yr hospital retrain

★Data lake: raw, any format, schema-on-read, HDFS/S3, ML

★Swamp: no catalogue, owners, duplicates, PII; fix catalogue, ACL, quality, Iceberg/Delta

★Bank scenario: Sqoop nightly Oracle, Kafka card-swipes keyed by card + Spark Streaming <200 ms, 2nd group 1-min windows, Lambda for audit

★Flink late events: event time, 5-min tumbling, watermark 30 s, allowed lateness, side output

Netflix: Kafka single source of truth, 7-day retention reprocess, S3 bounded stream, Schema Registry, backpressure

X vs Y

Point-to-point vs bus: O(N²) brittle, no replay | N links, decoupled, replay

Sqoop vs Flume: tables batch | logs streaming

Flume vs Kafka: push into Hadoop | any→any log, replay, many consumers

Batch vs speed layer: all, accurate, hours | recent, approximate, seconds

Lake vs warehouse: raw, schema-on-read, ML | clean tables, schema-on-write, BI

Memory vs file channel: fast, loses on crash | disk, survives

Kafka vs Hive partition: ordered slice, parallelism | directory, pruning

Formulas

point-to-point jobs = N(N − 1); bus = N (50: 2,450 vs 50)

replay time t = H ÷ (S − L); never if S ≤ L (≈ 22 h)

brokers = ceil(topics × P × R ÷ max per broker) (144,000 ÷ 50,000 → 3)

copies = P × R; survives R − 1; active consumers = min(C, P)

MB/s = msgs/s × bytes ÷ 10^6 (505,000 × 100 = 50.5)

serving = batch view + real-time view (1,200,000 + 85,000)

Week 9 — Data visualization

★Data-ink ratio (Tufte): data ink ÷ total ink, maximise, "erase if no info lost"

Chartjunk: 3-D, gradients, heavy grid, borders, single-series legend

★Shneiderman mantra: overview first, zoom and filter, details on demand

Shneiderman 7 types: 1-D, 2-D, 3-D, temporal, multi-dim, tree, network; tasks + relate, history, extract

★Grafana: real-time ops, InfluxDB/Prometheus, 5 s poll

★Histogram: distribution, shape, centre, spread (pie part-whole, line time, treemap hierarchy)

★Pie: ≤ 4 categories only, angles hard → sorted horizontal bars

★Overplotting: blob hides density; alpha (relative density, saturates), hexbin (counts), KDE (shape, modes, tails)

★Hexbin: hexagon coloured by count, 10 M points → ~10,000 cells

★D3.js: binds data to SVG DOM, interactive browser, not static PNG

★Choropleth: region colour = rate (per 100,000); counts → bubble map

★Lie factor: effect shown ÷ effect in data, 1 = truthful, start axis at 0

★Anscombe (1973): same means, variance, r = 0.816, y = 3 + 0.5x, different shapes → plot first

★Small multiples: same chart per subset, same scale (NYT 50 states); Sparklines: word-sized lines (Tufte 2006)

Tumbling window: fixed, non-overlapping, each event once, aggregate before browser

★Data cube: pre-computed aggregates per dimension combo, <1 s, stale ≤24 h, fixed dimensions

★DGHS dashboard: small multiples 7-day lines + choropleth + cube; Kafka→Spark 5-min→InfluxDB→Grafana; grouped bars, no 3-D pie

★Twitter sentiment 10,000/s: 1-min tumbling, line per topic, hexbin clusters, send aggregates, Canvas, WebSocket→D3

★NYT COVID: no grid, 50-state grid; overview→state dropdown→tooltip; 7-day avg removes weekend zigzag, lags ~3 days

★Problem→fix: GPS blob → hexbin; 80 B rows slow → cube; map→dropdown→click = mantra; live → WebSocket

Grafana redesign: 3-D → flat, axis from 500 → 0, grid/gradient off, tooltip

Live D3: domain([0, max]), no grid, flat colour, tooltip, sparkline per bar

1 M trips dashboard: KPI + sparklines, city multiples, hexbin → filters from cube → hover/click

X vs Y

Small multiples vs animation: all at once | one frame, memory

Alpha vs hexbin: relative, saturates | exact counts

Hexbin vs KDE: counts | smooth shape, modes

Data cube vs AQP: exact, stale | fresh, approximate (sampling, BlinkDB), not finance

Grafana poll vs WebSocket: 5 s, ops | sub-second push, D3 tickers

Tableau/Power BI vs D3.js: drag-drop reports | custom coded SVG

7-day vs 14-day avg: reacts faster | smoother, delays peaks

Formulas

lie factor = effect shown ÷ effect in data (50% ÷ 5% = 10)

data-ink ratio = data ink ÷ total ink (200/800 = 0.25 → 0.5)

cube cells = product of cardinalities; cuboids = 2^n (9,344,000; 16)

events per window = rate × window length (3,000 × 60 = 180,000)

refreshes/day = 86,400 ÷ refresh s (17,280)

alpha darkness = 1 − (1 − α)^n (0.98^100 → 0.87)

Week 10 — Social media, time series, health

★Prophet: Facebook, y(t) = g(t) + s(t) + h(t) + ε(t), trend changepoints, Fourier seasonality, holidays, Stan

★changepoint_prior_scale: default 0.05 stiff; 0.5 bends fast, chases noise, wider band; trend g(t) catches new wave

weekly_seasonality=False: weekly data, no day-of-week pattern

★ARIMA(p,d,q): AR last p values, I difference d → stationary, MA last q errors, hand-tuned

★Prefer Prophet: many series, multi-seasonality, holidays (Eid), missing data, outliers; ARIMA: short, stationary, small

★Time series shuffle: destroys autocorrelation, trend, seasonality; back-test time-ordered

★Louvain: community detection, greedy modularity, O(n log n)

★Louvain steps: node alone → move to best modularity gain → collapse to super-nodes → repeat until no gain

★Sparse graphs: few hundred links of millions, Twitter density ≈ 8.5×10⁻⁷

★Twitter = news medium (Kwak 2010): 22.1% reciprocity, power-law hubs, 85% trends = news

★VADER: lexicon + rules, CAPS, "!!!", negation, emojis, no training; compound ±0.05 pos/neutral/neg

★Social analyses + risk: community (profiling minorities), sentiment (suppress dissent), influence max Kempe greedy 63%, NP-hard (microtargeting)

★HIPAA: US health data privacy/security, 18 identifiers (finance = GLBA)

★AlphaFold: protein 3D structure from amino-acid sequence, 170,000 PDB, Nobel 2024

★Google Flu Trends: over-predicted 2× 2012–13; hubris (r² 0.97 training), autocomplete confounding, media amplification

★MRI/CT: unstructured binary DICOM, CNN, not SQL

★Isolation Forest: random splits, anomaly isolated in fewer splits, short path

STL: trend/season/residual, flag |residual| > k × IQR

★Health challenges: linkage → de-identification; silos (PDPA consent) → federated learning; small counts → differential privacy

★Flu early warning: APIs→Kafka, POS→Sqoop, Parquet by date/district; symptom counts, VADER, spike; Prophet per district + regressors; ethics, supplement DGHS

★SKU 90-day forecast: Sqoop, Parquet by sale_date (not SKU), Prophet, groupBy(sku).applyInPandas, 8 h→12 min; bottleneck CPU fitting

★Dengue: ED chief complaints HL7 FHIR (BioSense, <72 h) + tweets → Kafka → Spark NLP → Prophet + monsoon/rain; back-test + silent season

X vs Y

Louvain vs PageRank: which group | how important

ARIMA vs Prophet: stationary, hand-tuned, 1 season | auto, many seasons, holidays

Prophet vs LSTM: interpretable, little data | black box, big data, GPU

Twitter vs Facebook: directed, 22.1% mutual, news | mutual ≈100%, social

STL vs Isolation Forest: residual > k×IQR | few random splits

ILINet vs syndromic: confirmed, 1–2 wk late | early, noisy (tweets, pharmacy, ED)

HIPAA vs GDPR: US health, 18 identifiers | EU all personal data, minimisation, erasure

DP vs federated learning: noise on aggregates | train locally, share weights

Safe harbour vs expert determination: remove 18 identifiers | statistical low-risk proof

Formulas

reach = d + d² + d³ (45 → 93,195, upper bound)

speed-up = old ÷ new (480 ÷ 12 = 40×; 400×2 s ÷ 20 = 40 s)

spike = current ÷ baseline (12,000 ÷ 40 = 300×)

anomaly if |residual| > k × IQR (3×4 = 12; 15 yes, −9 no)

y = g + s + h + ε (500+40+150 = 690)

storage = patients × size (10,000 × 200 GB = 2 PB)
