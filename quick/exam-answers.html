W06: K-Means on 50 GB, MapReduce vs Spark (10 marks)

Given: 50 GB of data, 128 MB HDFS blocks, 100 ms to read one block, 100 iterations. (1)

1. Blocks and one full scan (1)

Formula: blocks = data size ÷ block size.

50 GB = 50 × 1,024 MB = 51,200 MB. Blocks = 51,200 ÷ 128 = 400 blocks.

One scan = 400 × 100 ms = 40,000 ms = 40 s.

2. MapReduce I/O cost (3)

Each iteration is a separate MapReduce job, so it re-reads the whole dataset from HDFS and writes its output back to disk.

Formula: reads = iterations × blocks.

Reads = 100 × 400 = 40,000 block reads.

Time = 40,000 × 100 ms = 4,000,000 ms = 4,000 s ≈ 66.7 min.

Meaning: MapReduce pays the full disk read 100 times.

3. Spark I/O cost (3)

Spark reads HDFS once, keeps the points in executor memory with cache(), and runs iterations 2 to 100 from RAM.

Reads = 400 block reads, time = 400 × 100 ms = 40 s. Later RAM passes are near zero (assumed).

Speed-up = 4,000 s ÷ 40 s = 100× on I/O.

Summary: block reads 40,000 vs 400. I/O time 4,000 s vs 40 s.

Meaning: caching turns 100 disk scans into 1, so Spark wins any iterative algorithm whose data fits in memory.

4. Executor crash: recovery by lineage (2)

The driver notices missing heartbeats and marks the executor lost. Its cached partitions are gone.

Spark keeps the lineage of every RDD: the chain of transformations (textFile → map → cache). It recomputes only the lost partitions on other executors, re-reading those blocks from an HDFS replica.

Worst case: all cached partitions lost = one extra full scan, 40 s. No in-memory replication is needed. For very long lineages, use checkpoint().

W07: Hive design for a 5 TB e-commerce table (10 marks)

Table: (order_id, user_id, product_id, amount, country, order_date). Query 1: daily revenue by country. Query 2: join with a 10 M-row user table on user_id.

1. Partitioning (2)

Partition by order_date. Every daily report filters on the date, so Hive reads one folder instead of 5 TB: partition pruning.

Assume 3 years = 1,095 days. 5 TB ÷ 1,095 ≈ 5,000 GB ÷ 1,095 ≈ 4.57 GB per day.

Country stays a normal column (ORC min/max stats skip blocks). A second partition level by country adds many small folders, so skip it unless there are only a few countries.

2. Bucketing (2)

Bucket both tables on user_id into the same number of buckets, sorted by user_id. Bucket = hash(user_id) mod N.

Choose N for about one HDFS block per file: 4.57 GB ÷ 32 ≈ 143 MB, so N = 32.

Bucket i of orders joins only bucket i of users: a bucket map join / sort-merge-bucket join, with no full shuffle.

3. DDL (2)

CREATE TABLE orders (
  order_id BIGINT, user_id BIGINT, product_id BIGINT,
  country STRING, amount DECIMAL(12,2))
PARTITIONED BY (order_date DATE)
CLUSTERED BY (user_id) SORTED BY (user_id) INTO 32 BUCKETS
STORED AS ORC;

CREATE TABLE users (user_id BIGINT, name STRING, city STRING)
CLUSTERED BY (user_id) SORTED BY (user_id) INTO 32 BUCKETS
STORED AS ORC;

4. Top 5 products by revenue in 2023 (2)

SELECT product_id, SUM(amount) AS revenue
FROM orders
WHERE order_date BETWEEN '2023-01-01' AND '2023-12-31'
GROUP BY product_id
ORDER BY revenue DESC
LIMIT 5;

MapReduce stages: Job 1 map reads only 2023 partitions and emits (product_id, amount); shuffle key = product_id; reduce sums. Job 2: one reducer sorts by revenue and keeps 5. On Tez this is one DAG with no temporary HDFS write.

5. Monthly average per country, Q1 2024 (2)

SELECT country, MONTH(order_date) AS mon, AVG(amount) AS avg_amount
FROM orders
WHERE order_date BETWEEN '2024-01-01' AND '2024-03-31'
GROUP BY country, MONTH(order_date);

Shuffle key = (country, month). The WHERE clause prunes to 91 daily partitions.

W08: Bank pipeline (10 marks)

Needs: (a) nightly sync of 10 M Oracle records, (b) card-swipe fraud decision within 200 ms, (c) risk dashboard no older than 5 min.

1. Tool per stage (5)

(a) Sqoop incremental import (--incremental lastmodified, 8 parallel mappers) into Hive/ORC, scheduled by Oozie or Airflow. Batch, high throughput, YARN retries failed mappers. 10 M × 1 KB (assumed) ≈ 10 GB: minutes.

(b) Kafka takes every swipe (key = card_id, replication factor 3, acks=all): durable and replayable. Flink (or Kafka Streams) scores each event with per-card state and answers in under 200 ms.

(c) Spark Structured Streaming, 1-minute micro-batches from Kafka, writes aggregates to HBase or Druid; Grafana or Kibana reads them. Data is at most a few minutes old, inside the 5-minute limit.

History and model training: Spark and Hive on HDFS, retraining the fraud model nightly.

2. Lambda vs Kappa (4)

Layers: Lambda = batch + speed + serving. Kappa = one streaming layer.

Reprocessing: Lambda recomputes in the batch layer. Kappa replays the Kafka log through new code.

Code: Lambda keeps two code paths that must give the same answer. Kappa has one.

Weakness: Lambda = duplicate logic and higher complexity. Kappa = needs long log retention and a stream engine with exactly-once state; full-history recomputes are slow.

3. Choice (1)

Lambda. The Oracle sync is batch by nature, and regulators need accurate, auditable nightly figures from the batch layer. The speed layer covers fraud and the dashboard.

W10-A: Flu early-warning system for Bangladesh (10 marks)

1. Data sources (2)

Twitter/social media: flu words in Bangla and English (jor, kashi, fever, flu) with location.

Pharmacy sales: daily paracetamol, cough syrup and antiviral sales by district.

Ground truth: IEDCR / DGHS surveillance reports, used to train and validate.

2. Ingestion (1)

Kafka (or Flume) streams tweets; Sqoop or daily file loads bring pharmacy data. Both land in HDFS.

3. Processing with Spark (3)

Clean text and detect the language.

Classify tweets as real illness reports vs news or jokes (MLlib Naive Bayes or logistic regression).

Map each tweet to a district and aggregate daily counts per district.

4. Features and model (2)

Features: tweet trend, pharmacy-sales spike vs baseline, lagged values, seasonality.

Model: ARIMA or Prophet per district, or a regression model, validated against surveillance data on a time-based split.

5. Alerting (1)

Alert when the forecast or count exceeds the baseline mean + 2 standard deviations. Show it on a district map dashboard and send SMS to health officers.

6. Challenges (1)

Noisy text, weak Bangla NLP, urban bias of Twitter, privacy, false alarms from media hype. Google Flu Trends over-predicted about 2× in 2013 for the same reason. Two independent sources cut these errors.

W10-B: Sales forecasting for 5,000 store-products (10 marks)

1. Data (2)

Daily sales per (store, product), plus price, promotions, holidays and weather, stored in HDFS/Hive and partitioned by date.

2. ETL with Spark (2)

Clean the data, fill missing days with zero sales, aggregate to daily or weekly series. 5,000 series × 90-day horizon.

3. Features (2)

Lag-7 and lag-30 values, 7-day and 30-day rolling means, day of week, holiday and promotion flags.

4. Modelling in parallel (2)

Each series is independent: embarrassingly parallel. Group by (store_id, product_id) and train one Prophet or ARIMA model per series with applyInPandas, so 5,000 small models run across the executors.

Alternative: one global gradient-boosted tree model in MLlib with store and product as features.

5. Evaluation (1)

Time-based split (train on the past, test on the last weeks), never random. Score with MAPE and RMSE.

6. Serving and scheduling (1)

Write forecasts to Hive or HBase for dashboards and stock planning. A weekly Airflow or Oozie job retrains and re-forecasts. Bottleneck: the per-series training step; fix by more executors and a shorter training window.

Exam tip: write the W06 numbers clearly: 400 blocks, 40,000 reads, 4,000 s vs 40 s. They carry most of the marks.
